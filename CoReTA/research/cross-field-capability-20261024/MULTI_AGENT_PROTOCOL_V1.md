# 分散条件应用协议 v1：开发实验规格

日期：2026-10-24。状态：行为与实验规格已明确，尚未实现新的运行器、未执行模型实验。本文细化并修正MULTI_AGENT_EXPERIMENT_REVIEW.md；有冲突以本文为准。

## 1. 要验证的主张

在成员各自持有不完整资料时，围绕共同计划定位条件的实际应用，并持续检查修订前后，是否比普通讨论及同工具普通讨论更可靠地组合、保留有效知识？

本轮只测互补信息，不声称成员形成了领域专长。不测来源本身造假；测模型可能出现的遗漏、错误翻译、错误绑定及应用错误。

## 2. 固定对象与权限

- Task：公开作业ID、时长和明确时间语义，不含私有规则或正确计划。
- Source：原件ID、owner、文本。每次模型请求只包含调用者自己的原件；他人合法共享的摘录和条件可见。
- Contribution：宿主生成ID、owner、原件ID及准确摘录、自由文字说明、可选DSL条件。来源必须属于提交者；引用在原件中存在仅证明来源，不证明解释正确。
- Condition：固定ID、版本、表达式、owner、来源。所有成员条件一律标记member_interpretation，模型不能自行升级成宿主强制任务要求。
- Work：宿主版本ID、作者、完整order、简要说明。所有执行结果必须绑定work_version和condition_snapshot。
- Check：合法排列检查、位置、完成时间、每条条件状态及具体操作数。状态为consistent/violates/unknown；unknown不得当作通过。

采用受限DSL：before(a,b)、not_adjacent(a,b)、deadline(a,value)、not_position(a,value)。允许每个原件0到多个条件，不强制一条原件只能有一个条件。宿主分配条件ID，避免让模型复制复杂ID格式。DSL外的知识可在自由说明中交流，但不伪装成已执行检查。

语义错误如错误数字、错误作业仍保留为可执行成员假设；未知作业、非法操作符、缺参数等输入不执行，记unknown/invalid_condition并向B/C提供同样错误信息，不触发额外模型修复调用。技术JSON/schema损坏则按冻结停止规则处理，不能混淆这两类错误。

成员只可修订/撤回自己贡献的条件，可以质疑他人条件。质疑不能直接撤掉对方的条件。宿主按稳定ID应用修订：旧表达式、来源、新表达式或withdraw、理由和快照全部留存。首版不处理复杂跨owner仲裁；本预算内未解决的质疑保留为争议。

## 3. 相同流程，明确三组差异

初始化三次：每位成员只读自己的资料，提交局部知识和可选初步想法；不要求猜完整答案。共享三份初始化用于三组，分别报告每组部署成本中的初始化。各组后续运行不共享输出。

每组五次模型调用：

1. BUILD：轮换编辑者形成W0，读取自己原件及共享贡献。
2. REVIEW-A1/A2/A3：三名成员并行语义上的同一轮复核，各自只读W0、自己原件和本组共享内容。后续成员不能看到本轮其他成员反馈，避免不同调用顺序造成隐含额外轮次。
3. FINAL：编辑者读取全部本轮反馈，提交W1。没有额外付费裁判或循环重试。

| 行为 | A普通讨论 | B同工具普通讨论 | C应用反馈协议 |
|---|---|---|---|
| 自由提出错误、反例、完整修订计划 | 允许 | 允许 | 允许 |
| 成员修订自己的条件 | 允许 | 允许 | 允许 |
| 执行器及原始具体反馈 | 不提供运行时程序反馈 | 提供 | 与B等价提供 |
| REVIEW内容组织 | 自由说明，可主动定位条件 | 同A | 明确指出自己的哪条条件影响W0何处，或明确无相关问题；正确反例本身即有效贡献，不强迫给完整修复 |
| 条件与计划版本关联 | 宿主仅记日志、不控制答案 | 同A | 条件应用状态在修订后自动重算，不因“已回应”而清除 |
| 最终版本采用 | 编辑者选择W0或W1 | 同A | 宿主执行下述版本规则，允许显式带争议提交 |

A/B不能被要求“不要使用C的思想”；其自发定位/闭环都允许。B也可选择保留旧稿或主动发现新增错误。C是“定向应用反馈＋版本保留”的组合机制，首轮不能把效果单独归因于其中某一个。

B/C工具内容在相同work、相同条件下逐字等价；后续各组条件或work发生差异时，不要求报告字面相同。C额外有自动维护的版本关系视图，但必须由已共享记录计算，不引入隐藏资料或更强检验器。

## 4. 执行时点与实际闭环

修正旧计划“两次检查”的说法：固定四次完整计划检查，B/C完全相同，无模型调用增加。

T1：BUILD后，用初始化条件C0检查W0，报告给三名复核者。

T2：收齐反馈并应用owner合法修订得到C1后，用C1重检W0，报告给FINAL编辑者。这样编辑者能看到条件修订的实际后果，而非仅听“条件改了”。

T3/T4：FINAL后，分别用同一C1检查W0和W1。B仅记录并提交编辑者所选版本；C按第5节处理。W0的重检可复用缓存，但预算按四次上限报告。程序不枚举搜索正确计划，不提供oracle条件或参考答案。

FINAL阶段不再偷偷修改条件，条件冻结于C1，避免模型通过临时撤条件逃避最终检查。若FINAL发现仍有条件歧义，可说明争议并按例外提交；留待后续预算，不增加一轮API。

## 5. C的版本采用规则

比较必须使用同一C1，不能拿W0/C0与W1/C1直接比较。

V(W,C1)为违反条件ID集合；unknown另列，不能因条件不可执行而获得“检查通过”。

- W1合法、没有新增unknown且V(W1,C1)是V(W0,C1)的子集：采用W1；等集合可采用。称为与当前编码条件相容/改善，不称语义正确。
- W1新增违反、出现新unknown或不是合法排列：默认保留合法W0，保存W1为争议版本，记录被拦截原因。W0本身可能错误，保留不代表验证成功。
- 编辑者可以在同一次FINAL显式选择排列合法的带争议W1，列明对应条件ID和当前来源/适用性争议，宿主仍执行并返回remaining_conflicts，不将其标为通过。例外不能放行重复/遗漏作业的非法排列。这允许合法但不单调的修订，不要求模型永远服从可能错误的条件。
- W0和W1都不合法：保留模型原始输出，结果标invalid_plan，无宿主暗中生成第三个计划。

显式例外仅是可审计决策，不证明理由正确。过多例外、无效理由、或模型动辄绕过，都作为机制失效观察。C如果只是靠强制字段填满而未改善实际修改，应判无机制收益。

误译条件可能拦住正确W1，这是真实风险。离线评分需要同时记录W1本身和最终采用版本的真实质量，判断版本规则是否救回错误修订，还是拒绝了正确修订。首轮不得隐藏raw_W1仅报告被选择后的结果。

不对所有成员解释施加“永远禁止违反”的硬门槛；没有可靠条件准入算法。版本规则是可撤销的保守默认策略，是否有净收益必须由对照验证。

## 6. 输出接口和故障处理

INIT/REVIEW/FINAL的完整JSON schema在实现阶段由上面的对象生成；自由文字无任意字符硬上限，总输出token上限控制预算。FINAL采用reason先、order最后，另可指定retained_work和带争议条件ID；不要求模型自报“所有检查通过”。

解释与order不一致时，以order作任务答案；理由保留用于过程审查。格式错误、响应截断、传输失败及usage未知单列，首个技术错误停止整批，不自动重试或续跑。语义无效条件和错误计划要评分、不能伪装成格式错误删去。

没有API调用来修格式。新增错误不能事后改变标准；失败批次的可用结果和未完成名单全部输出。

## 7. 评分及解释边界

主指标：最终实际采用计划满足离线全部真实要求。运行器不能读oracle_conditions.json和offline/reference.json；评分程序在批次后独立读取并校验hash。

同时保留：raw_W0、raw_W1、实际采用版本、真实违反列表、模型条件违反列表、每次条件修订、例外提交、条件提取遗漏/误译、技术状态、每调用输入输出token。

关键机制观察：

1. W0真实错误是否被成员定位、W1是否真正修好；错误定位与修好分别记录。
2. W0正确部分是否在W1/采用版本中被破坏；是否由版本规则防住。
3. 新条件或修订是否让当前计划真实改善；仅引用/回应不得计有效利用。
4. 最终满足某规则只是结果一致；若无明确贡献—反馈—修改链条，不宣称已证明因果知识利用。撤贡献消融留在主结果出现之后。

人工注入错误贡献不是主试验；自然误译如实保留并审查。所有事后语义注释标为助手复核，不能称独立人工金标。

## 8. 运行次序与预算

阶段0：本地模拟。覆盖下方验收场景，不发模型请求。

阶段1a：calibration-01固定一个episode，三组共享初始化3次、各5次，总18次；只作真实组包、解析、自动条件执行及版本选择的流程验证。该轮无论输赢都保留；不得作为效果结论。

阶段1b：流程无阻塞后，再运行原定剩余开发episodes：calibration-01的第2次、calibration-03的第1/2次，共54次。1a+1b共72次；这不是新增到72次之外。编辑者按episode稳定轮换，组别运行顺序平衡。各请求token cap在实现后测载荷再冻结，不能现在宣称总token预算已就绪。

阶段2：方法和分析先冻结，再决定是否运行12道留出题。可能的两重复三组总432次只作预算估算，未授权、未准备、不是自动触发。留出集不因开发输赢选题或改规则；一旦用来指导修改则降为开发。

如果三组开发都正确，保留结果，不追求造出A失败；判断需要更贴近目标的任务族。C<B时分解条件提取、错误默认拦截、编辑者实际应用问题；不因单个失败堆新角色/步骤。B>A但C不优，归因于工具，停止协调优势宣传。72次开发也不足以声称稳定超过基线。

## 9. 本地验收用例

以下是待实现的验收，不是已经通过的测试：

| 场景 | 必须观察到的行为 |
|---|---|
| A1请求包 | 不含A2/A3原件，仅合法共享摘录/贡献 |
| 同一输入比较B/C | 原始执行报告相同，DSL及执行次数上限相同 |
| 条件修订 | 条件快照变更后重检W0，旧报告不能作为新版本依据 |
| 新稿新增违反 | C默认保留旧稿，原始新稿仍保存；B由编辑者决定 |
| 新稿消除违反且不添新错 | C采用新稿，记录实际违反集合变化 |
| 错误条件阻拦真实正确新稿 | 标记误拦截，允许显式争议路径；不隐藏损害 |
| 单纯“我接受建议” | 不改变任何执行状态，不算修复 |
| 错误/不可执行条件 | 不执行任意代码，不读离线规则补全，unknown可见 |
| 长解释但合法JSON | 无任意字符上限导致整批停止 |
| 中途技术失败 | 不重试，导出已完成/未完成所有组别，未完成不计错 |

## 10. 实现边界

保留既有实验，新增独立运行器。建议分成order_protocol.py（权限组包、贡献/条件快照、宿主版本选择）、prepare_order_collaboration.py（冻结组别/预算/请求规则）、run_order_collaboration.py（有界API与日志）、score_order_collaboration.py（离线真实规则和过程导出）。

现local_conditions.py的候选属性比较不能直接冒充调度DSL；order_constraints.py可复用执行后端，但要增加未知条件/权限/引用/版本处理。旧order_feedback_pilot.py是集中复核，不能改名冒充新多Agent运行器。

只有验收场景实现并通过、阶段1a的实际schema和预算冻结之后，才能说准备好启动18次流程试验。目前设计完备度已提高，实现准备尚未完成。
