# 局部条件机制：首轮本地试验

日期：2026-10-24。性质：程序机制验证，不是模型能力实验，不是准确率结果。

实现：`src/coreta/workboard/local_conditions.py`。原型独立于现有工作流；没有改变旧实验，也没有调用外部模型。

## 已执行结果

`PYTHONPATH=src .venv/Scripts/python.exe -m unittest discover -s tests -p test_local_conditions.py -v`

5项测试通过：

1. 明确的年龄要求能够阻止违反条件的候选作为普通通过结果提交；满足该条件的另一候选可以提交。
2. 错误成员条件产生可见冲突；解释冲突不会把冲突抹掉。撤回错误条件后，候选重新与现有条件一致，历史保存撤回前后影响。
3. 属性未知和预算耗尽返回未解决状态，不冒充检查通过。
4. 条件修订后，旧版本检查不能用于提交。
5. 不存在的引用及缺少依据记录的修订被拒绝。

条件引用存在不代表条件正确。测试刻意放入引用真实但含义不支持的错误条件，确认程序不能发现这一语义错误。

## 本地试验说明的实际问题

明确任务要求可以由控制器执行；成员解释只要求说明冲突，仍允许带未解决状态提交。因此，这一原型消除了“冲突无声消失”，但没有证明模型会做出正确修复。解释冲突仍然可能变成另一种形式的口头回应。下一阶段必须测实际候选变化，不能把填写responses当作成功。

task_requirement的身份目前由宿主实验代码设定，不能开放给模型自行设置；引用查验不提供成员权限隔离。任务要求的自动提取、成员私有来源权限、模型输出schema、token预算及网关尚未接入。因此目前只能进行本地机制试验，不能宣称端到端架构已准备完毕。

## 下一阶段冻结建议

先做同一组信息下的配对诊断，不用005开放权重任务来证明条件执行价值。004仅作旧题回归，不计新任务泛化结果。

新增6个小型有限候选案例，覆盖：两个正确条件必须组合；正确条件需改变错误初答；混合正确/错误条件；错误但一致条件排除正确候选；缺少属性；证据不足以唯一确定候选。案例和离线参考解释在运行前固定，模型看不到参考答案。

对照：A普通文本检查；B相同资料、初稿、成员贡献和相同条件内容，加确定执行结果及一次定向修订。每案例两次独立重复，两个条件均一次修订调用，共24次请求上限。首轮故意固定贡献，隔离“执行反馈是否改变应用”；这是机制诊断，不能证明自动提取或完整多Agent收益。无外部模型授权、未冻结输入和输出格式前不启动。

先比较最终任务正确性、有效条件实际遵守、错误条件损害、初始正确答案被改坏、未解决冲突及成本。程序检查通过只是辅助指标。盲审最终内容与离线参考，不能只统计模型自报接受/拒绝。

若B不能改善正确条件应用，先停止扩展；若提高应用却增加错误条件损害，则核心问题转为条件准入与回查，不能以协议完整宣称成功。
