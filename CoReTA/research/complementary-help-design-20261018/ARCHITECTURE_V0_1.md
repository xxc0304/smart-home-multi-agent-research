# 按需互补协作：可执行架构草案 v0.1

状态：历史草稿。当前修订设计见 [ARCHITECTURE_V0_2.md](ARCHITECTURE_V0_2.md)，明确语义决策、修改规则、对照与预算边界；本文件保留用于追溯。

日期：2026-10-18。阶段：设计，不是已经验证的新方法。本轮不执行付费实验。目的保持为可靠利用互补专长、提升团队完整任务表现；帮助机会成本是设计约束，不将主线改为单独的“帮助有害”benchmark。

## 1. 截图现象在多Agent中有无先例

**有，但应区分直接的帮助决策研究与一般协调负收益。**

### 传统MAS的直接先例

Jernej Polajnar、Narek Nalbandyan、Omid Alemi、Desanka Polajnar (2012), *An Interaction Protocol for Mutual Assistance in Agent Teamwork*, CISIS, DOI10.1109/CISIS.2012.169。

[作者上传全文](https://www.researchgate.net/publication/228703020_An_Interaction_Protocol_for_Mutual_Assistance_in_Agent_Teamwork)。本轮读取摘要、引言、团队模型和协议相关文本；不是代码复现。MAP让求助者与帮助者基于各自计划对团队的影响作近似评估，通过类似合同网的双边交互决定是否帮助；比较不同帮助决策协议、无帮助情形，并考察通信/计算成本等。其计划代价、动作能力比开放式LLM推理更结构化。它证明“帮助须考虑团队净收益”不是LLM时代才出现的问题，不能将此概念当新颖贡献；也不能从其仿真效果推断LLM通用任务效果。

### LLM中的相关证据

[Kim et al., Towards a Science of Scaling Agent Systems, v3](https://arxiv.org/html/2512.08296v3)分析多架构、任务与预算下的协调成本和能力关系。支持在固定预算下检查协作开销，但不是对“特定帮助者因帮别人而放弃自己工作”作同一个因果实验。本轮不引用初版/最新版容易混淆的配置数或统一阈值。

[Yadav, Black & Sourbut, More Capable, Less Cooperative? When LLMs Fail at Zero-Cost Collaboration, ICML2026](https://proceedings.mlr.press/v306/yadav26a.html)研究帮助几乎无个人成本且团队有益时，LLM仍可能不共享有用信息；采用沟通一侧自动化的分解来区分能力与合作失败。它与截图是不同条件，提醒不能把所有不合作都解释为帮助成本，更不能据此推断应无限鼓励帮助。此项本轮核验正式摘要，未读全套方法。

结论：已有直接传统MAS工作和LLM相关机制研究；未完成所有LLM论文中“同一帮助行为、受助收益、帮助者本职损失”三项的穷尽查新，不作“没人研究过”声明。

还需区分任务结构：多个并行子任务中，帮助者确实可能耽误自己的工作；共同解一道题时，某成员未必有独立本职任务，机会成本主要是这笔推理预算原本可用于别的求解/检查动作。当前架构首先验证后一种，不能直接把一般token开销称为已复现Barnes式本职损失。

## 2. 具体架构

暂称按需互补协作，不取带新颖暗示的缩写。三个执行Agent、一个程序调度器、共享工作记录、可用的检查工具。调度器不是默认新增更强模型；语义判断由已计预算的成员输出或公开检查信号提供。

三个Agent可使用不同模型，具体名单需在后续协议按可用API和成本确定；不是三个专家persona就视为真实互补。角色不永久绑定：同一成员可以提出方案、补构造、查反例、核计算。默认主解题者事前固定或用独立开发集选择，测试中不使用谁答对的标签。

共享状态最小包含：任务、独立初稿、当前候选方案、未解决步骤、帮助请求、带来源的贡献、检查结果、版本记录、剩余预算。第一版不要求复杂知识图谱或自动建立形式证明DAG。

### 阶段A：独立初稿和当前可用支点

三个成员各一次独立初答，输出候选答案、关键推理/产物、尚未解决或可疑的一步及检查线索。无需强迫每个成员都声称不知道，也允许报告无可见障碍。保留原始输出供事后诊断，不能因初稿结论不合预期而重采样。

主解题者基于初稿推进一个当前候选方案。在其正常推理回复中报告仍未解决的具体步骤；不要为每个元决策都新增一轮全员长讨论。

### 阶段B：产生具体求助

触发来源：执行者具体报告；测试/前置输入/结果冲突等可见事件；同伴对中间产物提出局部质疑。另保留有限独立检查，以避免“自信但错误者不求助”的盲区。不是每个低置信都必然启动全体协作。

请求最小格式：

```json
{
  "target_step": "需要补全或检查的步骤",
  "current_attempt": "实际尝试或产物引用",
  "observed_issue": "失败结果、缺失条件或未解决问题",
  "requested_deliverable": "一项补充，如构造、反例、引理或补丁",
  "check_plan": "怎样检查该交付是否推进了目标",
  "context_refs": ["需要的上下文引用"],
  "budget_limit": "本项帮助允许的调用和输出预算"
}
```

这只是数据接口，不宣称字段本身是创新。调度器检查引用、预算和重复请求等结构，不能从结构完整自动推断语义正确。

### 阶段C：选择一项局部帮助

按当前请求和已有独立产物，选择具有相关支点的成员；相关来源、工具访问和开发集能力记录可作线索。信息不足时，最多询问少量候选的短提案/拒答，不每轮广播全员。候选自称擅长不能视为已证明能力。

第一版采用透明的有限选择规则，不写一个不可实现的“选择预期净收益最高者”oracle。记录选择依据，允许“自己继续”“请别人局部帮忙”“交给另一成员重新解题”作为不同动作。前两者无需保证总比第三者好。

### 阶段D：交付、独立检查、应用

帮助者返回一项指定交付、适用条件、依据及可检查方式。例如修正一个计数、给出一个缺失构造或可执行补丁；若整体思路无效，可以提出重解建议，不人为禁止合理接管。

主解题者或另一成员应用交付，优先执行客观局部检查，再继续下游推理。提出与检查不能仅靠同一成员的口头自证。没有客观检查时，独立审查只给支持性证据，状态标为候选/未决而非证明正确。

检查结果分为推进、未推进、出现反证、无法判定。结果控制继续、换人/换方式、撤回或结束；保存旧版本，但不假设旧版本一定比新版本正确。

### 阶段E：有界迭代与最终解答

原型建议至多两个帮助周期，用于控制首轮工程复杂度，不是经验最优结论；后续在开发集固定预算和早停规则。协调、候选短提案、检查、工具和汇总全部计入总预算，不能把“观察是否有进展”当免费操作。

达到预算、反复提出相同未解决问题或无新可用贡献时停止/接管。最后由预先固定的汇总方式生成完整答案，所有基线使用匹配版本。隐藏评分器和测试答案不参与运行时决策。

## 3. 为什么这可能带来专长扩展

希望发生的计算过程是：A提供有用但未完成的方案，B交付A当前缺少的局部结果，A将其用于继续推导，C检查边界或实现。A不必变成B领域的永久专家，B也不必完整重做A全部工作。真正需要检验的是这些非冗余贡献能否节约无效重复并改善完整任务，而不是“帮助者更积极”。

当所有成员都没有相关支点、检查器也不可靠时，协议可能没有收益；若一个强者已能独自高效完成全部步骤，简单单体可以更好。两种情况都应留在完整测试结果中，不能删掉。

## 4. 哪些是已有组件，哪些是待验证的方法设计

已有组件：blackboard共享状态、定向求助、合同网式认领、局部检验、早停。它们是设计资源，不是拒绝组合的理由；但也不能作为首次主张。

本草案希望建立的差异是：以执行中可观察的具体阻塞为单位，选择有边界的补充贡献，再用该贡献是否被正确接入后续任务控制下一轮协作。此组合的完整新颖性尚未完成算法和代码层逐一比较，现阶段不宣布“没人做过”。若实现只是普通blackboard中多放几个字段，独立贡献不足。

## 5. 最小验证与互补归因

主比较：同成员的独立初答+同汇总器、普通讨论/相关强架构、预算匹配最强单体继续推理/采样。不要只比较单次单体或多数票。

机制比较：在总预算尽量匹配下，比较有/无具体请求，有/无交付后应用反馈；对预定位置的真实贡献与同题冗余替换作配对干预。记录下游应用和最终任务变化。异质团队与同一强模型多角色比较，区分成员差异与组织结构。

只有同时改善完整任务，并且内容干预及流程消融支持该机制，才能称存在互补收益。受助步骤变好、有人引用帮助、初始全错后答对，都不能单独承担全部因果归因。

## 6. 当前行动边界

这是回应用户“是否有类似研究、架构是否具体”的设计交付，不是已授权的新付费实验。下一步可把v0.1规则编成无付费状态机、接入已有任务/评分器做本地路径检查，再按具体协议审查采样预算。不能用脚本路径成功冒充真实LLM增益。
