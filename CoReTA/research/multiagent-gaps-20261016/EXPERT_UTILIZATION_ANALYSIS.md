# 方向1深化：把局部专长转化为可靠的团队决策

日期：2026-10-16。状态：问题与方法要求分析，不是新算法定稿或付费实验协议。

## 1. 研究对象

团队成员掌握不同的知识、工具或证据。研究系统怎样让相关专长影响共同决策，同时避免把错误、自信或被操纵的意见放大。专家应是某类子问题上具有较可靠能力或相关证据的成员，不是实验者指定的全知角色；专家身份与当前主张正确性不等价。

这一方向可以研究方法，也可以研究评测，但“团队有时忽视专家”已有直接论文。当前更自然的贡献路径是针对已知问题提出更可靠机制，并用有独立验收的任务检验。

## 2. 已有工作怎样限定空间

| 第一方文献 | 已有内容 | 对本方向的约束 |
|---|---|---|
| [Multi-Agent Teams Hold Experts Back](https://proceedings.mlr.press/v306/pappu26a.html) | 在所测自组织任务中专家已知仍利用不足，共识又有抗对抗意见的收益 | 再次报告专家被忽视，或只要求听专家，均不足 |
| [MAS-ProVe](https://proceedings.mlr.press/v306/venkataramani26a.html) | 过程验证不稳定改善多Agent表现 | 不能假定再加judge自然更可靠 |
| [AgentAuditor / ACPO](https://arxiv.org/html/2602.09341v1) | 在推理分歧处审计证据，学习选择有依据的少数答案 | 证据胜过票数、局部核验、反从众训练均已有先例 |
| [Beyond Majority Voting](https://proceedings.mlr.press/v306/ai26d.html) | 利用异质性与相关信息进行聚合 | 不能只把普通投票换成权重宣称方法创新 |
| [Robust Multi-Agent LLMs under Byzantine Faults](https://dasc-lab.github.io/papers/2026/2026-robust-llms/) | 分散过滤和迭代修正，以抵抗不可靠成员影响 | 正常错误与有意对抗需区分，不能只测攻击有效率 |
| [ECMR](https://arxiv.org/html/2610.17869v1) | 根据证据状态、角色和预算选择质疑、核验、仲裁等操作 | 主动控制讨论流程本身也不是空白；其报告同时指出最可靠配置使用更多token |
| [When Debate Helps](https://arxiv.org/html/2610.04686v1) | 研究互补提案供给与验证感知读出的共同作用 | 团队中有没有好意见与能否利用它，应分开分析 |

这些方法的存在说明竞争对象具体，不能证明问题已普遍解决。本文没有复现它们，也不把预印本报告直接视为已独立验证的事实。

## 3. 哪一层出了问题

一次失败可能有多个机制，以下不是互斥、完备的根因标签。

1. 信息供给：有价值证据未被提供给团队。改变最终聚合不能补上缺失事实。
2. 理解：其他成员没有理解证据的适用范围或前提。
3. 采用：相关信息已被理解，最终决策仍被人数、身份、口头自信或早期结论主导。
4. 落实：结论采纳了正确意见，后续行动却未遵循对应约束。
5. 核验：检查器被同源错误误导，或核验了无关、便宜但无决定价值的部分。
6. 成本：核验本身正确，但其调用代价使整体收益不足。

必须从轨迹和环境证据确定支持哪一层，不用模型事后“承认错误”直接归因，也不能把所有最终失败都计作专家利用失败。

## 4. 具体问题应如何表述

建议围绕一个主问题继续思考：**团队能否根据当前子问题的证据，选择应采纳、应核验和应撤回的意见，让专长真正改善共同决策？**

不要把“谁更强”固定成全局排名。一个代码Agent可能更擅长实现，却误解业务规则；一个检索Agent拿到了正确政策，也可能引用了过时版本。可靠性属于任务、主张、证据和适用前提之间的关系。

但这个表述本身不是独立贡献证明。它需要一个确实不同且有效的机制，或新的、有决策价值的实证发现。不能把证据、角色、预算、控制器顺次拼接就宣布新算法。

## 5. 方法草图与必须回答的问题

可以从争议中的关键主张出发：明确不同意见的分歧，确定缺少什么可区分证据，向适当成员或工具请求检查，再根据结果更新共同决定；证据不足时允许保留不确定，而非强制达成一致。

这是一份可执行设计草图，也是已有方法覆盖很多的区域。下一步真正需要提出的是：

- 新机制如何发现关键检查对象，现有AgentAuditor或ECMR为何在相同信息下不足？
- 它怎样利用外部观测而不把另一个LLM意见误当独立证据？
- 改善来自更好的判断，还是仅增加了模型调用与工具访问？
- 证据质量不够或检查不可行时，怎样避免虚假确定性？

若答案只有“写一个更好的审核prompt”，应降低贡献预期；若实际优势来自多一种工具，所有可比较系统也应获准使用该工具。

## 6. 任务与数据怎样构造才有辨别力

优先选择能够独立验收的代码、数据分析或文档约束任务。例：一位成员指出报告使用了错误分母，另一位认为应按总人数计算；系统可以检查原始数据、定义和计算，而不是凭谁说得更像专家决断。

专长可来自真实能力差异、专业工具或相关资料访问。角色分工应有任务依据。不能仅在提示中宣布A是专家，再把A所有答案设为正确；也不能只抽取我们方法擅长的“多数错误、少数正确”样本当主分布。

应区分自然模型失败与受控压力条件。受控修改某条意见可帮助解释机制，但不能用于估计自然失败率。自然样本必须包含无需争议解决也能完成的任务。

决策系统不接触测试答案。公开可调用检查与隐藏最终验收分开；不能用最终金标准作为在线专家识别信号。若某工具直接给出全答案，需要一个使用同工具的强单Agent基线，否则评到的可能只是工具价值。

## 7. 实验应怎样逐步做

### A. 先检查意见供给与最终选择

保存真实模型生成的初始提案，查看是否存在有价值且可核验的分歧。以相同初始提案比较聚合，可隔离初步判断能力；不能保证闭环主动方法的整体效果。

### B. 再检查主动取证的闭环价值

各策略从共同初始状态出发，之后按照各自观察重新决策。若新机制改变了对话或工具结果，后续模型响应必须重新采样，不能把旧响应串回去当真实反事实。

### C. 最后检验迁移和代价

在未用于调参的任务与团队组合中测试。跨任务迁移需避免只改名称，跨模型不是同时更换整个系统后再声称纯架构效应。

强对照包括同预算单Agent、预先选定的最强成员、投票、普通judge、AgentAuditor和适配的可信聚合/证据控制方法。按单题答案事后选出的最佳成员只能作为乐观参考，不冒充实际可用策略。预算包括提案、审计、核验、重试等实际开销。

## 8. 看什么结果

主要看最终任务正确性与成本。诊断分别看正确关键证据保留、错误意见采用和不必要核验；有可判定条件的子集才报告相应诊断，不能强行给所有轨迹贴原因标签。

| 结果 | 解释 |
|---|---|
| 正确少数采纳上升，但错误少数采纳也上升 | 可能仅改变偏好，不是可靠性提升 |
| 比投票好，但不优于已有审计方法 | 新机制优势尚未建立 |
| 只在人工指定专家永远正确时好 | 可能是读身份标签，不是利用专长 |
| 同预算下提升最终结果，正常任务和错误意见条件未明显受损，并能迁移 | 支持有效机制进展，但仍需确认与近邻的区别 |
| 多用检查工具后变好，单Agent同工具同预算也同样变好 | 主要证据支持工具收益，而非团队独有收益 |
| 所有成员都缺少决定性事实，且没有获得新证据的渠道 | 不能要求信任策略凭空恢复答案 |

不要求证明多Agent在所有任务上胜过单Agent。一个更可靠的协作方法可以只在需要互补专长的任务分布上有价值，但这种任务分布应独立说明，不能事后挑选获胜案例。

## 9. 值得什么投入

问题重要性与ACL语言/推理关联明确；具体方法目前仍未定，新颖性尚未确认。近期值得做机制方案与强基线对照，不值得立刻启动大批API网格。

如果希望做方法论文，下一项交付应是对AgentAuditor、ECMR及可信聚合方法的机制差别说明，并提出一个可被否定的优势假设。如果希望做benchmark，必须另外证明现有任务缺少重要测量用途，而非仅把上述失败改写成新题目。

本轮只做检索与分析，没有新增实验API调用、没有训练任务，也没有将本草图注册为新主线或实验协议。
