# 最近检索与架构修改方向审核

2026-10-19。审核对象：机制综述、三个来源笔记、修订设计，与 v0.3 PROMPTS / protocol.py 的实际阶段比较。本轮重新查看 AgentVerse、DMAD、MoA 的相关官方文件；没有复现论文、运行测试或追加模型实验。

## 结论

检索足以支持“参考已有架构补足工作流”；修改方向部分合理，但上一版还不能称为可实现定稿。核心不足是：**纠错与记录设计多，主动构造和局部连接设计少；对现有流程重复描述较多，真正改变行为的约束未明确。**

当前优先目标仍是让协作实际解决单独没解决的问题。新颖性与精细贡献归因不是本轮设计的前置门槛。

## 一、来源审核

### 可以保留的结论

- AgentVerse 官方 solver-first 确实安排 solver→reviewers→有异议则修订。它支持明确的意见消费流程；不支持“这样就能保证发现缺口或修对”。[源码](https://raw.githubusercontent.com/OpenBMB/AgentVerse/main/agentverse/environments/tasksolving_env/rules/decision_maker/vertical_solver_first.py)
- DMAD 官方 reasoning.py 有子问题与场景图的分阶段生成，支持不同操作/表示的实现先例；不直接支持我们提出的 A0/A1/A2 固定划分，更不证明该划分适合数学和代码。[源码](https://raw.githubusercontent.com/MraDonkey/DMAD/main/reasoning.py)
- MoA 的演示聚合阶段可生成新答案，支持综合内容超出整解选择；演示中没有独立执行核验。[源码](https://raw.githubusercontent.com/togethercomputer/MoA/main/moa.py)
- MetaGPT/ChatDev 的交付依赖可借鉴；其软件任务和执行条件，与我们的短数学/函数任务不同。已有笔记已注明版本区别，不能把当前 main 当作历史实验代码。

### 需收窄的说法

1. **“17 项工作”是覆盖范围，不是 17 项同深度核查。**有的读方法及代码，有的只读相关正文；DMAD 正文受阻、TMAS 只核 README。综述台账写了这些边界，但对外概括时也应保留“部分官方实现”的限定。
2. “VERIFIED”只覆盖身份和所读机制事实，不表示效果已复现、全部结论可信或可直接迁移。
3. 不同操作、交付依赖、反馈修订、执行工具是不同机制；不能把几篇论文的正面结果拼接成“这组组件共同有效”的证据。
4. 论文给出可借鉴的设计，不等于已定位 E1 无提升的根因。E1 只说明现有表现与若干具体失效，不能单凭结果相同证明缺少角色分工就是原因。

不必继续广撒网增加篇数。下一步只对最终采用的流程补读准确提示、输入输出和版本，再冻结我们自己的适配。

## 二、修改方向中的主要问题

### [高] 1. 主动联合构造仍然缺位

原稿以异议、反例和未完成项为触发中心。但大家都没有发现错误时，它仍可能整体认可后停止；大家都知道卡住却没有新材料时，处置表也不会补出解。

**改正：**加入明确的建设性任务：从已有材料中识别当前方案尚未使用、可能补足关键依赖的局部结果，尝试完成一项具体计算、引理、构造、算法子问题或连接推导。不能只问“哪里错”；也不要求凭空找一个不同意见。三个初稿答案相同仍可做这种检查。

### [高] 2. 与 v0.3 的真实差异未写清

现有 `collaborate()` 已先 A2 review，再 A0 update；update 已允许修订、补完、替换及求助。前一版“完成整合后才停止”的文字，可能完全由现有一次 update 满足，无法改变 E1 行为。

**改正：**新增行为必须定义为可观察交付：初审检查记录；整合时显式完成局部连接或说明无法连接；对关键未解项选择下一工作；停止类型和理由由状态/预算约束。字段齐全本身不是能力提升。若仍允许同一自评直接跳过工作，新版就没有解决原来的调度疑问。

### [高] 3. “有未处理异议仍可结束”与改进目标冲突

预算结束当然允许失败；但有预算、有具体可做检查、同时未处理的关键问题却以正常完成结束，会重现原来的路径。反过来，强制等到所有批评被同意也会被错误批评拖住。

**改正：**区分完成、预算/时间耗尽、暂时无可行动路径。对关键问题允许有依据地反驳、尝试修复、请求帮助或请求核查；暂置不等于正常完成。程序只保证问题被处置和动作合法，不裁定语义真伪。模型仍可能把问题错判为无关，此风险保留并观察。

### [高] 4. 局部连接标准过于抽象

“前提—结果—用途”是合理原则，但还缺接入操作。两份局部推导使用不同假设、变量、单位或输入域时，直接拼接会产生错误。

**改正：**在整合阶段具体核对：两份材料的假设是否同时成立；符号/变量/输入域能否对齐；上游结论是否满足下游所需前提；缺失的桥接推导是否已完成。代码则核对返回值、数据结构、不变量、边界和子步骤依赖。连接失败时，把缺少的桥接本身转成下一工作目标。可以先用现有步骤与引用表达，无须先造大型图结构。

### [中] 5. 固定三种角色只是候选

直接求解/分解/反例的区别有来源启发，但 A0 负责主方案、A2 既独立求解又持续审查，可能形成偏向 A0 和消耗 A2 的安排；A1“另一方法”也可能只换措辞。

**改正：**把它们称为初始操作默认值；任务推进中三者均可构造、检查或换方法。不强迫 A1 与正确方法不同，不把 A2 固定为否定者。是否保留这些默认值，需看交付是否真的不同且有用。

### [中] 6. 核验与日志不能替代求解

逐条处置、支持状态、程序 diff 能修复可追踪性，不能使推理变正确；同模型 reviewer 可能共享错误。追加大量字段还可能挤占实际推导空间。

**改正：**保留少量必要信息，优先把输出预算给具体局部求解和连接。程序 diff 作为自动日志，避免模型重复填写。暂不实现自动记忆裁剪：错误筛选可能删掉少数正确意见，现有日志应保留冲突内容与状态。

### [中] 7. 无在线工具是当前版本条件，不是长期结论

论文中的代码执行是重要机制。保持无工具有利于连续比较，但不能因此断言手算就足以核验代码，也不能断言加入执行已被排除。

**改正：**此版先明确文字推理条件；对代码任务单独评估公开自生成测试执行的价值。若引入，使用 Docker 隔离并给对照同等能力；隐藏测试仍只在离线评分。当前不擅自改变条件。

### [中] 8. 实验叙述应服从当前开发阶段

原稿过早铺开多项消融与归因，且“共享初稿的继续独立推理”有歧义：单个成员若看了其他初稿，就不再是独立推理。

**改正：**先观察新流程是否产生有效贡献、接入方案并改善求解；先安排小规模开发验证。随后再展开系统消融。独立继续推理条件各自只看自己的轨迹；独立综合条件才看三份初稿。先记录能力与过程，暂不把等成本优势设为通过门槛。

## 三、修订优先级

| 保留 | 先补实 | 暂缓 |
|---|---|---|
| 三成员、共享方案、定向工作、检查整合 | 建设性局部求解与桥接操作 | RL、额外 Agent、复杂记忆框架 |
| 独立完整候选及不同操作默认值 | 问题处置如何实际约束下一动作 | 大规模正式实验与全套消融 |
| 具体核对、实际变更记录 | 明确完成/受限停止及预算 | 首创判断与精细因果归因作为前置要求 |

## 四、下一步的具体交付

完成一版阶段表和状态转移表，至少回答：

1. 初稿之后怎样主动找到可用局部材料，而非只查错？
2. 谁负责哪一个新局部工作，完成后如何连接？
3. 检查发现冲突、没有帮助、无人发现问题时，各自怎么走？
4. 有预算且有关键未解项时，哪些动作合法？
5. 每一条新规则相对于现有 update 到底增加了什么实际行为？

之后再改提示与代码。审核判定：**保留总体骨架，修订上述缺口后再定稿；当前不是需要推倒重来的架构，也还不是可直接声称设计完备的版本。**
