# CoReTA 修订版：阶段、交付与状态转移规格

状态：本轮具体设计交付，供下一步实现；不是已启用的运行版本。2026-10-19。

依据：[机制调查](../research/COMPLEMENTARITY_MECHANISM_REVIEW_20261019.md)、[修改方向审核](../research/RETRIEVAL_AND_REVISION_AUDIT_20261019.md)。本稿取代旧修订稿中未明确的调度与停止建议；原 v0.3、配置和 E1 原始结果保留。

## 1. 设计决定

保留三实例、现有 DeepSeek Flash 接入、无训练、无在线工具。A0 维护共同方案；A1/A2 可以构造、检查和换方法。独立阶段采用不同操作默认值，后续按问题调度，不假定角色拥有不同知识。

**新增一个实际执行的建设性阶段**：A0 先提出综合方案，A1 再尝试补出一个有用的局部结果或桥接推导，A2 检查新增内容与连接，最后 A0 应用。它不以发现错误、答案不同或 A0 主动求助为启动条件；无可用贡献时允许诚实报告。

这一决定借鉴 DMAD 的不同操作、MetaGPT 的交付依赖、AgentVerse/ChatDev 的意见消费流程，以及 MoA 的综合生成。具体三成员顺序、预算及契约是我们的适配假设。固定一次建设性尝试的收益尚未验证，但它使“主动互补”成为真实工作，而非一句原则。

### 对现有流程的明确差异

| v0.3 | 本稿 |
|---|---|
| 三份同模板初稿 | 三份完整初稿，分别强调构造、分解、约束核对 |
| A2 只看 A0 与自己的初稿做初审 | A0 先综合，A1 实际尝试建设性补充，A2 检查方案及新增连接 |
| A0 首次 update 可直接 FINISH | 固定建设性尝试、检查、应用完成后，才允许正常完成 |
| application 主要绑定整次事件 | 关键问题逐条处置，新增局部结果定位到当前方案 |
| 请求完全由主解题者自判触发 | 建设阶段可以提出缺失桥接，检查阶段可产生问题，程序约束其后续状态 |
| 总体 FINISH | 明确完成、预算耗尽、无法推进、运行故障 |

不宣称更严的格式能解决语义错误；真正新增的是 A1 的局部工作、A2 对该工作及其接入的检查，以及受问题状态约束的后续动作。

## 2. 阶段表

所有调用使用独立上下文。固定材料按下表显式提供；不依赖成员记住此前对话。表中“检查”均为文字推导/手算，不能报告真实执行结果。

| 阶段 | 执行者及输入 | 必须完成的工作 | 交付 | 后继 |
|---|---|---|---|---|
| D0/D1/D2 独立求解 | 各成员：公开任务 | 分别独立给出尽可能完整解；保留可检查中间结果，不编造困难 | Candidate：artifact、steps、open_issues | 三份就绪→S |
| S 综合提案 | A0：任务、三初稿 | 比较可用内容，构造当前完整方案；检查前提是否相容，指出仍缺的连接 | Candidate + 关键未完成项；尚不选择停止 | B |
| B 建设性补充 | A1：任务、三初稿、S 当前方案 | 优先补关键未完成项；没有报告缺口时，独立重建一个关键依赖，或利用未被采用的材料补强/替代；完成具体局部工作并指出接入位置 | provided/cannot_help；局部结果、成立条件、依据、接入建议、未完成桥接 | C |
| C 检查内容及连接 | A2：任务、三初稿、当前方案、B 交付 | 实际核对新增命题、条件与桥接；没有 B 贡献时核对当前方案的关键依赖；可给修正或新的建设性结果 | Review：目标、实际核对过程、结论/范围；问题列表 | U |
| U 应用与调度 | A0：任务、初稿、当前方案、B/C、问题状态及相关历史 | 采用、修正或拒绝具体内容；完成桥接并返回完整更新方案；逐条处理问题；选择下一工作或停止 | Candidate + 应用/问题处置 + Decision | 合法停止或工作轮 |
| W 定向工作 | 选定 A1/A2；SELF 时为 A0 新上下文 | 按具体目标完成局部构造、修复或替代，不只重复原答案 | Contribution，允许 cannot_help | CHECK→U |
| CHECK 工作核对 | 非贡献成员；见第5节 | 核对实际产物及计划接入位置，保留不确定性 | Review | U |
| FINAL 输出 | A0 新上下文：任务、完整当前方案、初稿、相关交付与未完成项 | 生成最佳最终答案；可补推导，不抹掉之前停止状态 | 最终 artifact、实际来源引用 | 归档 |

独立操作默认值：A0 直接构造；A1 分解或换表示；A2 从约束、边界和可失败位置求解。三者均可给完整解。无法产生另一方法时如实说明，不为差异牺牲正确方法。初稿差异与协作效果分别观察。

## 3. 建设性补充的具体规则

B 阶段依次尝试：

1. 完成当前方案明确未解的关键子问题。
2. 检查三份材料中是否有未接入、能补足该依赖的局部结果。
3. 若没有显式缺口，选一个决定答案的关键依赖，采用具体计算、另一推导或构造重新建立它，尝试发现遗漏条件或给出改进。
4. 若仍无有用结果，报告 cannot_help，并说明尝试的对象、过程和结论。不能仅写“我同意”，不能强行修改正确答案。

交付区分：补出新局部结果、完成桥接、修复错误、已有内容重新核对、整体替代、无法帮助。前四种不自动意味着最终能力提升；整体替代仍允许，不强迫局部拼接。

### 数学接入

明确上游结果、成立条件、下游要证明的命题及连接推导；检查变量定义、量词、单位、范围是否一致。结果 A 与结果 B 都正确，但 B 要求的条件没有由 A 建立时，必须留下桥接问题，不能声称已接通。

### 代码接入

明确局部修改或算法结果、所需输入/状态、返回值或不变量，以及修改位置。检查空输入、索引范围、可变状态、返回类型和子步骤依赖。只给“考虑边界情况”不是完成贡献；给出具体输入和逐步预期才构成可核对材料。

这些是产物要求，不要求透露不可检查的内部思维；输出只需足以审查的推导、计算或实现依据。

## 4. 问题状态及程序权限

问题是“可能阻碍完成的具体工作”，来源可以是初稿、S/B/C 或后续工作。问题不局限于错误：也可为缺失构造、未证依赖、条件冲突。

程序分配稳定 ID，例如 `i0001`；事件内新问题使用本地序号，成功提交后映射到正式 ID。绑定候选版本及相关步骤引用，避免模型猜测事件 ID。

| 状态 | 意义 | 可用后继 |
|---|---|---|
| open | 需要处理；未开始或前次失败 | in_progress、addressed、dismissed |
| in_progress | 某个已发出的工作正在处理 | open、addressed |
| addressed | 给出了修复/完成结果、依据及接入位置 | 新反证可 reopen 为 open |
| dismissed | 以具体依据说明异议不成立或与解无关 | 新证据可 reopen 为 open |

`addressed/dismissed` 是模型有依据的处置，不是程序认证正确。`cannot_help`、review unresolved 或仅有“接受建议”不能机械关闭问题；要么继续处理，要么以受限状态结束。反馈相反时允许 A0 反驳 reviewer，但必须定位依据。

每项问题有 `blocking`：若不处理可能改变答案/代码正确性则为 true。其语义由模型判断；程序只检查该判断及理由存在。从 blocking 改为非 blocking 要记录理由。即使三成员一致也不自动关闭问题。

程序能检查：引用可见且版本匹配、必填交付、问题状态转移、处置有非空依据、动作/预算合法、实际文本差异。不能检查：结论正确、桥接充分、问题优先级真实、自然语言确有意义。这些依然可能失败。

## 5. 动作与接收者

U 输出下面一个动作；每个继续动作绑定一个首要工作目标，可以关联多个相关问题。

| 动作 | 适用条件及交付 | 后继 |
|---|---|---|
| REQUEST_HELP | 局部结果或桥接缺失；说明需要什么、用途和核对办法 | W→CHECK→U |
| REQUEST_ALTERNATIVE | 当前路径无进展或有条件冲突；说明需打破的依赖 | W→CHECK→U |
| CONTINUE_SELF | A0 有具体可执行的新步骤 | A0 的独立 W→A2 CHECK→U |
| REQUEST_CHECK | 已有结果需核对；目标及方法具体 | peer CHECK→U |
| FINISH_COMPLETE | 固定阶段完成，无 open/in_progress 的 blocking 问题；给出关键依赖完成依据 | FINAL |
| FINISH_STALLED | 固定阶段完成；对未解目标已有实际尝试且没有新的具体可执行办法；列出失败尝试和未解项 | FINAL，状态 stalled |

外部调度器在无工作预算时输出 BUDGET_EXHAUSTED，不要求模型假装 complete；超时、接口或协议故障分别归档运行状态。

接收者依据可见产物与所需操作选择；HELP 由 A1 提供时 A2 检查，反之亦然。SELF 由 A2 检查；REQUEST_CHECK 可选 A1/A2。检查者不是独立真值源，仅避免同一次贡献完全自评。

无变化的同一请求不得原样重复：后续请求至少给出新目标、新材料、新方法或换接收者的具体理由。程序可拒绝完全相同的请求指纹；“新方法确实有意义”仍属语义判断。

## 6. 状态转移表与停止

| 当前状态 | 条件/事件 | 下一状态 | 写回 |
|---|---|---|---|
| INIT | 三独立候选有效 | SYNTHESIZE | 初稿不可变，A0 初稿可作失败回退 |
| SYNTHESIZE | 综合提案有效 | BUILD | 提交新当前版本及问题 |
| BUILD | provided 或 cannot_help | CHECK | 保存产物或真实失败尝试 |
| CHECK | 有效 review | APPLY | 保存核对记录及问题；未核实内容不变成事实 |
| APPLY | U 更新及处置有效 | DECIDE | 原子提交当前方案、问题状态与自动差异 |
| DECIDE | 关键问题开放且还有具体工作 | WORK / CHECK | 发出目标和接收者；不能 COMPLETE |
| DECIDE | 完成条件满足 | FINAL | complete，仅代表协议完成 |
| DECIDE | 无工作轮剩余 | FINAL | budget_exhausted，保留未解项 |
| DECIDE | STALLED 条件满足 | FINAL | stalled，保留失败尝试及未解项 |
| WORK | provided | CHECK | 贡献绑定目标及候选版本 |
| WORK | cannot_help | APPLY | 无需对空贡献再审；保留目标为 open |
| 任一状态 | 不可修复运行错误 | DEGRADED | 最后有效候选、错误和未完成阶段 |

S 阶段不是最终方案完成声明；B/C/U 均不能跳过。U 若产出新的关键推导，必须给可核对依据及标注“本次新增、未另经同行检查”；不能伪称 C 已审过。有具体疑点时走下一轮 CHECK，预算不足则保留范围限制。

固定尝试已完成却三者都没有识别出问题时，允许 complete；程序不强制发明缺口。此时可能仍错，这是语义能力边界，不以无限对话解决。

## 7. 预算与失败恢复

初始设计采用：3 个独立初稿 + S/B/C/U 各1次 + 最多2个工作轮 + FINAL 1次。完整工作轮最多 W/CHECK/U 三次，因此正常调用上限 **14**。REQUEST_CHECK 轮最多2次，cannot_help 轮最多2次；固定阶段最多7次，最早正常输出8次。

这是为明确工作流采用的默认预算，比旧上限12有所增加；不声称同成本更好。沿用当前模型/非思考参数；新增阶段的输出预算在提示和 schema 实现时明确，不能直接沿用不匹配的旧阶段名称。格式修复沿用每次最多1次、每任务最多2次的既有规则，单独统计。

开始新工作前必须确保可容纳该完整轮次和 FINAL；不足则以 budget_exhausted 结束。保留最终输出调用。失败时不把无效载荷提交到共享状态；一个事务中的 Candidate、处置与 Decision 要么全部成功，要么均不提交。原文保存供诊断。

STALLED 至少需引用一次对当前未解目标的真实工作尝试；固定 B 的尝试可计入，但“没有发现问题”不能伪造为对某个后来新问题的尝试。不是以轮数用完作为唯一停止方式，也不允许空理由直接逃过开放问题。

## 8. 输入输出契约的最小增量

继续使用现有 Candidate、步骤引用、HelpRequest、Contribution、Review 和版本信封。具体 JSON Schema 与提示词将在实现工序中与本表逐项对齐；本稿不是可被旧运行器直接加载的配置。

必要增量只有：

1. S 输出 Candidate 与新问题提案；无 Decision，无 FINISH。
2. Contribution 在现有 body 内要求“局部结果/条件/依据/接入位置/剩余桥接”；provided 时不得缺失，可先保持结构化短段落，避免增加冗余模型字段。
3. Review 提供 `checks`：target_refs、method、observation、conclusion、scope；以及具体问题提案。observation 为可复核依据，不得将手算标执行。
4. 共享问题表：程序 ID、来源、目标版本/步骤、问题描述、blocking、状态、处理事件。此表由事务生成，不让模型重抄全表。
5. U 输出对可见问题的处置增量，引用已有问题 ID；关闭时有理由与 evidence_refs/本次新增步骤引用。未提及问题保留原状态，不默认为解决。
6. Decision 绑定工作目标与停止类型；候选内容、问题处置、下一动作属于同一事务。
7. 程序自动生成 artifact/steps 增删改记录。模型只说明实际用途；解释补充不算代码变化，也不依赖模型自行准确列全 changed_step_ids。

新字段是我们的适配，不称为文献标准。候选中的步骤重排采用版本化引用；旧版本的引用不改写，新步骤必须明确引用来源，日志保留完整前后版本。

## 9. 三类路径示例（设计说明，非实验结果）

**有局部材料但连接缺失。** S 给出方法，但一个界的推导未完成；A1 从另一初稿提取约束并完成该界，指出前提；A2 检查成立域；A0 将它接入后续推导。若 A2 发现边界缺失，创建 blocking 问题，下一轮处理。

**答案一致却潜藏错误。** 不因一致跳过 B。A1 重建关键等式或手算边界，可能发现不同结果；A2 检查其新计算，A0 修正。若仍无人发现，允许完成并由离线评分揭示失败；不将完整流程等同保证正确。

**贡献无效或无法帮助。** B 已尝试但失败，C 对关键依赖仍不确定；A0 要么自己提出具体工作，要么换路径/成员。真实尝试后仍无可行办法可 stalled；有预算但有可做检查时，应选择 CHECK，而非 COMPLETE。

## 10. 下一工序与验收内容

接下来可以据此实现新的阶段提示、契约和运行器分支，保持旧版本可重跑。先处理固定 S/B/C/U、问题状态与停止，再接两轮定向工作和自动差异。无需再泛化扩展文献或增加组件。

实现完成后需要核查的内容：固定阶段实际执行、相同答案仍执行 B、cannot_help 不误关问题、关键未解项不能 COMPLETE、预算预留完整轮次、错误 review 可被有依据反驳、引用和版本错误不提交、旧日志不混入新版。此处列验收项目，本轮没有运行测试。

开发观察首先看实际局部结果、连接变化及题目完成情况。新对照共享新版初稿；继续独立推理各自只看自身轨迹。旧 E1 仅为历史参照。多项消融、等成本比较和精细贡献归因不阻塞本次设计与实现。
