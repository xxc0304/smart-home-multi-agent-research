## 1. 需要先修的工程缺口

CONTRIBUTE首调用、Q1的REPLY各触发一次SCHEMA_ERROR：support_refs最多12个，但A1提交了16条私有资料或16条加T的来源列表。JSON解析和引用ID本身合法，问题是数量上限。

schema允许分组贡献绕开上限，但不应依靠恢复删除聚合结论的部分有效来源。本次恢复确实主要减少引用数，未纠正计算。此次适配检查虽覆盖16资料输入，却只使用少量引用的短输出，没覆盖完整资料聚合引用。这是输入规模与输出引用容量的验收缺口。

后续应在独立v2中修正可见引用容量，并补16资料及T的真实形状离线检查；保留严格可见引用枚举、去重和原尝试预算。不能修改已冻结v1或把本次记录覆盖掉。

## 2. 协作执行了，但错误内容未被纠正

2. U1识别C2/C3矛盾，Q1向资料持有者请求16条原始valence。这次请求是真实且相关的，不是只有日志字段。
3. C13的16条逐项值正确，却把A四个-1加成-5；C15沿用D共享-1，宣称C=D、A=B。原始事实已足够，但推导错误。
4. 接收者更新同一应用并引用回复，却照收错误小计；U2仍以假平分为由提交共享排序。W1/W2的L1均8。

## 3. 适配措辞与复核角色的边界

我们的任务适配新增“Do not count the same fact twice”。C9把它扩大为相似属性合并，随后C14推演Communication/Public speaking等是否同一属性。官方原规则按逐条特征相加，并未授权这种语义合并。新增措辞确实成了错误分支入口；不能仅凭本次轨迹证明它是全部错误的原因，算术错误也独立存在。

资料持有者A1同时被选为两次核查者（来源权限覆盖最高），反复沿用自己报告的小计。程序原本就标epistemic_independence_guaranteed=false；本次显示有原始资料权限不代表独立重算可靠。此处先记录，不据单次失败立即新增角色或全面改路由。
