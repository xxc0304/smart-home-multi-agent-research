# 应用接续v2实现复审

## 判断

主干实现可以保留。本次源码复审未确认新的阻断性程序错误；回复目标约束、事务式更新、版本失效传播和最终未决约束确已接入运行器。

当前准确定位是“关键协议路径已通过离线工程验收”。不能将其扩大为“模型已按核心思想正确协作”或“实验准备全部完成”。本轮未改运行代码、未新增/重跑测试、未发API。核对验收记录中的6个v2源码和2个测试源码，8项哈希一致；133项通过是前次运行的证据。

## 1. 高优先级：实际知识使用的评价尚未补齐

state.py:132根据result/missing及已声明上游状态赋予applied_declared/provisional。runtime.py:65提交应用状态；候选排序独立由artifact提供，也允许保留旧文本。程序不能据此检查新回复是否真的改变了局部推导、该结果是否进入候选答案。

这符合规格已声明的语义边界，不是应通过“禁止答案不变”修复的错误：正确补充可以支持原答案，撤回一个路径也可以保持同一结果。缺的是内容层面的验证。

实施映射第29行提出了单独离线评价，但当前score仍复用ranking.score_run，只给排序和协议状态等，未形成应用接续的内容核验输出。原始C/U/Q/W日志已具备追溯材料，因此先补一份人工可审核的接续记录即可，不需要训练新裁判或复杂打分器。

每次真实交接至少核对：原步骤缺什么；回复实际补了什么；接收者如何用；局部结果及最终答案有无合理变化；无帮助/部分帮助时是否如实保留。状态转换本身不能替代这些判断。

## 2. 中优先级：多层更新的完整集成覆盖不足

tests/test_application_v2.py:341及383先直接调用多次apply构造依赖链，再进入run贡献/核查流程。这有效检查了注册表和stale调度，但没有覆盖正常入口中“贡献→初次应用→请求/核查→积累依赖→上游被纠正→多层更新”的完整组合。

已有7调用接续主干是完整Runner流程，不能说所有测试都只测数据结构；缺口集中在多层依赖更新与正常前序流程的组合。应补一条遵循正常调用顺序的脚本集成场景，不需要因此重写运行器。

## 3. 中优先级：上下文长度与服务兼容尚未验收

验收记录的最大脚本输入估计5064 tokens。runtime.packet每次发送全部U版本，公共贡献也随回复增长；旧版本内容、bindings.use和result可能明显长于短脚本。现有20次尝试上限不保证输入始终低于32768。

底层已有超限停止机制，不能据此说预算控制失效；但此次短脚本未覆盖接近真实输出长度的后段输入，也未验证新APPLY schema被DeepSeek服务接受。需要先补有代表性的长流程输入检查，再做最小接口兼容检查；只有出现真实压力问题再决定是否压缩历史，不预先扩建摘要系统。

## 4. 保留的合理边界

- 缺口发现、请求必要性与内容判断仍由模型承担；不强迫每题求助。
- 应用版本与请求、回复、候选关联分开记录，能区分收到回复和重新应用。
- 只沿直接U绑定传播，不自动从自然语言或C/W/Q/V推导完整依赖图。
- 排除、部分接受与退休可以保留有效原始贡献，不默认一错全删。
- 评估需检验资料优势和真实知识接续；NASA旧负结果继续保留。
