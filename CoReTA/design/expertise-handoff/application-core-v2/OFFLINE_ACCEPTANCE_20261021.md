## 验收范围

| 范围 | 已观察行为 |
|---|---|
| 接续主干 | 登记缺项→Q绑定U→REPLY新C→更新原应用并生成新版本 |
| 部分解决与无法帮助 | 保留missing；可拒绝C或无法帮助的Q记录；不标完成 |
| 退出原路径 | 允许只退役原U处理交接，不要求同时否定回复或核查意见 |
| 采用目标 | 接受回复及明确指向唯一U的核查，不能改在无关U上算处理完 |
| 后继更新 | 多层显式依赖失效后按上游到下游更新，再核查；排除上游不修复后继 |
| 自主完成 | 没有请求或没有需跟踪应用也可以提交并核查 |
| 状态一致性 | 不静默丢候选关联；保留文本但改依据产生新W；依赖未决不得完成 |
| 恢复与停止 | 格式/动作恢复无部分提交；总尝试、时间、3次干预与2次核查受限 |
| 入口与权限 | CLI主干、独立离线评分、中断保存、live开关、私有引用权限 |

测试使用明确标注的脚本输出。结果中的http_attempts表示经过传输层的模拟尝试；不能算真实API调用。脚本排序仅用于检查数组交付，脚本分数不可作为研究结果。

## 发现并修复的问题

1. 明确退役请求路径仍被强制要求采用/排除回复：已允许退役本身处理交接，保留原C。
2. 同一回复同时出现在bindings与excluded可绕过原目标检查：现在部分采用仍须处理原U。
3. 明确指向一个U的核查可通过无关应用“采用”：新增唯一当前U目标约束；整体W或多个U仍由模型定位。
4. 补目标约束后发现核查退役也有重复处理要求：与回复一样允许明确退役处理。

每个问题均先用失败测试复现，相关日志保留在runs/application-v2-offline-20261021/。未修改v1代码、任务资料、评分和既有实验结果。
