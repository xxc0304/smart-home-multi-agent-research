# 修订判断最小规格 v1

状态：隔离工具已实现并完成离线检查，未发起API调用，模型效果尚未验证。2026-10-21。实现及证据见IMPLEMENTATION.md。

## 1. 要解决的问题与范围

在已有工作解收到核查意见后，区分“旧结论受到什么影响”和“修改后的结论由什么支持”，避免将质疑直接转换为反向判断。该规则适用于局部事实、条件、推导和操作，不局限于排序。

这是现有CoReTA的待测修订规则，不是已经确认的新组件。先检验APPLY的接受决策，不同时改变贡献生成、检查者选择和讨论轮次。初次整合丢失有效贡献是另外的已知问题，本轮局部修订对照不声称解决它。

## 2. 缺陷与替代必须分别判断

| 已有内容 | 应作的判断与行动 |
|---|---|
| 反例、计算或事实直接否定当前结论，但尚无修复 | 承认缺陷；请求可完成的局部修复或保留未决，不能因没有替代而拒绝反例 |
| 替代推导/操作处理了缺陷，有相应任务依据 | 可以采用并说明改变了什么、保留什么；无需等待额外成员批准 |
| 只有“没充分证明”、另一种偏好或新猜测 | 记录疑问，不因此认定反面或替代成立；如有判别检查则请求，否则如实保留不确定性 |
| 质疑与原题事实、已有计算或适用范围冲突 | 根据具体内容拒绝或只接受其中成立的部分，不根据成员身份决定 |
| 两种方案都只有部分支持 | 比较现有任务依据，必要时求助；最终可提交最佳努力候选，但不把选择写成已证明结论 |

有效支持可以是已有资料、内部知识的明确应用、重新推导、手工计算或反例；不要求新引用、新资料或实验工具。此前没有完整证明不意味着结论错误，未被反驳也不意味着结论正确。

## 3. 现有字段如何承载

不新增JSON字段、对象类别、角色或模型调用类型。

- REVIEW.finding：具体观察、影响对象和范围。若发现真实缺陷但不知修复，仍可issue；仅有重要未决疑问时可undetermined，不强迫提出替代答案。REVIEW规则先保留为后续候选，不纳入第一阶段对照。
- APPLY.applications.result：以简短文字说明当前相关结论的依据、核查实际削弱了什么、拟修改内容的支持。只记录本次重要判断，不重写整份推理，不要求每项填模板。
- APPLY.excluded.reason：拒绝核查的具体部分或替代建议及依据；拒绝不能只写“没有新证据”或“原作者更专业”。
- APPLY.unresolved：仍有后果的真实缺口。若旧结论被有效推翻且未修好，不能仅因保留完整候选便清空此处。
- APPLY.request：复用ask/check/probe，仅在需要一项可完成的判别资料或操作时发起。recipient按需求和权限选择，原作者不是默认裁判。
- artifact：仍是当前完整候选或协议允许的null。保持候选不自动认证其正确；修改也不自动认证已解决问题。无法完成时沿用现有真实终止状态。

要求模型说明依据不是程序判真。结构验证只检查原契约、引用与处理记录，不按关键词或理由字数决定语义正确，也不以“理由看起来完整”强制放行修改。

## 4. 接续与复杂度

无需判别检查：直接APPLY处理核查，可以修改、部分修改、拒绝或保留未决。

需要具体资料/局部推导且有可访问者：沿用APPLY提出请求→REPLY→APPLY。请求问可改变当前决策的问题，不问谁赞成谁。原作者可能就是driver；资料持有者也可能是提出错误意见的人，不把找到更多参与者当作独立正确性保证。

保持原最多3次干预、2次最终核查、20次网络尝试的完整任务预算，不增加固定轮次。第一阶段诊断只执行单次修订，采用更小且两臂一致的诊断预算，见DIAGNOSTIC_PLAN.json；它不是完整任务预算的调整。

## 5. 编码映射与实施顺序

第一阶段只需一个隔离诊断工具：从旧轨迹重建核查后可见快照，调用现有Gateway/HandoffContracts/HandoffPrompts。对照臂使用现有提示，修订臂追加本目录PROMPT_DELTA.md中的APPLY片段。现有运行器和冻结提示不直接改动，不为一个诊断添加生产配置框架。

两臂都只做一次APPLY，禁止额外请求，确保检验的是修订判断文字的作用。保留现有一次结构恢复及有界传输重试；输出数组与评分仍沿用现有入口。

离线验证应覆盖：快照无未来V/W信息、两臂仅提示增量不同、权限与引用一致、未决可保留、有效反例不因缺少替代被忽略、接受有据修改与拒绝无据反转均可表达、原始轨迹不被覆盖。语义场景的脚本输出只能检验调度和记录，不能证明模型学会这些判断。

只有局部对照值得继续时，再单独检验REVIEW表达和按需接续；不得把多项同时变化的结果都归因于本规则。真实改善需要未用于该设计的任务和有资料优势的设置验证。
