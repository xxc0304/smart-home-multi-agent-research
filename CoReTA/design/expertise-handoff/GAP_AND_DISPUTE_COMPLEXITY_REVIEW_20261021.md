# 缺口发现与争议处理：可靠性及流程负担审核

日期：2026-10-21。审查上轮六项实现候选中的第2、5项及其整体负担。本轮仅分析设计，未运行模型、测试或修改运行实现。下述按需执行方式是待验证的候选变体，不代表已证明删减环节无损。

## 1. 总体判断

两项功能有必要，但原设计存在较重的执行解释：每条贡献各自审查、使用者重新审查、必做条件扰动、第三人再查、争议后重复整队讨论。这会增加串行等待、上下文长度、误报与程序状态分支，也可能把精力转到协作过程本身。

保留的研究对象是可接续的局部贡献及其实际应用、条件更正后局部更新。建议把通常路径收敛为“贡献→应用/整合→原题核查”，在可见事件出现时局部补证或检查。不要求所有步骤都经过同样的完整审查流程。

复杂度判断来自流程分析，尚无延迟、token、正确率或认知负担的测量结果。用户以解题能力为首要目标；简化的理由包括误报、上下文干扰和交接失效，而不仅是费用。

## 2. 第2项：发现缺口

### 2.1 保留的部分

成员提供局部内容与尚缺依赖；实际使用者在推进当前步骤时检查输入和操作是否可用。这两个视角互补，但无需分别安排两轮独立审计调用，可放入原本的贡献和应用回复。

### 2.2 必须修正的风险

| 风险 | 需要怎样处理 |
|---|---|
| 成员不知道自己遗漏了什么，自报和接收者都漏检 | 承认不能穷尽隐含前提；另保留提交前针对原始任务的整体核查，检查具体结果/约束，而非只问是否漏假设 |
| 无外部引用被当作无知识 | 模型内部知识与局部推导可作为候选支持；来源不足触发审视，不自动判错、删除或询问他人 |
| 列出大量与当前目标无关的未知 | 请求必须说明阻塞哪一步，或指出哪种可行替代前提会改变当前结果；不要求补齐一切背景知识 |
| 扰动修改已给事实，产生不可能分支 | 只有在能保持已有事实及必要约束时才生成局部对比；不能构造时可改用原始资料核对或直接检查推导 |
| 明明只缺一个可查参数，却先做两次假设推演 | 优先请求可取得的实际资料；依赖探测用于疑似隐含且会影响结果的补全，不机械覆盖每个已知缺口 |
| 所有资料齐备但使用者不会应用 | 将所缺操作、推导或工具权限写成具体请求，不能把缺口发现收缩成参数填表 |

### 2.3 建议采用的触发方式

贡献和应用回复只补充简短信息：当前推进哪一步，尚缺什么，为什么影响结果。以下信号可触发额外动作：

1. 当前步骤缺少必要输入或操作，确实无法继续。
2. 两份贡献在同对象和前提下导向不相容结果，需要局部核查。
3. 已用前提缺少支持，并有理由怀疑其另一合法取值/解释会改变结果，需要依赖探测或补证。
4. 当前应用或最终核查发现原题要求未满足，回查相关步骤及其依赖。

语义相关性与影响性仍由模型判断，程序只能检查显式声明与引用、调度和预算。调度条件不能写成“仅当系统已经知道答案错了”，也不允许研究者把真实缺口标签交给运行模型。

已识别的缺项优先定向询问；同一来源清楚且彼此相关的几项输入可合并请求。无缺口信号时继续应用，避免为每次消息交换新增审计。

## 3. 第5项：处理争议

### 3.1 并非所有分歧都需要独立讨论

先说明争议对象和任务后果。不同措辞可以指相同内容；不同条件可使不同结论同时成立。只有需要改变求解动作、适用性或最终结论的具体疑点，才进入局部核查。它仍可能是误报，不预设提出者正确。

质疑者需提供“针对哪项内容、为什么可能影响任务、已有依据或建议怎样核查”。可以是尚未证明的合理怀疑或可区分的检查，不要求较弱成员先给出完整反证才允许发言。

### 3.2 用有界局部处理替代反复全员辩论

一次争议采用以下候选流程：

1. 对齐对象、单位、前提和版本；若可直接消除表面分歧，则继续应用。
2. 选择一项最相关的检查：原始记录核对、局部重算、具体推导检查或最小反例。工具检查仅在运行时权限允许时使用。
3. 由能够取得该依据的成员交付检查结果；并非固定第三人裁定，也不只要求被质疑者重复解释。
4. 当前应用者依据结果更新相关输入、关系或操作，实际重算受影响部分。允许多层同时修改，不强制先唯一分类。
5. 仍无法判断时保留局部备选与未决原因，停止该次争议；有新依据才重开，否则转向其他路径或在预算结束时提交最佳努力答案。

首轮候选可设一项争议一次针对性检查、必要时一次补问；其上限可配置，尚无最优性结论。若多个争议同源，合并处理，不逐条重开会议。

有检查结果不等于有正确裁决。原始记录也可能版本不明，重算和反例可能有错；程序保存依据与变化，不能将同伴认可升级为数学/语义真值。

### 3.3 控制候选与上下文增长

保留一份当前工作解和争议位置的局部备选，不为每项疑问复制完整对话或自动枚举所有组合。程序保留完整原文，当前调用只加载相关贡献、必要支持、原始任务要求及明确引用的历史；按需取回更多材料。

同一项内容的支持发生变化时，只使显式依赖结果过期，并在最终原题核查中防范漏记依赖。精简上下文不能删除任务条件或把模型摘要当作不可质疑的原始证据。

## 4. 流程怎样减轻

| 场景 | 候选流程 |
|---|---|
| 资料充分、应用顺利 | 收集局部贡献→应用/整合成答案→原题核查后提交 |
| 缺少可取得的参数或操作 | 当前应用提出具体请求→相关成员回复→继续应用 |
| 疑似关键隐含假设 | 局部对比或补证→将依赖显式化→继续应用/定向求助 |
| 有影响结果的具体争议 | 对齐对象→一项针对性检查→局部更新；未决则有界保留 |
| 无新增材料或预算耗尽 | 停止局部循环，按同一任务标准交付并记录未决 |

在最简三人无异常路径中，可以设计为三份贡献、一次应用/整合、一次最终核查；此处只是阶段安排，不保证复杂任务固定五次调用。计划选择和简单自查尽量合并到现有回复，避免另加全职协调模型和逐消息审核链。

## 5. 核心机制保留与研究变化

始终保留：局部贡献可以在条件未满足时存续；不同成员的支持要进入实际应用；条件或关系修改后更新关联结果，保留仍有依据的其他支持。

候选简化：取消“每份初稿都必须额外做条件对比”的解释；改为关键疑似依赖触发探测，避免每步固定第三人审查和全员重复讨论。

此变化影响探测的执行时机，需要明确作为待验证方法变体，不能一边删掉强制探测一边声称它已被证明无用。未来可比较无额外探测、按需探测与更密集探测，观察缺口漏检、误报、最终能力和协调负担；本轮不开展这些实验。

剩余首要风险：按需处理可能漏掉没有显式信号的错误；最终原题核查提供另一触发机会，但仍不能保证发现所有问题。保留适度核查与控制过度协调之间的选择必须通过实测判断。

## 6. 处置建议

将本候选流程用于后续提示词与调度设计；先写清一次缺口请求和一次局部争议处理的完整输入输出，保留无异常的直接应用路径。检查同一典型状态下两项功能是否重复产生相同工作，能合并的合并。当前不新增角色或庞大状态枚举，不在本轮冻结预算最优值、宣布机制可靠或启动实验。
