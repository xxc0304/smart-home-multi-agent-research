# 最近结果及定位接口改进方案审查

日期：2026-10-20。范围：本地实现验证、MATH140的task_audit_v1单次真实回归、原始两次响应、运行与评分记录，以及下一版本的改进建议。本轮仅做离线审核，未修改冻结运行代码、未重跑模型或重评分。

审查结论：原始结果与主要诊断一致；“模型引用原句、程序计算位置”的方向可以保留。原建议还需补全来源选择、错误反馈和覆盖粒度规则。本稿给出可供下一版实现的最小修订；当前没有依据因这次运行去改三Agent协作骨架，也没有效果证据支持新机制。

## 1. 结果可信，但必须区分交付评分与机制执行

重新核对了23个冻结文件的SHA256、三份初稿payload哈希、两个实际请求及响应、事件列表和交付artifact，均与计划及报告一致。

- 4次逻辑调用包含3份缓存初稿；只有TaskFacts阶段实际发出2个API请求。1次有界修复不是重新运行整条实验。
- 两次请求的MATERIAL都只有与冻结版本相同的PublicTask，REFERENCE_INDEX为空，未配置工具。请求日志中未提供旧诊断、其他轨迹或gold。
- 三份初稿都是原来的错误初稿。运行未进入综合、B、U、C；审计记录0。实际交付artifact严格等于原A0初稿。
- 固定Docker评分为0，状态为degraded/runtime_error/unreviewed。因此交付成功率记失败是正确的，不能从能力统计中悄悄删去；同时必须标明协作机制尚未执行，不能把0分解释为“反例保留之后仍修不好”。

建议下一版汇总显式同时记录 `delivery_score`、`pipeline_completed` 和 `mechanism_evaluable`。本次对应0、false、false。它们描述不同问题，不改变原始分数。

## 2. 高优先：来源定位接口把可程序确定的工作交给了模型

F01的引文确实存在，正确跨度为[6,97)，模型两次却都填[4,152)。第二次响应10条prompt引文都能唯一精确匹配，10条申报跨度仍全错；其余两条路径把请求包装层当成PublicTask根。因此“字符位置/路径来源绑定失败”比笼统称“格式错误”更准确。JSON本身可解析、结构也通过。

这个失败来自接口设计及反馈：`validate_task_facts()`在首个错误退出，只回报F01不匹配；修复请求又统一要求修复syntax/structure，没有给出正确引文实际匹配的位置、全部错误清单或明确的字段根。模型修复了一处漏掉的`&`，却没有改正坐标。

本地测试确实通过，但它们主要验证正确构造的输入能通过、错误输入被拒绝。真实140 fixture中的正确跨度由Python正则生成，而生产流程要求模型填写；测试与真实输入生成方式不同。这是覆盖缺口，不应把测试通过解释为真实模型接口已经可靠。

## 3. 高优先：事实ID覆盖不等于逐条件覆盖

原响应的F02包含三个点，F03和F04各含两个点，八个点被装进四条约束记录。提示要求逐项提取，schema并没有落实这个粒度要求。

当前 `_inspection_errors()`以 `used_fact_ids == declared_fact_ids` 检查 `exhaustive_for_listed_facts`。本次离线构造了一个反例：F02保留三个点的原文，只提交(0,0)一条case，却在scope声称检查了三个点；该结构校验不报错。证据保存在 `MATH140_TASK_AUDIT_REVIEW_CHECKS_20261020.json`。这是本地构造的契约诊断，没有发生新的模型轨迹。

因此，即使修好了字符定位，也不能凭这个覆盖标记声称八个点都检查过。应给声明的可检查条件独立ID，并按这些检查项记录coverage；来源引文可以共享，但不能用“引用了同一条包含多个条件的事实”替代逐项检查。程序仍无法自动证明模型提取了题面全部条件，覆盖结论必须限定为所声明检查项，不能推广为整道题的穷尽验证。

## 4. 中优先：精确引文只能验证来源，不能验证语义

首次F01擅自加入real-coefficient，同一输出F09又承认系数域未声明；修复后撤回了real限定。F01/F09和F06/F10在第二份响应中各共享同一段原文，却表达不同解释。这说明：

- 同一原文被多条解释引用并非自动重复错误，不能按引文直接去重删除事实。
- 引文精确匹配成功只能称“来源已绑定”；normalized_fact仍是模型解释，需要与完整题面比较。
- 任务元数据task_type与空entry_point由程序已知，不必让数学任务的事实提取阶段再为它们生成路径；删除这种重复操作能减少本次暴露的无效输出，但不能把必要题意条件当作可丢弃项。

## 5. 推荐的最小修订规格

### 模型与程序的职责

模型提交 `fact_id`、预定义 `source_id`、原文 `quoted_text`、解释和类型，不再填写start/end，也不生成JSON Pointer。数学任务提供prompt来源；代码任务可额外提供有意义的entry_point来源。source_id来自程序提供的固定白名单，程序映射到PublicTask字段。

程序在解析后的原始字符串中查找引句：

1. 精确且唯一出现：生成来源位置，保存模型原始输出和派生定位。
2. 精确出现多次：标为ambiguous，要求更完整上下文；不默认取第一处。
3. 无精确匹配：标为unmatched，反馈对应fact_id和原引句；不通过去空格、删标点、公式改写或模糊匹配制造“来源正确”。

JSON转义的正常解码不属于模糊匹配；应在解码后的题面字符串上操作，并使用明确的Unicode字符索引。原始响应与程序派生位置分开保留。

### 错误处理与覆盖

一次收集全部绑定错误，修复只针对未解决条目；已绑定条目保留，避免为修复一个字段重写全部事实。涉及题意的必要来源在预算内仍无法绑定时，应明确记录入口降级，不能通过静默删掉该条件换取complete。本轮不引入无条件“忽略坏事实继续”的全局兜底。

每个声明的检查项应单独关联案例。覆盖标签只报告声明项覆盖；提取遗漏、解释不一致或仍有未定位条件时保留partial/unknown。完整公共题面继续对后续Agent可见。来源对齐不提供数学求解、算术验证或模型共同错误的保障。

### 修改范围

保持三Agent、B→U→C、反例先入账、repair/rebuttal与14次逻辑预算。下一版只修来源绑定接口、修复反馈和检查项覆盖表达，并在新版本/新计划中明确这些变化。保留v1代码与本次失败的冻结记录。

## 6. 执行顺序与通过条件

1. 先实现上述来源绑定和覆盖边界；不修改本次失败结果。
2. 直接回放本次两份真实响应中的引文，而不是先手工补正再验证。期望首次F02因缺`&`仍被准确报告为unmatched；其余可精确匹配的引文绑定成功。第二次10条prompt引文全部可绑定。旧JSON Pointer字段通过明确的新schema迁移，不用隐式字符串删前缀伪装为模型已修正。
3. 验证重复引文、短引文、缺字、TeX符号、Unicode、同一来源支持不同解释、一个事实含多个检查项，以及已绑定项在修复后仍保留。不能只统计新增测试数量；应记录这些具体通过条件。
4. 离线验证通过后，冻结新版本对140做一次工程回归。仍复用原三份错误初稿，并分别检查入口是否完成、C是否真实发现反例、后续是否修复/反驳并复核、最终得分是否改变。
5. 完成这条工程闭环后再考虑新题对照。单题回归即使成功，也只提供已见工程证据。
