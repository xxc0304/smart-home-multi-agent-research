# CoReTA近期修改与架构审查

## 总体判断

核心协作假设仍有研究价值，但实现协议过重、真实可执行性不足，尚不宜扩展题集或批量稳定性试验。建议保留核心流程，先收敛模型与程序职责。不是全部推倒，也不是再叠加一版字段后继续付费试跑。

本审查基于本地设计、实际代码和已保存轨迹，未检索文献、未进行新模型调用、未运行测试。既有208次测试只能说明已列fixture通过，不能证明真实协议可靠或数学正确。

## 原设计到当前实现

最早v0.3是共享候选、定向请求、成员贡献、检查、应用反馈和程序调度。后来主动建设性阶段替代仅靠A0发现缺口的触发，流程从B/C/U改成B/U/C（应用后复核），取消自由final改写，再增加TaskFacts、原文绑定、审计保留、双路径关闭和历史归属。三成员、同模型、无在线求解工具和互补目标保持。调用顺序、停止规则和关闭规则已实质改变，不能把近期全部修改称为格式工程。

| 模块 | 评价 | 建议 |
|---|---|---|
| 三份独立初稿及综合 | 保留多种初始材料，但同模型操作差异不保证互补 | 保留，分别标注局部贡献与独立重解 |
| 建设性补充及实际应用 | 与主动互补目标直接相关；已有一次反例驱动正确修复过程 | 保留，检查贡献被用在何处 |
| 应用后独立角色复核 | 能避免A0单方面关闭，但不同实例不等于认知独立 | 保留角色门控，不把reviewed当正确 |
| 任务约束提取/原文绑定 | 有助于锚定核查，但曾成为标点级阻塞入口 | 保留公共原文可追溯性；考虑程序预分配来源片段标识，模型只选择并解释；穷尽性不可由绑定证明 |
| 不可覆盖反例账本 | 对已提交矛盾保留有必要 | 程序负责保存，模型不复制旧账本 |
| repair/rebuttal与历史归属 | 思路必要，目前契约实现不合适 | 区分旧证据、新观察、替代对象验证；重做最小接口 |
| 多层运行器/设计版本 | 保存历史合理，当前入口与规范过多易混淆 | 选一个开发入口和一份当前规格；旧版本作为冻结参考，不删除旧记录 |

## 主要问题及严重性

### 1. 机制级：把不可变历史当作必须复制的重查结果

v7要求historical记录原payload逐值相等（除issue映射），原案例、观测、verdict、scope等均保持，再要求它参与独立复查。原记录不可覆盖应是存储性质，新的复查理应允许得到不同观测或判断。如果原观察本来就错，逐字复制不能构成真实核查。rebuttal也不能通过这种复制证明原反例错误。

改法：程序保留原记录；检查者提交新的观测与理由，程序追加保存两者差异。原反例仍成立但被替代，与原反例本身算错，必须分别处理。

### 2. 接口级：让模型生成可由程序维护的关系

数组索引、重复原record、版本/hash、来源跨度、已存在的ID集合，造成额外输出负担和人为失败面。最近[0,1,2]对两条记录的错误，是此问题的直接证据。应在输入提供稳定句柄，程序生成身份、关联和时间戳，模型只选择已提供句柄并给新推理。必须保留必要语义目标选择，不由程序猜测哪个结论被修复。

### 3. 机制级：历史反例与当前候选缺陷一度混淆

旧g1错误不会因新p1正确而消失。关闭条件应是当前方案不再依赖旧错误对象且替换有效，而非要求旧g1变成正确。v7补了这个方向，但又增加复制与索引要求；应保留语义原则、重做接口，不直接放松现有校验求通过。

### 4. 语义级：数值门控不等于数学验证

程序只能判断模型声明的两个精确数是否相等，不能保证量、对象、公式、计算或依赖解释正确。检查者曾认可错误解空间，旧反例和新主张混在一记录中。应分别记录结构通过、引用通过、关键数学正确、当前问题处理合理，不能合并成“有效检查”。

### 5. 实验级：已见单题与逐次补丁不足以支持能力主张

140已被反复诊断，属于开发案例；不能据其成功/失败推断一般收益。此前出现C反例→另一成员正确推导，支持有用修复过程；尚未证明局部贡献组合优于额外独立重解，也没有稳定端到端或对照结果。测试数量增加不替代这些证据。

## 最小职责划分（建议，尚未实现）

Agent：具体问题/主张；新推导或修改；实际检查与新观察；是否仍依赖旧错误及理由；对修复或反驳的独立判断。

程序：原题/候选/证据存取；句柄、版本、hash、角色、关联与时间戳；原记录不可变；把新观察追加并与历史对照；预算与停止。

检查输出只需围绕：当前候选新检查、新发现；按已提供issue/case句柄提交复查观察；对替换关系给出有依据判断。历史账本直接引用，不全文输出；新record由程序生成稳定ID，不让模型填写数组位置。归属关系仍须检查者明确说明，不自动假定正确替换。

## 下一步及验收

1. 先完成一份当前架构规格和最小输入/输出例子，覆盖同对象修复、对象替换、原异议错误三类。不要同时改角色、工具或调用轮数。
2. 按该规格实现职责收敛，复用现有候选与账本，不再扩展继承链；旧冻结入口保持原样。用全部已保存错误做离线回放。模型旧输出只作为诊断，不自动转换成新成功记录。
3. 验收：原记录不改；新观察允许纠正旧计算；错误角色/不可见引用在发送前被拦；历史反例不误阻塞已验证替换；虚假弃用、当前反例、桥梁不明仍保持open；无需复制历史或填写生成后索引。语义真实性仍需人工审查。
4. 验收后仅做一组预先冻结的错误/修复候选组件核查，全部失败保留；若仍需新字段才能运行，先复审，不连续循环付费。
5. 再做一次完整开发回归；能够获得完整轨迹后，冻结新题共享初稿与对照。分别报告全员初稿失败恢复、已有正确答案的损失、流程失败和互补过程。

当前最优先交付是步骤1的职责与契约收敛，不是再调用一次模型，也不是立即跑稳定性六次实验。
