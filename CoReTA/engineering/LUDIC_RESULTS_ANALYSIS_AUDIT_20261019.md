# 最近603实验与分析审核

审核方式：本地原始日志、评分输入/输出、冻结哈希与实现静态核对。未发起模型调用、未重跑评分或实验、未修改运行协议。不是独立审稿或文献复核。

## 总判断

失败分数与主要事件链可确认；归因找到了真实的程序允许路径，但不足以证明其为解题失败的充分原因。修改方向有价值，尚非可直接实施的完整设计。应先补调度及比较协议，分开验证工程约束与解题收益。

## 1. 已核实的事实

- 冻结计划所有source_hashes仍一致，四条件初稿payload哈希均与筛选初稿一致。
- 三个初稿在筛选中任务分数为0；本轮四条件prefinal/final共8份产物任务分数均0，评分容器正常结束，报告AssertionError。四条件评分输入均使用相同原始三条断言。
- 29次逻辑调用、20次新增HTTP、3次格式修复与result/响应记录相符。缓存初稿计入逻辑调用，不重复计新增HTTP。
- CoReTA发现并记录矛盾，A1以无可见依据的MBPP参考断言反驳，A2指出依据不足并维持阻塞，A0关闭问题；final改动代码但未再检查。该链条与原始事件相符。
- A0首次apply时remaining_work_turns=2；本轮没有耗尽正常调用上限后被迫停止。

## 2. [高] 普通讨论失败原因先前报告不够具体

此前只称“不可用响应/响应故障”。responses.jsonl显示static_debate两次响应均status=incomplete，incomplete_details.reason=max_output_tokens，max_output_tokens=2048，实际output_tokens=2048。内容并非API没有生成；validation.raw为空来自运行时在不完整响应时未抽取文本。

CoReTA的build首次响应、independent_refine的一次响应也同样在2048处截断，各自重试成功。不是普通讨论独有问题，也不能据此判定某方法天然更差；它暴露当前输出schema/长度与阶段限额的适配风险。

后续新协议需先估算或校准输出长度，统一定义截断处理与HTTP/修复预算，保持历史结果不变。不能只给失败基线临时加限额后挑选替代结果；如重跑应另建完整、事先固定的对照批次。

## 3. [高] 结构缺口已证实，能力归因仍需反事实

update_registry允许有可见引用或改过步骤即关闭问题；validate_update读取关闭后的registry；final允许新推理与改码且不触发复核。这些是代码事实。

但不能由此推出“阻止关闭就会得到正确解”。本例没有成员构造正确完整算法，检查者也可能错；多检查一轮可能只是更长的错误争论。准确表述为：当前协议允许未充分回应的异议被关闭，且存在未复核最终变更；二者是应验证的设计缺口，而非已经实验证明的唯一根因。

最终化不是本轮从正确变错误的原因：prefinal已失败，final仍失败。收紧final首先提高产物与过程的对应性，未必增加正确率，甚至可能失去原final本可产生的新解。若改为直接导出候选，须为独立综合定义新的显式综合阶段，否则它原本只有三初稿+final，会被意外取消解题环节。

## 4. [中] “检查意见正确”与“互补”仍需收窄

A2正确暴露无依据参考断言及候选矛盾，不等于它对数列定义的全部说明正确，更不等于它已有正确修复。当前观察到局部有用的纠错与反对意见，尚无“通过组合成员贡献形成正确完整解”的证据。

本题三份初稿有高度重合的错误筛法。角色标签不同不保证知识、策略或错误独立。本例能诊断信息采纳与关闭失败，不能据此证明成员原本已有足够互补材料而被纯粹组织问题浪费，也不能反向证明模型绝无能力。

## 5. [中] 修改方案仍缺可执行细节

closure_proposal/pending_check方向合理，但“最小修改”措辞过早。至少需要在实现前确定：

1. 复核绑定哪个候选版本及哪些异议；修改候选后旧复核何时失效。
2. 检查者不同意时的下一步、可反驳方式、预算耗尽时交付什么；不能用检查者单票作为真值或让争议无限循环。
3. 完整最坏调用路径。旧路径三初稿+S/B/C/U为7次，两轮各工作/检查/应用3次，加final即14；额外关闭复核不能无说明塞入同一上限。若减少工作轮，也是一项实验处理变化。
4. 问题拆分与合并规则，避免“每个问题原子化”变成无限子项或新增大量字段。
5. 四条件统一交付语义及截断策略；独立综合必须保留综合机会。

建议先隔离两个因素：关闭复核机制与最终交付规则。资源允许时做旧版、仅关闭复核、仅交付规则、两者组合；不把提示词改写、预算扩张、在线执行同时混入一次修订后将收益全归于单机制。

## 6. [中] 任务与评分外推边界

603有lucid/ludic笔误且已反复分析，是已见开发诊断题，不是无歧义新题。使用它检验状态约束是否执行合理，但不能用其修复后成功作为总体能力证据。

task_score=0表示至少一条断言失败。评分器遇异常退出，现有记录不支持“三个测试各自全失败”或逐测试改进数量。四条件全0也不等于算法完全相同或错误程度相同。没有统计显著性或总体优劣结论。

## 审核后的推进顺序

先完成关闭复核的状态转换、调用路径、最终交付与截断处理设计，再实施。工程检查验证协议约束；603用于已见诊断。能力验证使用独立选定的新困难任务，分别报告误报完成、实际修复、全员失败后的恢复及基线比较，不只报告流程更规范。

本次审核未证明CoReTA有效或无效；确认本轮失败与可定位缺口，同时纠正了运行故障归因不足和修改方案成熟度过高的表述。
