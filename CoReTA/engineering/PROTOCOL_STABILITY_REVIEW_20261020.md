# 协议工程集中审查与离线收敛

## 审查结论

近五次已见140开发运行不构成能力实验：v1停在来源跨度，v2停在首轮审计ID，v3到C和正确work后停在引用索引/输入预算，v4停在C输出截断，v5又停在TaskFacts语法/来源组合错误。不能将这些0分全部解读为协作无效，也不能凭一次正确work宣布协作有效。

集中问题是结构化输出与恢复路径衔接。原测试多数覆盖单一错误，但漏了“一个阶段先语法错、修复后来源错”等组合。旧入口每阶段一次修复的限制与全局两次修复不一致。本轮新增独立v6修复此路径，不改写任何旧版本或失败记录。

## 故障矩阵与处理

| 故障 | 处理与离线证据 | 仍有限制 |
|---|---|---|
| JSON语法或多余尾部 | StabilityClient捕获完整原输出；TaskFacts反馈包含原文与错误，不静默提取首个JSON | 模型仍可能反复输出无效内容 |
| 引文缺符号/错误来源 | 原文唯一精确绑定；成功条目锁定，只允许未绑定条目patch | 不模糊匹配；语义完整性仍是模型判断 |
| 先语法错再来源错 | v6允许在原全局两次修复内顺序恢复；真实两输出+显式人工patch测试通过 | 人工patch是fixture，未证明模型能自行生成 |
| 审计引用漏收录 | v4实际完整记录可引用，仅提及ID不授予可见性 | 尚缺完整带反例修复的真实闭环 |
| 输入/修复预算 | 原始材料完整保留，紧凑编码；每次发送前预检，超限0外发 | 内容继续增长仍可超限；不保证无限恢复 |
| 检查输出截断 | v5 inspect8192；完整partial进入修复；最多一次检查修复，片段不入账 | 尚未完成真实模型检查验证 |
| 修复额度耗尽 | v6全局仍2次，不增逻辑阶段；连续3次无效输出停止，已有修复消耗也计入 | TaskFacts消耗2次后，其他阶段无修复余量 |
| 错误关闭/遗漏反例 | 原审计记录、逐项异议与原案例复查、独立检查门控保留 | 手算和模型语义判断仍可能错 |

## 字段必要性审查

ClosureInspection有6个根字段，传递schema中44个属性声明（不是每次必须生成44个字段）。最明显重复出现在checks.method/observation、closure_reviews.method/observation、issues.description和audit_records的计算叙述。v5已要求决定性计算在审计记录写一次，其余简短说明关联；本轮不再叠加新的格式字段。

保留candidate_version/hash防止检查旧候选；保留issue/objection/record绑定以防止错误关闭；保留fact/item/input与精确值以支持原案例复查。直接删除这些字段会改变机制与审计能力，当前没有证据支持此举。checks、issues、closure_reviews、audit_records各自服务一般核查、新异议、关闭复核和不可覆盖证据，不应无设计地合并。重复自由文本先减少，协议字段暂不进一步扩张。

## 验证及边界

新增6项检查，包含真实两次TaskFacts输出串联、错误patch不可改锁定条目、全局额度、无效输出耗尽、输入超限零请求，以及真实schema脚本完整闭环。全套195次执行通过。此前测试继续覆盖引用、截断、预算、审计复查等路径。真实失败输出只用于离线输入，人工patch及脚本输出均不记作模型结果。

五份冻结计划来源哈希全部一致（各23/25/27/34/36文件，彼此有重叠）。本轮0外部API、无新评分。

## 下一步顺序

优先做独立标记的检查组件回放，输入固定公开候选及其约束，验证8192输出与恢复路径；只报告组件工程表现。需要完整端到端结果时，再冻结v6的一次运行，严格复用原三错初稿，所有失败保留。组件回放不可合并计作原始端到端成功。当前不宣称工程已不会再出错，也不再次直接付费重跑。
