# 设计—实现—真实行为诊断

日期：2026-10-19。范围：已完成E1中20条CoReTA轨迹。执行者本地审查，无独立外部review。新增模型生成0；未修改原协议、原提示词、任务、gold、评分或既有轨迹。

## 1. 直接回答：哪里出了问题

**没有发现程序把当前设计执行成另一套流程的证据；发现了Agent在内容核验和应用记账上的真实错误。同时，当前设计将求助需求与停止判断主要交给模型，允许其在初审后直接结束，本轮正是走了这个合法分支。**

所以不能简单二选一：“架构正确，只是Agent没照做”或“核心思想已被证伪”。形式流程基本符合规格；部分语义行为不符合指令要求；现有规则没有保证这些语义要求可靠落实。主Agent何时发现缺口、何时请求、何时结束本来就是方法组成，不能把其不可靠表现排除在架构责任之外。

对局部互补的结论仍是未获验证：帮助请求、贡献互审及贡献后的应用均无真实执行样本，无法把失败定位到这些尚未执行的组件。

## 3. 新定位到的内容错误传播：mbpp/train/799

任务为32位循环左移。A0初稿的代码和相关原始步骤已正确处理掩码与回卷。

### 初审新增了错误“验证”

A2声称：n=0x80000001、d=1，左旋结果为0x40000000，并将其当作支持代码正确的例子。

独立整数运算可直接核对：

```text
0x80000001 << 1  = 0x100000002
0x80000001 >> 31 = 0x1
(0x100000002 | 0x1) & 0xFFFFFFFF = 0x3
```

即正确结果为3，不是0x40000000。本轮仅计算这些整数表达式，没有在宿主机执行生成的候选函数。

### A0将错误例子接入候选

原始s5仅解释d=0的行为。更新后的s5新增了上述错误例子，引用初审e0003，并保持supported。Application为accepted/resolved，却填写changed_step_ids=[]。随后选择FINISH。

这里可以定位：错误局部材料由初审出现，被接入候选步骤，错误没有得到纠正，记录也漏报了实际文本变化。该例没有改变代码artifact，原测试仍通过。因此它证明的是**局部推理核验与应用记录不可靠**，不是本题最终代码得分被降低，也不证明所有初审都有害。

它比单纯统计“无请求”更能暴露架构的实际弱处：消息和引用可以合法，但内容未正确核验就成为支持依据；resolved标签也可能只是模型自述。

## 4. 为什么请求链没有启动

### 已证实的直接原因

19条合法更新返回FINISH，源码按设计终止工作轮；另1条因引用错误进入降级最终化。没有请求被程序偷偷丢弃，没有已产生的HELP贡献被遗漏。定向帮助没有启动的直接位置就在首次主Agent动作选择。

### 为什么会选择FINISH：可见理由与尚未验证的解释

可见理由大体为已有答案完整、初审支持，或剩余问题是题面未说明的约定。多数任务的主体解法在三份初稿中已经相近；已有A0初稿17题通过原评分，另外3题的评价一致性有疑点。这使本批难以提供清楚的“仍有实质缺口，成员可以进一步补上”的判断样例。

但不能据此排除局部互补，也不能把全部结束都认定为过早。尤其“没有同伴现成正确整解”不是本研究缺少局部互补机会的证明。

当前规格本身有以下设计假设，尚未得到验证：

1. **把需求识别交给整解维护者。** A0在同一次调用中先给出完整更新候选，再选择动作。模型可能认为候选完整即无需请求，但未做干预验证其因果作用。
2. **把后续帮助当作可选的新推理来源。** A0已经看到三份完整初稿；后续请求需要产生已有材料之外的内容。当前没有观测到它形成这样的请求。
3. **缺口与完成判断主要依靠语言指令。** 设计规定请求字段和合法动作，但没有进一步规定可操作的需求诊断程序。模板要求说明使用，却不能保证模型真正核算每个依据；799就是实际失效例。
4. **允许未决状态结束。** 这是原设计的明确选择，适合避免对无解的题面约定无效循环；同时也意味着“有未决项”不会自动激活帮助。需要检验模型是否分得清可解决缺口与不可获得的信息，本批尚不足以给出成功率。

这些不是已证实的单因素原因。未追加任何“换提示、禁FINISH、强制求助”的实验，因此不能声称已经证明某项修改能带来提升。

## 6. 下一步应修什么，哪些还不能直接改

### 可直接定位的小修

- 引用错误反馈给出具体字段、实际值、期望ID或null，修复802暴露的模糊反馈。
- 应用记录至少覆盖实际新增/改写的步骤文本；可做确定性文本变更核对，但不能把它称为语义正确性验证。799提供了现成的漏记载荷。
- 预算描述明确区分“还有轮数但无需继续”和“轮数用尽”；不靠解析一句英文理由强制改动作。

这些修改能改进记录或合约可靠性，不能据此预告解题能力提升。本轮未应用任何修改。

### 需要先明确的机制设计

应把首次决策的诊断过程具体化：公开约束下还有什么未验证的主张，现有成员材料有何不同，哪项局部交付有望改变当前解，选择结束有什么依据。初审新增的支持也应成为待核对的主张，不能仅因名为review便升级为真。

这不等于增加一个Agent或强制每题求助，也不要求某个成员先独立整题答对。目标仍是能够产生、核对和连接不同成员的局部推理。

验证这些规则时，需要评价清楚、可追踪局部缺口的开发诊断案例，以及保持原样本总体报告的对照。不能用已知gold作为在线纠错提示，不把事后挑出的有利案例当总体效果。若今后观察到全员整解未通过而团队通过，还应核查是局部联合补全，还是主Agent/Finalizer额外独自重解。

### 新的范围统计

在19条有效首次更新中，17条artifact逐字保持A0初稿；有效代码更新9条，其代码artifact全部未改。6条更新修改了至少一个步骤的文本，但包含验证补充、说明改写和错误例子传播，不能把6解释为6次有效互补。

更新后步骤中，仅5134和763显式引用A1/A2初稿；这只是显式引用统计，**不能从其他轨迹未引用推断它们完全未阅读或未受影响**。判断实质内容使用仍要看具体文本及连接。

上述代码不变统计只针对首次A0更新，另行核查了最终化：10条CoReTA代码轨迹中，只有763的Finalizer改变了去除docstring后的AST；802只改了说明文本。763最终代码主体与A2已有初稿AST相同，使用排序加相邻差，并采用n<2返回None。最终记录也引用A1/A2初稿。它支持“已有完整实现被择取”的解释，不是可见的不同局部算法组成一个新解；原前后评分都通过，没有新增补救。

AST相同或不同不是语义等价证明，本次只将其作为文本对照定位工具；没有在宿主机执行候选代码。

### 现有规则在哪些地方还不够具体

1. **从问题到动作**：现有模板列出可选动作及请求要填什么，但没有把“可检验的剩余主张—当前证据不足之处—所需新增内容—请求或结束的依据”展开成明确的诊断步骤。不能据此断言增加这种提示一定提高表现，但它是需要具体化并验证的机制假设。
2. **把检查计划用于实际核查**：Request.check_plan和Contribution.check_suggestion会作为数据传入，Review模板主要要求Audit SUBJECT against PUBLIC_TASK；没有明确逐项回报这些检查要求完成了什么、发现什么。因为本轮无HELP，这只是静态规则缺口，不能被列作已证实的本轮失败原因。
3. **核验新增依据**：A0已被要求判断贡献，但799说明实际没有正确核算新增例子；后续应明确把“review提供的支持”也作为待检验的主张。字段与文字要求存在，不等于执行可靠。
4. **登记与内容变化一致**：程序只校验changed_step_ids是新候选中合法ID的子集；它没有检查新增/改写的步骤是否被覆盖，799因此合法提交却漏记s5。可增加确定性文本变化核对，而不冒充自动语义验证。

建议修订应优先使上述判断和核查可执行、可追踪，保持三Agent和现有信息边界；不先通过强制调用、轮数扩张或把完整答案拆成固定角色来制造协作现象。修订后仍需分开验证：消息结构能否执行、局部贡献是否正确且被连接、最终能力是否提升。
