# 后续实现边界与交付拆分

状态：设计交接草案；本轮没有新增运行代码、测试或解题API调用。以最终FINAL_PROPOSAL.md为方法规范，旧运行器不覆盖。

## 最小实现范围

| 部分 | 要实现的行为 | 可复用部分 |
|---|---|---|
| 不可变产物与工作板 | 原生初稿候选区、当前Work、试用副本、可交付回退F、版本定位与原样选择 | 日志和任务产物渲染 |
| 成员输入构造 | 同快照的独立观察、私有材料与公开消息边界、检查输入的隔离 | 原有成员资料和权限加载 |
| 一个统一调度器 | 初始化→观察→选择一条贡献→试用→检查→选择→收尾；每条分支有预算和失败出口 | 现有gateway、用量与传输错误记录 |
| 短消息接口 | pass/offer；实际产物或无法应用；检查观察；候选指针选择 | 原有结构化接口能力，需独立确认服务兼容 |
| 任务adapter | 原生交付形状、定位、渲染和既有工具；不把离线gold带入模型输入 | 当前四项/十五项任务的输入、评分和可见材料 |
| 独立过程导出 | 原offer、试用前后产物、用法记录、检查观察、最终版本；真实性与正确性标签另行离线加 | 原有原始请求/响应与调用追踪 |

建议新模块独立组织，不把v2的C/U/Q等全部状态搬过来再加字段。代码包名称在实施时确定，不影响研究贡献；真实模型配置从既有接入读取。

## 状态分支必须能表达

- 初稿存在完整正确候选，但编辑者初稿错误；候选可直接进入工作路径。
- 全部pass；没有任何提供者，但收尾角色仍确定。
- 有多条offer；未入选与被拒绝、试用后未采纳分别记录。
- 有效反例但没有修复方案；不当作非法贡献。
- 无法应用；具体原因返回提供者，不生成假trial或假检查。
- 新产物不满足交付形状；保留F，不能把形状合法等同正确。
- 有来源记录但第三方无法看原件；只检查可见范围，不虚构核实。
- 收尾引入新内容；真实候选经过检查，最终选择不能又改写。
- 执行器缺席、失败或仅模型自称成功；三者分开。
- 上下文不足、格式恢复或传输中断；保留真实记录、预算和可交付版本，不静默改写原输出或结果。

这些是实现需求，不是本轮已运行通过的验收。

## 实现与实验分两次冻结

先冻结方法的实际状态转移、消息输入和产物选择；再冻结数据、模型配置、token/调用/工具上限、强普通讨论对照、重复与停止规则。结构化服务兼容及状态边界核对属于后续工程工作，不等于架构能力已验证。

实验不继续沿用“普通讨论只跑少量轮次、CoReTA多次检查”的不对称设置。采用相同初答方式、候选访问、工具和充分有效推理机会；固定同一内容回放仍单列诊断，避免把人工构造错误当自然互补成功。

## 本轮结束时应保留的问题

设计可实现，不代表收益已成立。重点风险仍是：持有者也识别不了贡献机会；编辑者拒绝/误用正确知识；两位同源检查者重复错误；额外上下文与流程反而降低自然解题质量。后续日志必须定位这些失效，而不是仅统计采纳和闭环完成次数。
