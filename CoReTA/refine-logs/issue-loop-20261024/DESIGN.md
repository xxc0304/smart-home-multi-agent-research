# 检查闭环修订（独立候选，未验证效果）

## 实现前约定

- 新增 `ground_issue_loop_v2` 候选，原 `ground_full_public_v1`、已冻结批次及原始日志不改写。沿用 OBSERVE→GROUND→TRY→CHECK_USE→CHOOSE 和终稿双检查，不新增模型调用。
- 权限元数据描述原件的分配/可访问性，不证明成员实际阅读，也不把作者私件内容或新的引用权限授予检查者。检查包分别给出 CHECKER_ACCESS 和按作品 ID 索引的 WORK_AUTHOR_ACCESS。
- 复用其他作者的作品时，当前应用者仍为编辑者，因此另外给出 APPLICATION_ACTOR_ACCESS。应用来源声明按当前应用者权限核对，作品中的第一人称表述按原作者权限核对。
- 检查意见必须指向具体问题、位置、依据和可能后果。程序分配问题 ID；模型不得自行宣称检查通过就等于答案正确。
- CHOOSE/FINAL_CHOOSE 对程序列出的每条问题返回 accept/reject/unresolved 及理由。accept 表示认可问题、仍待修订，不表示已经解决。reject 是编辑者判断，不等于客观驳倒。
- 后续检查逐条报告 resolved/persists/unable；记录绑定所检查的版本。只有对当前选择版本有 resolved 且无相反/不确定复核时，问题才从后续待核列表移除；全部历史留在账本。状态为 model_reported_resolved，不能当作真值。
- 旧版本上的解决结论不自动继承给新版本；涉及新版本时重新核对。相互冲突的复核不能用最后一条覆盖。
- 模型仍可能形式上回应但语义判断错误。本次工程验证不能说明误报减少、募资权衡改善或准确率提高。

## 离线验收

真实 005 存档用于验证作者 A2 与检查者 A3 的权限分离、W6 漏列 O5 与 W7 补列的静态事实。脚本模型用于验证完整工作流：问题逐条处置、修订阶段接收问题、终稿复核、反对意见冲突保留、旧版本解决状态不跨版本继承、遗漏回应会被 schema 拒绝。任何脚本输出都不计作真实模型结果。

新选择阶段有更长输出，显式设置 choose/final_choose 输出 cap；增加的实际 token 开销要在真实对照中测量。未建立新的实验冻结或调用 DeepSeek。

终稿检查才首次发现的问题仍可能保留到交付；本候选没有新增修订调用，不能声称所有问题强制修复。工程改动保证可追踪和逐条回应，不能保证回应内容正确。

## 实际长稿负载后的共同输入修正

真实历史稿压力测试发现重复全文加上问题记录可能超出32768输入预算。两组均改为CANDIDATES保存每份完整作品一次，CURRENT_WORK/BEFORE/AFTER/FINAL_PROPOSAL/FALLBACK只引用对应作品ID。完整原文、位置和问题历史不删减，检查包明确如何解析引用；没有增加同一任务的新资料。工程测试逐一核对句柄解析后的作品与Board记录完全相等。
