# 实验计划

## 研究假设

H1：环境变化和 Agent 间干扰会使“最终状态正确率”高估真实可部署性；加入按时和过程安全指标后，方法排序会发生变化。

H2：固定周期全局重规划在低干扰任务上浪费推理，在高干扰任务上又可能来不及完成；事件触发的选择性修复可以在相同模型预算下提高按时成功率。

H3：只检查同一设备的冲突会漏掉通过共享环境变量产生的间接冲突，例如加湿／除湿同时作用于湿度；使用语义资源 footprint 后，错误并发会减少。

H4：把慢 LLM 从首次物理动作的关键路径移出，配合预授权本地策略，可以改善 P95/P99 首次有效动作延迟；它不能保证任意陌生自然语言请求都在 1 秒内正确完成。

## 形式化对象

每个任务 (i) 至少记录：释放时间 (r_i)、截止时间 (d_i)、优先级、目标、前置条件、后置条件、资源读写集合、可取消／可补偿属性、预计执行和验证时间。

每个正在执行的计划还记录：产生时的状态版本、依赖的设备和环境变量、已完成动作、在途动作、租约或权限版本、可接受的状态漂移范围。

运行时在复用、局部修复和全局重规划之间选择。选择目标可以写为：

\[
m^*=\arg\max_m P(\text{在 }d_i\text{ 前正确达成目标}\mid s_t,\text{在途动作},\text{剩余时间},m)
\]

候选动作必须先通过权限、安全不变量、资源冲突和状态版本检查。概率估计应由带真实耗时标签的历史轨迹校准，不能直接使用 LLM 自报置信度。

## 环境与任务

第一阶段基于 SimuHome 或等价 Home Assistant 测试床，增加：

- 连续任务到达和不同优先级；
- 设备操作依赖和共享环境变量；
- 推理、通信、设备反馈和验证延迟；
- 中途用户改意图、设备离线和并发 Agent 动作；
- 可行、不可行、需要澄清和不可安全执行的请求。

每条轨迹在模型思考时继续推进环境，不能冻结世界等待 LLM 返回。

## 必须比较的基线

1. Home Assistant 规则＋确定性 Skill＋优先级／最早截止时间调度。
2. 单主 Agent＋确定性执行器。
3. 固定快／慢模型路由＋相同缓存和安全检查。
4. 事件触发全局重规划。
5. LLMCompiler／Agent JIT 风格的计划并行执行适配。
6. 选择性修复方法的消融：去掉状态版本、去掉局部修复、去掉截止时间、改为固定阈值。

所有方法应使用相同模型、设备信息、工具权限和总预算，避免把额外的安全检查误算成算法增益。

## 指标

- 首次有效物理动作延迟：中位数、P95、P99；
- 按时任务成功率；
- 最终任务成功率；
- 资源／互斥冲突率、过程安全违反率；
- 计划过期率和状态版本拒绝率；
- 重规划次数、局部修复范围、LLM 调用次数和成本；
- 不可行请求的正确拒绝率；
- 低优先级任务的饥饿时间。

紧急事件应单独报告“事件检测时间”和“预授权动作时间”，不得与普通复杂请求混为一个平均延迟。

## 近期四周验证门槛

第一周：建立单主 Agent、确定性执行器和分段延迟日志。

第二周：实现强规则基线，测量其在现有项目场景中的覆盖率和失败边界。

第三周：加入任务插入、状态漂移、资源互斥和跨 Agent 干扰，比较全局重规划、固定周期重规划和局部修复。

第四周：加入剩余时间选择器，在不同模型、负载和家庭配置上做重复实验，报告置信区间和失败案例。

如果强规则基线已解决所有 MVP 场景，应把研究集中到它解决不了的动态组合任务，而不是仅增加更多家电名称。
