# HomeCoord-Bench 截止时间可行性与基线覆盖复核

日期：2026-09-26  
阶段：数据结构／调度下界审计；设备工作量仍是未校准假设。

## 为什么先做可行性检查

若任务在理想调度下都无法赶上期限，就不能把失败归因于多 Agent 协调。反过来，理想可行也不代表真实在线执行能按时，因为模型提案、网络、设备启动确认、传感器反馈及状态同步都可能消耗时间。这里先用动作声明的持续时间、功率、任务释放时刻和家庭总功率上限检查最基本的物理排程下界。

## 审计范围与结果

当前 34 条 episode 中，仅 2 条包含明确完成期限，共 4 个任务；两条是同一 EV／热水器任务模板在冲突与无冲突容量下的配对条件。审计穷举每条 episode 的全部任务执行顺序，假设动作在任务释放时立即可执行、不可抢占，只检查总功率上限。

| Episode | 功率上限 | 截止期限下可行顺序 | 机器结论 |
|---|---:|---|---|
| `HC-PHYSICAL-V2-EV-WATER-CONFLICT` | 6.0 kW | 仅 `charge_ev → heat_water` | 顺序敏感 |
| `HC-PHYSICAL-V2-EV-WATER-CONTROL` | 7.2 kW | 两种顺序均可行 | 容量充足时顺序不影响期限可行性 |

冲突条件下，EV 从 20% 充到 50% 的假设工作量为 5 小时，期限为 5 小时 20 分；热水从 35°C 加热到 50°C 的假设工作量约 38 分 46 秒，期限为 6 小时。6.0 kW 下 4 kW 充电和 3 kW 加热不可同时进行。先充 EV 时两任务都可按时完成；先加热再充 EV 会使 EV 超过其期限。7.2 kW 对照允许并发，两种执行次序都可行。

这些数值与先前的 5 次固定模型提案回放相符：仅一组出现热水提案更早返回，安全的容量感知优先级规则把充电排在前面并按时完成。它证明当前合成样例有一个可解释的次序边界，同时也再次说明普通规则可以解决该样例。

## 截止时间基线覆盖

当前确定性事件矩阵有 34 条 episode × 5 种策略 = 170 次运行：`CentralSingleAgent`、`IndependentMultiAgent`、`RuleCoordinator`、`ConstraintCoordinator` 和 `DeadlineAwareCoordinator`。固定 DeepSeek 专家提案的 224 次回放比较了后四种策略；没有把专家 Agent 提案直接塞给中央 Agent，因为中央架构需要单独生成自己的提案，否则信息与调用预算不公平。C3 另有 40 条在线规则回放，包含立即 FIFO、已发布任务优先级、EDF、容量感知优先级；截止时间敏感性批次共 200 次固定提案离线回放，覆盖两个容量条件、五档 EV 截止时间与四种策略，均未新增 API 调用。

在 310／320 分钟的合成 EV 期限压力档，等待截止时间优先提案的 `DeadlineAwareCoordinator` 将低容量条件下的按时、安全完成从 ConstraintCoordinator 的 4/5 提升到 5/5；高容量条件下两者都是 5/5。另一个五次重复的维度自洽假设试验中，容量感知优先规则也在全部五次完成。高容量对照显示，未看资源容量的等待规则可能无冲突也多等；容量感知规则能避免这部分等待。所有期限档和设备工作量仍是研究者设定的合成情境。

强基线已比“只和不协调 Agent 比”更完整，但模型架构公平性和实际开销仍缺口：中央单 Agent 尚无自己的同任务模型提案批次；已保存的 DeepSeek API 请求是顺序发出后按记录时延离线重放，不是真实并发；170 条事件矩阵运行里，规则协调计算延迟数值记录为 0 条。因此目前可比较决策策略对相同提案的影响，不能声称测到了协调器真实墙钟成本或中央／多 Agent 的公平模型优势。可复核计数见 `homecoord_bench/results/baseline_coverage_audit_20260926.json`。

## 数据就绪度复核

候选任务机器审计的状态为“仅自动标记，不是人工审核”。20/20 候选任务未双审、未校准、没有显式完成期限，也没有 `tool_catalog` 可供模型查看可调用动作签名；5 条 C2 候选任务的环境效应尚未进入运行时状态更新，4 条 stale-state 候选任务还可能在 Agent 执行之前就被外部事件满足总目标。现有 68/68 DryRun 提案能找到 episode grounding，只证明 deterministic client 与动作表一致，不能证明模型工具接口充分，也不能证明物理语义正确。

因此下一批数据整理先补齐接口，而不是给 20 条任务机械添加期限：每个 Agent 的请求应展示真实可调用动作、目标与参数类型，至少包含两个合理选项；以盲测方式隐藏 `required_action` 和 `action_template`；随后由领域人员审核每条任务和配对对照的效果时点、功率／工作量、优先级、期限与安全标签。机器检查和模型试跑应分别报告，双审状态未完成前维持 candidate 标记。数据字段要求已补充到 `docs/HOMECOORD_BENCH_DATA_SPEC.md`。

## 虚拟环境采用决策

当前 HomeCoord 已有离散事件协调实验台，足以检查提案到达、事件排序、冲突规则和 deadline 计算；它不是完整家庭物理模拟器。SimuHome 的状态、设备与温度动力学可作为独立后端候选，但静态审查显示它没有原生多 Agent 异步队列、家庭总功率约束和通用突发事件注入，不能原样覆盖当前 C3／C4 episode。仓库声明 CC BY-NC-ND 4.0，当前可用隔离 Python 为 3.12.14，而审查版本要求 3.13 及以上；本轮没有运行上游代码。

因此不从零重建第二套“全屋模拟器”，也不把当前离散事件台当作真实环境证据。继续用它验证协调时间线；若完成运行时与许可核查，再以薄适配器做 SimuHome HVAC 的状态／温度试点，并保持结果与本地 C3 合成实验分开报告。只有当适配试点证明温度动力学或其他缺失机制对论文结论不可替代时，才扩建家庭动力学。

## 解释边界

1. 两个 episode 不是两类独立任务，而是同一任务模板的冲突／对照；4 个 deadline-bearing tasks 不能算作 4 个独立样本。
2. 5 小时充电和约 39 分钟热水加热由电池容量、功率、效率、体积和比热等假设推得，尚未由具体设备规格或测量校准。期限是压力条件，不是用户需求分布。
3. 审计的“立即就绪”是假想下界，不含 LLM 延迟、适配器／协调开销、设备响应或传感器反馈。只有审计发现不可能的期限时，才可据此排除；通过不能认证线上可行性。
4. 当前 20 条候选任务没有完成期限。期限扫描生成的合成副本只做敏感性分析，不能扩充原始 benchmark 的审核覆盖数。
5. 当前动作物理效果和长动作启停阶段仍需领域人员复核；26 个至少 1 秒的动作尚未显式标注启动态／完成态分相。

## 可复跑方法

`python homecoord_bench/audit_deadline_feasibility.py` 会写入 `homecoord_bench/results/deadline_feasibility_audit_20260926.json`。统一离线入口 `python homecoord_bench/run_event_pilot_suite.py` 也会重建该报告。审计器报告零网络调用；其单测检查当前冲突／对照的可行顺序，并确保极短期限被识别为不可行。

## 下一步数据门槛

新增 deadline episode 前，先记录目标完成定义、任务释放时刻、设备可见额定功率／工作量来源、硬期限来源、不可抢占与可取消属性，并运行这个下界审计。冲突条件需要配对无冲突控制；至少由两名评审独立核对任务目标、动作语义、期限可行性和冲突标签，分歧留记录。现有强基线应作为每条 episode 的预先比较项；若 EDF／容量感知规则已经解释结果，就把它报告为 benchmark 发现，而不是为制造方法缺口改规则或收紧期限。
