# C3 厨房任务匿名输入复现

日期：2026-09-30。状态：探索性跨结构复现；不是独立留出集、正式 benchmark 冻结或现实家庭抽样。运行前设计见 [`C3_KITCHEN_ANON_REPLICATION_PREREG_2026-09-30.md`](C3_KITCHEN_ANON_REPLICATION_PREREG_2026-09-30.md)。

## 采样与盲化

在先前看过的厨房三 Agent 结构上，对烧水、烤箱和洗碗 Agent 各并发调用 DeepSeek 三批，共 **9 次 Agent 请求**。9/9 返回有效的工具动作，没有协议错误或失败重试。三批并发完成顺序都不同：

| 批次 | 并发完成顺序 | 批次墙钟 |
|---:|---|---:|
| 1 | 洗碗机 → 烤箱 → 水壶 | 1511 ms |
| 2 | 洗碗机 → 水壶 → 烤箱 | 1398 ms |
| 3 | 烤箱 → 水壶 → 洗碗机 | 1505 ms |

实际 API 日志记录 9 次成功、0 次失败，合计 **9480 输入 token、1197 输出 token**。发给模型的请求使用匿名 episode ID；容量压力值、总容量、其他任务 ID、全局目标、全局约束、`required_action` 和 `action_template` 均未出现在 9 份请求中。逐份请求记录保存在结果 JSON 里。模型只看本地任务和设备信息，所以这些调用检验的是本地任务提案，不检验模型是否能推理共享容量。

## 36 次配对回放

每批真实提案及其并发返回时延，分别回放到 `ρ=0.8/1.2/1.6` 和四种策略中。表内是全部任务按时完成的批次数／总批次数；“服务”另外报告，以免把安全门控拒绝误当成安全违规。

| 资源压力 | 独立执行 | 约束调度 | 等齐已发布提案 | 容量感知期限规则 | 首个安全动作：立即／等齐中位数 |
|---:|---:|---:|---:|---:|---:|
| 0.8 | 3/3 按时；3/3 全部服务 | 3/3 按时；3/3 全部服务 | 3/3 按时；3/3 全部服务 | 3/3 按时；3/3 全部服务 | 1427 / 1605 ms |
| 1.2 | 0/3 全部服务 | 2/3 按时；3/3 全部服务 | 3/3 按时；3/3 全部服务 | 2/3 按时；3/3 全部服务 | 1427 / 1605 ms |
| 1.6 | 0/3 全部服务 | 0/3 按时；3/3 全部服务 | 3/3 按时；3/3 全部服务 | 3/3 按时；3/3 全部服务 | 1427 / 1605 ms |

在 `ρ=1.6` 下，容量感知规则的首次安全动作中位数为 **1539 ms**；表格最后一列只比较立即执行与等齐提案。

资源宽松时，所有策略都按时完成；等齐没有成功率收益，首次安全动作中位数增加 **178 ms**。在 `ρ=1.2` 下，等齐三批都按时完成，而约束调度和容量感知规则各有一批超期；两种规则最终仍服务了全部任务。在 `ρ=1.6` 下，约束调度三批最终都服务全部任务，但三批都至少有一个任务超期；等齐和容量感知规则均为 3/3 按时。独立执行出现的服务损失是共同安全门控拒绝超容量动作，不表示系统实际执行了危险操作。

## 对研究问题的意义

这是一次跨设备和期限结构的复现：匿名提示下，真实模型仍能提出有效动作，三批响应次序不同；固定这些提案后，低负载下等待造成可测的首动作延迟，高负载下调度方式改变按时完成结果。它为“协调价值随条件变化”再添一组真实并发提案证据，也说明结论不是某个手工指定返回顺序的产物。

本轮不能证明普遍规律。厨房结构在此前已有脚本回放和 API 试点，因此这不是未见测试；三批都来自同一任务结构，统计独立样本仍只有很少几组；三档容量是受控管理预算；同一批模型提案跨压力档回放，不能解释为模型对每个容量条件分别作出的反应。容量感知规则也并非始终更差：在最高压力档它与等齐都完成了全部期限任务，首动作稍早。
