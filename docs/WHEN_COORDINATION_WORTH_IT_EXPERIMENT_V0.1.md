# HomeCoord-Bench：如何评测“何时值得协调”

日期：2026-09-27。状态：实验设计与 C1/C3 合成边界探针；不宣称已经找到家庭部署规律，也不改变“冲突—时延 benchmark”的主线。

**后续口径更正：** 本页探针里的 `safe_process_rate` 实际取自 `process_valid_success`，该字段包含最终家庭目标是否达成，并非纯过程安全率；表中“全任务服务率”另由必要动作服务计算。“平均完成”取自最终家庭目标达成时间，并非全部 Agent 必要动作完成时间。不能用这两列单独判断“何时值得协调”。共同安全门控、逐任务完成时间和后续实验协议见 `docs/C1_C3_REVIEW_AND_SHARED_GATE_PILOT_2026-09-27.md` 与 `docs/WHEN_COORDINATION_WORTH_IT_EXPERIMENT_V0.2.md`。

## 现有实验回答不了什么

此前 9 条 C1/C3/C4 草稿只测试了少量固定的冲突／安全条件；五种策略共用 300 ms 固定提案延迟，协调决策本身没有独立计时；三次重复是完全相同的确定性轨迹。C2 的连续物理探针单独运行。因此现有结果能说明“有些冲突可被解决且会带来等待”，不能从中估计冲突出现频率、协调调用成本，或判断某条件下应选独立执行、快速规则还是完整协调。

## 把问题变成可测量的比较

对同一批任务和模型提案，在条件 `x` 下比较三种决策：直接执行、快速规则检查、完整约束协调。`x` 先只包含两个实验变量：**冲突是否会出现**及**提案返回后协调额外耗时**。之后再分别增加状态变化和物理模型误差，不一次塞入所有前提。

每个条件同时报告四项结果：①全部必要任务完成且过程中无安全／资源违反的比例；②首次安全物理动作的延迟；③全部任务完成时间和必要服务率；④协调推理、查询和模型调用成本。C2 另报告能耗。不能只凭“冲突数下降”宣布某策略更好，也不把安全、时间、能耗预先揉成一个任意加权总分。

“值得”采用可审查的判据：给定事先声明的安全要求和响应预算，某策略应完成更多有效服务；若两种策略的有效服务相同，则选择时延和开销更低者。论文应给出不同安全要求／响应预算下的策略前沿，而不是只给一个最佳策略。条件切换器也应与“始终使用强规则”和“始终协调”比较；它只能读取运行时真实可见的信息，不能偷看数据集的冲突标签。真实家庭中的冲突频率未知时，先把频率作为敏感性参数，不假称已经估计其分布。

## 已做的第一轮设计探针

脚本 `homecoord_bench/probe_coordination_activation_boundary.py` 复用 C1、C3 的冲突／安全配对和固定提案。独立执行无额外协调耗时；RuleCoordinator 与 ConstraintCoordinator 在提案返回后分别增加 0、100、300、800 ms 合成决策耗时，虚拟环境在此期间继续前进。共 36 个实际仿真单元；再将冲突臂与安全臂按假设占比 0%、25%、50%、75%、100% 做 90 个数学混合结果。这些占比**不是** 90 个新任务，更不是家庭冲突发生率。

例如假设两类配对各占一半、额外协调耗时为 300 ms 时：

| 机制 | 策略 | 过程安全成功率 | 全任务服务率 | 平均首动作 | 平均完成 |
|---|---|---:|---:|---:|---:|
| C1 同设备 | Independent | 0.50 | 1.00 | 400 ms | 6400 ms |
| C1 同设备 | Rule / Constraint | 1.00 | 1.00 | 700 ms | 6700 ms |
| C3 容量 | Independent | 0.50 | 1.00 | 400 ms | 3500 ms |
| C3 容量 | Rule | 0.50 | 1.00 | 700 ms | 3800 ms |
| C3 容量 | Constraint | 1.00 | 1.00 | 700 ms | 4250 ms |

这组结果说明评测设计可以分别呈现“安全收益”和“协调代价”：C1 的简单设备规则已经足够；C3 的设备锁规则没有识别共享容量，完整约束检查才增加过程安全成功率。**这不证明 C3 需要 LLM 或复杂协调算法**，因为把已知容量规则加入确定性调度器也能解决它。Independent 是诊断下界，不能作为容许已知安全风险的部署选项；正式比较应让所有方法先经过相同的最低安全门控，再问额外协调能否减少无谓拒绝、改善任务服务或缩短等待。上述数字来自每类仅一对合成任务、固定提案和人为设置的 300 ms 额外耗时，只是方法学验算，不能用于推断真实家庭的选择边界。

## 达到论文证据需要补齐的实验

1. 冻结经过独立审核的代表任务，给每种机制制作多条任务和匹配控制。C1 可以改变请求重叠程度，C3 改变容量余量；每次只改变一个关键因素。避免用“同一任务跑三遍”充当样本量。
2. 记录同一模型在相同工具、权限和观察边界下的真实提案、失败与时延。固定提案回放继续用于因果对照；真实提案用于检验自然语言理解和调用质量。单主 Agent＋执行器必须是基线。
3. 让各方法共享同一个最低安全门控，并补上包含设备互斥、共享容量与状态前提的强确定性规则基线。独立测量规则、额外协调和模型判断各自的处理时间，连同设备反馈时间进入事件时钟。若强规则的额外耗时接近零且服务已近饱和，“何时启动更复杂协调”就可能没有有意义的取舍，应如实报告。
4. C2 保持独立连续环境子集，先审核／校准换气和热模型，再研究“立即制热、等待关窗、依据不确定模型选择”在时间和能耗上的取舍。C4 在缺少停机与恢复契约时，只能评测状态失效及服务损失，不能声称研究了局部修复的价值。
5. 在多个任务、环境参数和模型提案上重复，报告各条件的过程安全、服务、首动作与完成时延分布及置信区间。若强规则在可信条件下始终占优，这就是 benchmark 的实证结论；不能人为补一条让它必败的规则缺口。
