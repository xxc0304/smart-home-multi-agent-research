# C1 SimuHome 交叉检查与 C3 项目资料来源审查

日期：2026-09-28。状态：本地技术核查；未调用模型 API、未连接真实设备、未更新 GitHub。

## C1：修正动作生命周期并检查设备状态

检查新版 C1 时发现：最初的 `cool` 动作在完成时仍写回“设备处于制冷”，会把其他 Agent 先前发出的关机覆盖。这不是物理设备的可靠语义，可能让终态评分因实现方式而失真。生成器已改为：`cool` 在启动时将设备置为制冷，动作完成时不重写设备；住户的制冷请求在合成的第 6 秒由独立外部事件结束。此前 29°C→24°C 的瞬时室温效果继续排除。能源 Agent 只接收自己的节能任务和空调状态，不接收另一个 Agent 的制冷请求及全局舒适约束；共享协调层持有跨任务规则。这一信息边界是待审核的实验设定，不能当成现实系统必然如此。此任务的 `task_service_rate` 只能表示必要命令被执行，不能证明住户获得了足时的热舒适。

对 C1 重叠／非重叠两条任务，各用无协调与约束协调策略产生固定动作轨迹。它们仍是 `DryRunClient` 提案，未采样 LLM。HomeCoord 中，重叠组的无协调执行在制冷需求尚有效时提前关机，`final_goal_success=True` 但 `process_valid_success=False`，并记录 5699 ms **合成事件钟上的**约束违规；约束协调将关机排在服务窗口后，过程有效。非重叠对照两种策略均有效。这说明只看最终目标会漏掉过程错误，但合成 5699 ms 不能称为真实家庭危险暴露时间。

随后将 HomeCoord 的“早关机／晚关机”**符号映射**为 SimuHome 工作流：制冷在模拟第 1 秒执行，早关机在第 2 秒，晚关机在第 8 秒。中间第 3.5 秒和末尾第 9.5 秒回读空调状态。两条 episode × 两种策略 × 两次相同配置技术重复，共 8 条本地回放，**8/8 符合命令状态预期**：早关机组中间空调关闭；晚关机组中间保持开启；末尾均关闭。两项工作流均完成。结果在 [`provenance_c1_simuhome_20260928.json`](../homecoord_bench/results/provenance_c1_simuhome_20260928.json)，可复跑脚本在 [`replay_provenance_c1_to_simuhome.py`](../homecoord_bench/simulator_adapter/replay_provenance_c1_to_simuhome.py)。上游固定版本是 `83d28837b69f0cbf1bc02ed5334cb8b561a9d54d`。

此回放**只验证设备命令状态和顺序的外部后端一致性**。符号映射没有保留 HomeCoord 的 301/6101 ms 与 SimuHome 秒数的量纲等价；两次是技术重复，不是独立家庭。SimuHome 温度原始值仅作诊断，不计热舒适成功、真实制冷速率、模型协调时延或 1 秒部署响应。SimuHome 没有替 HomeCoord 提供多 Agent 协调真值。

## C3：现有项目材料没有共享容量真值

只读检查了最初提供的《家庭微脑技术方案0814》《家庭智能中枢2026年下半年工作方案明细》《家庭智能中枢技术开发与预研任务及技术方案V1.0》《课题智慧家庭任务清单》，并补查本地两份设备／执行 HTML 和伴学台灯材料。没有找到可以定义当前 EV／热水器任务的**某一住宅或受控回路容量、断路器、充电桩型号、热水器型号、同步负载轨迹**。任务清单描述多 Agent 编排和设备接入目标，不是家庭配电记录。伴学台灯调研中有某款产品整机 14–18 W 的资料，反而说明旧草稿的 0.5 kW 书房灯不能被当成普通台灯实物。

新版 C3 的 40 美制加仑／单根 3.8 kW 元件有公开产品规格锚点；但一次加热启用几根元件、4.0 kW 充电档位、60 kWh 车辆、负载预算 7.0／7.8／9.0 kW、恒定负载和加热效率都没有这户家庭的记录。**C3 目前只能标为“部分规格锚定的合成托管负载预算实验”**，不能升级为现实家庭容量样本。公开美国产品资料也不能替代中国项目设备档案。

正式 C3 若要有物理解释，需先指定容量的实施点（主进线、分支回路或能源管理器设定值），取得相应额定值／配置记录，再对应具体负载型号或一段带时间戳的功率轨迹。没有这些资料仍可评“给定容量约束下的在线调度机制”，但不能推断真实家庭中容量冲突的频率或能耗收益。下一轮数据扩充应区分这种机制子集与有设备依据的子集，不把两者混作同一现实分布。
