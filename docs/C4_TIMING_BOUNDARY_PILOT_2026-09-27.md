# C4 状态变化与动作提交边界试验

日期：2026-09-27  
状态：M16–M20 的确定性机制试验已完成；这是合成时延下的执行语义诊断，不是物理或模型性能结果。

## 设计

选取 HC-M16–M20 五条状态变化候选任务，比较 `IndependentMultiAgent`、`RuleCoordinator`、`ConstraintCoordinator` 与 `DeadlineAwareCoordinator`。通过 DryRunClient 分别注入 300、400、600 ms 提案返回延迟；环境状态事件在 500 ms 发生，模拟器默认设备命令延迟为 100 ms。每个单元重复 3 次，共 5×4×3×3 = 180 次离线运行、60 个配置单元。三个延迟值是人为构造的边界条件，不是模型 API 延迟；没有调用模型 API 或真实设备。

因此前三种延迟对应：动作计划约在事件前 100 ms 开始、与事件同一虚拟时刻开始、事件后 200 ms 开始。同一时刻的外部状态更新先于动作开始事件处理。`DeadlineAwareCoordinator` 只等待已经发布任务的提案；它不会预知尚未发布任务或未来环境事件。

## 结果

三个固定重复均逐项完全一致：60/60 个重复组确定性一致。

| 提案延迟 | 普通三种策略的主要动作 | DeadlineAware 的主要动作 | 安全／目标表现 |
|---:|---|---|---|
| 300 ms（动作约 400 ms 开始，状态事件前） | 五个候选的主要动作都开始；状态随后变化，动作无法中止，五个任务均出现过程问题 | M16、M18–M20 等已发布任务的迟到提案使调度器等待，之后动作因前提失效而被拒；M17 的灌溉仍在未来降雨事件前开始 | Independent、Rule、Constraint 各 15/15 次过程无效；DeadlineAware 为 6/15 次：3 次 M17 出现过程安全违规，3 次 M16 未完成清洁。M18–M20 的目标又都被事件直接满足。 |
| 400 ms（动作预定在 500 ms 开始） | 外部事件先处理，失效前提使主要动作被拒绝 | 同样拒绝；等待批次不会改变前提检查 | 四种策略均无过程安全违规；各有 3/15 次 M16 清洁目标未完成。M17–M20 虽目标判为成功，但主要任务均未服务。 |
| 600 ms（动作约 700 ms 开始，状态事件后） | 主要动作因失效前提被拒绝 | 同样拒绝 | 与 400 ms 边界相同。 |

这 180 次运行的 `conflict_counts.C4` 全部为 0。原因是当前 C4 计数针对“带失效前提、仍被执行的动作”；状态变化后的拒绝记在 `precondition_violations_at_start`，中途变化导致的危险状态记在过程约束违规指标，而没有归入 C4 冲突数。对 M17–M20，在动作被拒后，最终目标仍会被外部事件满足；因此只看 `final_goal_success` 会把未服务任务算成成功。相同条件下必须同时报告目标成功、必要动作服务、失效提案拒绝和过程安全。

## 指标拆分后的复核

我在离散事件运行时中补充了三项生命周期指标，并按同一设计再次运行 180 次；候选 episode 未改动。每格汇总 5 条任务 × 3 次重复（15 次运行）：

| 提案延迟 | 策略 | 启动前过期拒绝 | 在途前置条件失效 | 在途期间安全状态转坏 |
|---:|---|---:|---:|---:|
| 300 ms | Independent / Rule / Constraint（各自） | 0/15 | 15/15 | 15/15 |
| 300 ms | DeadlineAware | 12/15 | 3/15 | 3/15 |
| 400 ms | 四种策略（各自） | 15/15 | 0/15 | 0/15 |
| 600 ms | 四种策略（各自） | 15/15 | 0/15 | 0/15 |

“在途前置条件失效”按每个动作最多计一次；“在途期间安全状态转坏”仅表示安全约束在一个动作仍运行时从满足转为不满足，可由外部事件或动作完成触发，不据此作单独因果归因。`conflict_counts.C4` 仍为 0，因为这批动作要么被拒绝，要么在有效前提下启动；新指标说明 0 个已执行的 stale action 并不等于没有 C4 生命周期问题。

300 ms 下，普通三种策略均有 15 个在途前置条件失效和 15 次安全状态转坏；DeadlineAware 的数值为 3。这里的改善来自它对当时已发布提案的等待／排序，且 M17 的灌溉仍在降雨前启动，因为降雨是未来外部事件，协调器并不知情。400／600 ms 下，所有策略均在动作开始前安全拒绝 15 个过期主动作，但必要动作没有被服务；这应呈现为“避免失效执行、任务未服务”，而非成功完成。四种策略在 400／600 ms 的 `final_goal_success` 均为 12/15，其中 M17–M20 的目标可由事件本身满足；任务服务率必须与目标成功率并列。

为避免这一类目标泄漏只靠 M16–M20 的手工分析发现，我新增了全数据审计 `audit_external_goal_credit.py`：当前 34 条 episode 中，0 条仅凭初始状态满足所有目标，4 条会在不执行 Agent 动作时被外部事件满足所有目标（HC-M17–M20），其余 30 条不会。该审计由离线主套件运行并保存到 `homecoord_bench/results/external_goal_credit_audit_20260927.json`；“会被外部事件满足”不自动表示任务设计错误，但必须将环境完成与 Agent 服务分开计分。

## 这批试验说明什么

当前候选能区分两种不同的动态故障：

1. **动作提交前状态已变化。**所有架构都使用动作前提检查，因而会拒绝基于旧状态提出的动作。这个保护本身不是协调算法的独有优势；代价主要表现为必要动作未服务。现有 C4 冲突计数没有把安全拒绝计作冲突或代价。
2. **动作开始后状态才变化。**起始时前提有效的动作会继续运行，简单 ConstraintCoordinator 不会中断或重验在途动作，状态事件可使其在完成时造成约束违规。已发布任务都到齐时，DeadlineAware 有时通过等待避免该动作；但 M17 显示，若触发事件对应的第二任务尚未发布，等待策略仍会过早开始浇水。

这比简单地把“过期动作”统称为 C4 更清楚，也给了后续候选任务一个可检验的机制。但它仍不足以证明新的局部修复算法必要：目前比较的是现有策略行为；低延迟情形下的 DeadlineAware 改善部分来自等待当前已发布提案，而不是理解或预测未来状态变化。M17–M20 的事件目标还让任务完成率失真，所有任务仍未双审。

## 后续数据与指标修订建议

- 把 `stale_at_commit`（状态更新后、动作尚未开始时的拒绝）与 `invalidated_in_flight`（动作已开始后受到状态变化影响）分开报告，不把两者都压进单一 C4 计数。
- 对两种情况分别记录必要动作服务率、拒绝原因、首次有效动作、截止时间、约束违规持续时间和完成／补偿动作。若状态事件本身已满足家庭目标，另报 `external_event_only_goal_success`，不能计作 Agent 服务成功。
- 为在途动作增加可取消性、可中止延迟、补偿动作和恢复目标；否则 benchmark 只能说明已有执行器的监测缺口，无法比较局部修复。
- M17 的关键边界要同时有无降雨配对，且降雨不能单独满足唯一目标；M16、M18–M20 需要无住户事件控制与必要动作目标。
- 注入的 300/400/600 ms 只用于定位边界。之后应用真实模型时延分布或公开、可复现实延数据重跑，仍不得把这些合成值当部署延迟。
