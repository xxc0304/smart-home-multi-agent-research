# HomeCoord-Bench 20 条任务候选目录 v0.1

状态：候选任务目录，尚未进入金标准集合。每条任务都需要经过人工双审、动作可执行性检查和确定性回放验证后，才能生成正式 episode。

当前进度：HC-M01–HC-M20 已完成首版 episode 与确定性四架构回放，状态为 `candidate_dry_run`；20 条任务均未完成物理参数校准和人工双审。

## 1. 目录目标

当前实验已经证明四类冲突能够被程序化评测，但主要依赖 4 条种子任务。下一轮将任务覆盖扩展到 20 条，同时保持核心问题不变：

> 多个专业 Agent 异步作用于动态共享家庭环境时，协调机制减少动作冲突需要付出多少响应时延和任务效用？

目录按 C1–C4 各放置 5 条候选。每组内部改变设备、房间、Agent 目标或外部事件，避免把结论绑定到“空调—开窗—扫地机器人”这几个固定对象。任务中的时间、功率和阈值均是待校准占位值，不是最终标准。

## 2. 20 条候选任务

|---|---|---|---|---|---|---|
| HC-M01 | C1 直接设备 | 舒适 Agent 请求客厅制冷；能源 Agent 请求关闭空调 | `living_hvac` | 两任务释放间隔与返回顺序变化 | 舒适请求有效时不能强制关闭；两任务都记录 `required_action` | 同一设备上的目标冲突与优先级协调 |
| HC-M02 | C1 直接设备 | 阅读 Agent 打开书房阅读灯；节能 Agent 关闭书房灯 | `study_light` | 阅读任务有短截止时间；节能任务异步到达 | 阅读模式生效时不能被关闭；灯光动作必须可验证 | 局部策略可见性是否能减少直接写冲突 |
| HC-M03 | C1 直接设备 | 隐私 Agent 关闭卧室窗帘；采光 Agent 打开窗帘 | `bedroom_blinds` | 用户进入事件改变隐私优先级 | 用户在卧室时不得自动打开；两个动作有不同优先级 | 同一执行器的互斥操作和用户状态变化 |
| HC-M04 | C1 直接设备 | 安防 Agent 锁门；到家 Agent 解锁入口门 | `front_door_lock` | 到家事件可能在锁门提案返回前到达 | 已确认住户到家时不得保持锁定；解锁动作需记录权限 | 安全动作与便利动作的冲突协调 |
| HC-M05 | C1 直接设备 | 热水 Agent 加热；峰值削减 Agent 关闭热水器 | `water_heater` | 峰值窗口和洗浴截止时间重叠或错开 | 洗浴截止前必须完成最低水温；峰值策略不能取消高优先级任务 | 具有截止时间的优先级冲突 |
| HC-M06 | C2 间接环境 | 空气质量 Agent 开窗；气候 Agent 制热 | 室温、CO2、`window`、`heater` | 开窗与制热释放间隔连续变化 | 室温不能低于安全下限；两个任务的必要动作分别记录 | 不同设备通过环境变量产生反向影响 |
| HC-M07 | C2 间接环境 | 空气质量 Agent 开窗；制冷 Agent 降温 | 室温、CO2、`window`、`living_hvac` | 用户要求在截止时间前降温 | 降温期间开窗超过重叠阈值标记 C2 | 间接冲突是否依赖动作重叠而非设备相同 |
| HC-M08 | C2 间接环境 | 加湿 Agent 启动加湿器；防霉 Agent 启动除湿器 | 湿度、`humidifier`、`dehumidifier` | 湿度传感器在两次提案之间更新 | 湿度必须保持在安全区间；同时运行视为环境浪费或目标反向 | 共享连续环境变量上的异步竞争 |

## 3. 任务准入与审核表

每条候选任务进入正式数据集前，需要逐项回答以下问题：

1. 是否至少有两个具有不同可见状态、工具权限或目标的 Agent？
2. 是否存在一个可明确定位的共享设备、环境变量或资源容量？
3. 是否能写出初始状态、任务释放顺序、外部事件和延迟配置？
4. 是否至少有一个合理基线会失败，而且失败不是因为故意隐藏了必要信息？
5. 成功条件能否用状态表达式验证，而不是依赖 LLM 主观打分？
6. 冲突是否能由设备能力表、效果模型或状态版本规则自动判定？
7. 每个任务是否声明了必要动作，从而能计算任务服务率？
8. 是否有正向轨迹、冲突轨迹和恢复轨迹三类可回放样本？
9. 动作的持续时间、功率和反馈延迟是否有来源或明确的待校准标记？
10. 是否不包含真实家庭的个人隐私信息？

一条任务只有在双人审核通过、确定性评测器能区分至少两个基线、并完成一次 dry-run 回放后，才能从 `candidate` 变为 `manual_template`。如果任务需要新增冲突类型或新的评测语义，应先单独扩展协议和评测器，不直接混入本轮 20 条任务。

## 4. 实施顺序

第一批优先实现 HC-M02、HC-M03、HC-M07、HC-M08、HC-M12、HC-M13、HC-M17 和 HC-M20。它们分别覆盖灯光、窗帘、空调、湿度、洗烘、电动车、天气和安防，比现有 4 条种子任务拥有更大的设备与环境变化，同时仍可以映射到 C1–C4。

实现每条任务时，先完成确定性环境能力表、正向和反向轨迹，再接入真实模型。先扩展任务和评测器，后比较模型；不要用新增任务上的单次模型运行直接替代人工审核。

## 5. 与普遍多 Agent 问题的对应

智慧家庭只是可回放的物理载体。20 条任务分别把以下可迁移问题具体化：

| 家庭约束 | 可抽象的多 Agent 问题 |
|---|---|
| 同一设备互斥写入 | 共享资源上的并发提交与优先级协调 |
| 设备通过温度、湿度等变量互相影响 | 非显式依赖下的间接冲突检测 |
| 家庭功率、插座和并发数有限 | 多任务资源容量分配 |
| 住户、天气和传感器持续变化 | 过期计划、状态版本和局部修复 |
| 洗浴、做饭、回家等时间要求 | 截止时间下的任务效用与安全权衡 |

正式论文中应先以家庭任务报告结果，再用这些映射说明问题为何可以迁移到机器人编排、边缘设备控制和其他动态多 Agent 环境；不能仅凭任务名称宣称已经完成跨场景泛化。
