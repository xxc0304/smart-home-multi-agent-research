# HomeCoord-Bench 候选任务取舍筛查

状态：设计筛查；不是正式 benchmark 结果。20 条候选任务仍为 `candidate_dry_run`，尚无独立双人审核或真实设备参数校准。本文所有新运行均使用确定性 `DryRunClient`，未调用模型 API。

## 要回答的问题

现有 20 条任务能否证明：在满足过程安全的前提下，不同协调机制仍须在响应时间、按时完成和任务服务之间做出非平凡取舍？

筛查时同时观察 `process_valid_success`、`task_service_rate`、首个有效动作和任务完成时间。若强规则基线在全部任务上安全通过，且与其他安全基线相比不在任务服务或时延上明显落后，当前候选集就不足以支撑“强方法仍有协调缺口”的结论。无协调架构的快速但不安全结果，只能建立安全与速度的基本矛盾。

## 实验设置与可复现结果

运行命令：

```powershell
python homecoord_bench/audit_candidate_tradeoffs.py
python homecoord_bench/probe_capacity_deadline.py
python homecoord_bench/run_capacity_deadline_matrix.py
python homecoord_bench/run_online_deadline_baselines.py
python -m unittest discover -s homecoord_bench/tests -v
```

脚本与数据：`homecoord_bench/audit_candidate_tradeoffs.py`、`homecoord_bench/probe_capacity_deadline.py`、`homecoord_bench/data/candidates/`。机器结果：`homecoord_bench/results/candidate_tradeoff_design_audit_20260924.json` 和 `homecoord_bench/results/capacity_deadline_design_probe_20260924.json`。

第一步对 20 条候选任务按相同输入运行中央单 Agent、无协调多 Agent、设备锁与版本规则、强约束规则四种现有架构。第二步只改变一项条件，为 C2 的 5 条任务延后第二任务到不再重叠，为 C3 的 5 条任务提高容量到足以并行，形成 10 条匹配安全对照。这些对照是程序生成的，尚未人工审核。

| 检查 | 结果 | 含义 |
|---|---:|---|
| 原候选任务 | 20 条，C1–C4 各 5 条 | 仍是待审核模板 |
| 强约束规则过程安全通过 | 20/20 | 当前候选集被这一规则基线完全覆盖 |
| 中央单 Agent 过程安全通过 | 20/20 | 单 Agent 也没有暴露安全失败边界 |
| 无协调多 Agent 过程安全通过 | 0/20 | 原候选全部为冲突压力样本，缺少天然安全比例 |
| 安全基线之间出现严格服务率与时延取舍 | 0/20 | 当前尚未形成强基线的非平凡 Pareto 前沿 |
| 匹配安全对照无协调通过 | 10/10 | C2/C3 冲突开关可控 |
| 强规则在安全对照中额外拖慢或少服务 | 0/10 | 目前没有发现强规则过度协调的代价 |

相对无协调执行，强规则在 9/20 条任务上降低了任务服务率，在 10/20 条任务上延长了现有“首次满足全部目标”时间；没有延长首个有效动作时间。这些差异不能直接解释为方法改进空间：C1 中的低优先级任务本来与高优先级动作互斥；C2/C3 延后的是会产生冲突的动作；C4 中 4 条任务的最终目标仅由外部事件就能满足，强规则没有产生首个有效动作。当前环境还为中央 Agent 固定增加 300 ms 合成推理时延，不能据此声称并行架构在真实系统中一定更快。

另一个指标问题是：现有 `task_completion_time_ms` 记录“第一次满足全部目标”，部分动作的效果在 `action_effective` 时刻立即写入状态，虽然设备动作还要持续一段时间。因此它可能早于任务真正结束；例如 HC-M08 的完成时间为 700 ms，但后续动作仍可能产生 C2 冲突。截止时间也尚未进入自动评测，即使 HC-M13 状态含有车辆离开时间，当前 `process_valid_success` 仍不会检查充电是否按时完成。

## 单条合成压力样例：安全不等于按时完成

为定位下一步应增加什么评测能力，另从 HC-M13 派生一条未审核样例：热水任务在 0 ms 到达，充电任务在 100 ms 到达，两者并行会超过 6 kW 容量；充电需在 9000 ms 前完成。此处“完成”明确规定为充电动作生效时间加设备持续时间，避免把开始充电误算为完成。动作时长、功率和模型时延仍为合成参数。

| 调度 | 过程安全 | 首个有效动作 | 充电完成 | 9000 ms 截止时间 |
|---|---|---:|---:|---|
| 无协调多 Agent | 否，容量超限 | 700 ms | 6800 ms | 达到，但执行不安全 |
| 强约束规则，先到先执行 | 是 | 700 ms | 9700 ms | 错过 |
| 优先执行充电的可行排程 | 是 | 800 ms | 6800 ms | 达到 |

可行排程把热水动作推迟 100 ms，先让已发布但提案尚未返回的充电任务执行。它只是重排同一批已知提案的**可行性见证**，不是已实现的在线协调方法。把容量提高到 7.1 kW 后，无协调与强规则都能安全并行并按时完成；把截止时间放宽到 10000 ms 后，原强规则也能按时完成。这两项对照说明差异来自容量与截止时间交界，而非设备名称。

这个样例表明“只看冲突是否消除”会遗漏按时完成损失，也显示首次动作快并不保证关键任务按时完成。但简单的优先级或 EDF 规则可能解决它，因此单条样例不能证明需要新算法，也不能直接并入正式数据集。

## 扩展为五组配对设计实验

为检查上述现象是否只依赖 HC-M13 的设备名称，又以 HC-M11–M15 五条 C3 候选任务为模板，分别生成“容量受限且截止紧”“容量充足”“截止放宽”三种条件，共 15 个合成场景、65 次架构/场景运行。每组只改变容量或高优先级任务截止时间；截止时间根据两种执行顺序的动作结束时间设置。逐项结果在 `homecoord_bench/results/capacity_deadline_matrix_20260924.json`，生成脚本是 `homecoord_bench/run_capacity_deadline_matrix.py`。

| 条件 | 观察到的结果（五组中） |
|---|---|
| 容量受限、截止紧 | 强约束规则 5/5 过程安全、0/5 按时完成高优先级任务；无协调 5/5 按时，但 0/5 过程安全 |
| 同一条件的优先排程可行性见证 | 5/5 过程安全且按时；首个有效动作比先到先执行晚 100 ms |
| 容量提高到可并行 | 强约束规则与无协调均 5/5 安全且按时 |
| 保持容量受限、放宽截止 | 强约束规则 5/5 安全且按时 |

这证明评测设计能系统地产生“过程安全与高优先级任务按时完成不能由先到先执行同时保证”的边界，并且有匹配对照，不是仅有一条例子。它**尚未**证明真实系统中普遍存在该边界，也没有证明需要复杂新算法：五组共享同一生成公式与合成时延，不是五个独立物理验证；优先排程见证使用了后到任务的完整提案，在低优先级提案首次就绪时，在线协调器还没有这些信息；简单优先级或最早截止时间规则仍可能解决全部样例。现有 `task_service_rate` 只看最终服务，五组各架构都是 1.0，无法代替按时完成率。中央单 Agent 的额外 300 ms 也是人为设定，不能据此比较真实响应性能。

## 在线简单规则复核：当前临界任务被解决

评测器现在另外报告 `task_action_finish_time_ms`、`task_deadline_met` 和 `timely_process_valid_success`。旧 `task_completion_time_ms` 保留其“目标首次满足”的原始含义，避免把动作启动误当动作完成。针对 C3 设计矩阵，另实现三个**因果在线的确定性规则基线**：提案一到即按先到先执行；已发布的紧急任务尚未回复时等待，再按优先级或最早截止时间排序。协调器在提案实际返回前只看已发布任务的优先级、截止时间等元数据，不看未来动作内容。执行前按已承诺动作预约容量。

| 临界条件中的基线 | 过程安全 | 安全且高优先级任务按时 | 首个有效动作 |
|---|---:|---:|---:|
| 在线先到先执行 | 5/5 | 0/5 | 700 ms |
| 在线等待＋优先级 | 5/5 | 5/5 | 800 ms |
| 在线等待＋最早截止时间 | 5/5 | 5/5 | 800 ms |

对应的容量充足和截止放宽对照里，三种规则均为 5/5 安全且按时。逐项数据见 `homecoord_bench/results/online_deadline_baselines_20260924.json`。额外的信息边界测试把 HC-M13 的紧急任务发布时间移到低优先级提案返回之后：等待规则无法预知这个尚未发布的任务，因此安全但错过新设截止时间。这表明在线规则的成功确实依赖**已发布任务的元数据**，不是偷看未来提案。

**修正判断：**五组临界任务能验证“按时完成”评测的重要性，却已被非常简单的在线规则全部解决，不能再拿它们作为新算法空间的证据。下一轮应先系统扫描任务发布与提案返回的相对时间、截止余量、容量和动作时长，找出在线 FIFO、优先级、EDF 与容量预约都无法同时兼顾安全和按时完成的任务，再判断这是否是合理且可复现的家庭场景。若找不到，benchmark 仍可研究协调规律，但方法创新的命题应收缩或调整。所有参数目前仍是合成的、无真实设备校准；在线基线仅实现 C3 容量场景，尚未覆盖其余冲突族或真实模型回复波动。

## 当前判断与下一轮门槛

**当前 20 条任务尚不能证明强协调方法之间存在非平凡取舍。** 它们足以用于展示问题存在和评测流程可执行；强规则 20/20 安全通过、10/10 安全对照无额外开销，说明现有候选集还没有充分挑战这一基线。新压力样例提供了具体的修订方向：把部分任务的按时完成作为可执行指标，并测试协调器是否能在必要时延迟一个较早、较不紧急的动作。

下一轮只围绕这一缺口推进：

1. 在数据规范中明确任务截止时间是硬约束还是效用指标，动作何时才算完成，并修正完成时间与截止时间评测。对已写入文字但未进入评测器的截止要求逐条核对。
2. 基于不同设备组合建立若干“安全、临界、冲突”配对任务；同时固定 Agent 可见信息，避免可行性见证偷用在线系统不可获得的未来信息。
3. 加入优先级队列、最早截止时间优先、全局串行和资源预约等强规则，再看新样例是否仍能区分方法。若简单规则已解决，应报告这一结果并继续寻找真实失败边界，不人为增加条件制造难题。
4. 对进入正式数据集的任务做双人独立审核、动作效果和时延校准，并加入模型生成提案的闭环重复实验。当前筛查不能替代这些工作。

与老师讨论时，可以如实说明：初步实验已经证明了多 Agent 冲突和协调代价；我们刚完成一次更严格的强基线筛查，发现现有 20 条候选任务被强规则完全覆盖，同时发现截止时间未被实际评估。下一步是验证“安全但错过关键任务”能否在多种任务和强规则比较下稳定出现，再决定 benchmark 的核心贡献和是否有新协调算法的空间。
