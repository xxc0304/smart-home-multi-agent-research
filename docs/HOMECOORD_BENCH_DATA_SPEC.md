### 1.1 Agent 决策协议

动作参数和前置条件均使用原生 JSON 值。例如，温度参数写为 `{"name": "temperature_c", "value": 24}`，住户占用前置条件写为 `{"path": "living_room.occupied", "op": "eq", "value": false}`。不要使用 `value_json`，也不要把 JSON 再编码成字符串。这样协议格式失败率可以作为单独的工程指标，而不会把双层字符串编码困难混入协调能力评测。

## 1. 核心研究问题

> 当多个专业 Agent 异步作用于持续变化的共享家庭环境时，现有协调机制在减少动作冲突的同时，需要付出多大的响应时延？

HomeCoord-Bench 第一版只评估四件事：多 Agent、共享状态、异步执行、冲突—时延权衡。个性化、多模态、云边模型路由、预测式执行和新的计划修复算法暂不作为数据集核心变量。

## 2. 一条数据的基本单位

一条数据称为一个 `episode`。它不是单独一句用户指令，而是一段可回放、可执行和可自动验证的家庭交互过程。

每个 episode 至少包含以下对象：

| 对象 | 必填内容 | 用途 |
|---|---|---|
| `home` | 房间、设备、环境变量和资源容量 | 定义共享物理环境 |
| `initial_state` | episode 开始时的完整状态和版本号 | 作为可复现起点 |
| `agents` | Agent 角色、目标、权限、工具和可见状态 | 定义真实的多 Agent 信息与能力边界 |
| `tool_catalog` | 每个 Agent 可调用动作的目标、操作、参数名／类型和适用 Agent | 明确真实工具接口，保证模型提案可执行且不同架构输入可比 |
| `task_stream` | 每个任务的释放时间、来源、目标、有效期和可验证的必要动作 | 产生异步任务流并衡量任务服务率 |
| `exogenous_events` | 用户、设备或环境在执行过程中的变化 | 防止环境被冻结等待模型 |
| `latency_profile` | 推理、通信、排队、设备生效和反馈延迟 | 分离协调时延来源 |
| `goals` | 可由状态表达式验证的目标 | 判断任务是否完成 |
| `constraints` | 执行过程中不能违反的规则 | 判断过程是否有效 |
| `conflict_rules` | 直接、间接和过期状态冲突规则 | 自动识别协调失败 |
| `event_log` | 观察、消息、动作请求、提交、生效和反馈时间 | 计算过程指标和复现实验 |

### 2.1 Episode 标识与来源

每条 episode 需要记录：

- `episode_id`：稳定且唯一的编号；
- `task_family`：任务家族；
- `source_type`：`project_seed`、`homebench_adaptation`、`simuhome_adaptation`、`manual_template` 或 `procedural_variant`；
- `source_reference`：来源文档页码、公开任务编号或模板编号；
- `generator_version`：程序化生成器版本；
- `review_status`：未审核、单人审核、双人审核或环境验证通过。

公开论文或项目材料只能作为任务设计来源。正式复用 HomeBench、SimuHome 等数据前，需要单独核对许可证、字段含义和引用要求。

## 3. 状态、动作与时间

### 3.1 共享状态

在时间 `t` 的家庭状态记为 `s_t`，由三部分组成：

1. 设备状态，例如空调模式、灯光亮度和扫地机器人运行状态；
2. 环境状态，例如温度、湿度、CO2、房间占用和总功率；
3. 协调状态，例如设备租约、在途动作和最近一次反馈。

每次有效变化都生成单调递增的 `state_version`。Agent 的观察必须携带版本号，动作也必须记录其依据的版本号。

### 3.2 Agent

每个 Agent 至少记录：

| 字段 | 含义 |
|---|---|
| `agent_id` | 稳定标识 |
| `role` | 例如舒适、能源、空气质量、安防或清洁 |
| `objective` | 该 Agent 在本 episode 中的局部目标 |
| `tools` | 可以调用的设备或服务接口 |
| `observable_state` | 能够直接读取的状态集合 |
| `writable_resources` | 可以修改的设备和环境资源 |
| `policy_constraints` | 必须遵守的家庭策略和权限边界 |

不同 Agent 必须存在真实的信息、工具或目标边界。仅把一个单 Agent 提示词拆成几个名称不同但能力完全相同的 Agent，不构成有效的多 Agent 数据。

### 3.3 动作生命周期

一个动作至少包含以下时间点：

| 时间点 | 含义 |
|---|---|
| `observed_at` | Agent 获得相关状态的时间 |
| `requested_at` | Agent 提交动作请求的时间 |
| `committed_at` | 协调器或执行器接受动作的时间 |
| `effective_at` | 动作开始对设备或环境产生效果的时间 |
| `feedback_at` | Agent 收到执行结果的时间 |

动作还需要记录：目标设备、操作与参数、所依据的 `state_version`、预期效果、实际效果和执行状态。

### 3.4 环境能力与候选任务模板

为避免把任务扩展绑定到执行器硬编码，episode 声明 `tool_catalog` 和 `action_grounding` 两张表。`tool_catalog` 为每个可调用接口给出目标、操作、参数 schema 和适用 Agent；`agents[].tools` 引用这些接口。若研究 Agent 的选择与协调能力，应为每个 Agent 提供至少两个语义合理的动作选择（可含取消／停止或替代目标），不要只提供评测所需的唯一标准动作；请求不得泄漏 `required_action`、`action_template` 等答案字段。每条 `action_grounding` 记录绑定 Agent、任务和提案操作，给出实际目标、落地操作、状态效果、设备持续时间和功率。间接环境冲突还应声明 `environment_effects`，把共享环境变量映射到方向值；C2 只有在两个动作对同一变量产生相反方向影响时才进入正式任务。执行器以能力表确定物理效果，Agent 的 `estimated_duration_ms` 和 `estimated_power_kw` 只作为提案元数据保存。确定性 dry-run 客户端使用任务内的 `action_template` 生成同一协议下的动作提案，因此增加设备或环境变量时不必修改旧任务分派逻辑。

首批候选任务位于 `homecoord_bench/data/candidates/`，包括灯光直接冲突（HC-M02）、窗帘直接冲突（HC-M03）、开窗与制冷间接冲突（HC-M07）和加湿与除湿间接冲突（HC-M08）。它们当前只通过确定性回放和协议测试，仍需人工双审、效果参数校准后才能进入正式数据集。

截至 2026-09-26，20 条候选任务均尚未双审、功率与时长为合成值，且都缺少可让模型直接调用的 `tool_catalog`；因此目前的 deterministic dry-run 通过不能替代 Agent 接口测试。正式任务在补齐动作签名和多种合理选择前，不应用模型完成率或动作参数正确率作结论。

对于持续数秒以上、设备有明显运行阶段的任务，`action_grounding` 应区分 `start_effects` 与 `completion_effects`：前者在设备实际启动时写入共享状态，后者只在物理动作完成时写入；若设备没有可观察的中间状态，`start_effects` 可以为空。旧字段 `effects` 仍供旧版闭环使用，不应代替新环境中的完成态标注。例如充电动作开始时将充电器置为 `charging`，完成时再将电池电量写到目标值并把充电器置为 `complete`。对会随时间连续变化的室温、湿度、电量等过程，本字段拆分仍只是离散近似，需后续接入物理模拟或校准轨迹。

## 3.5 离散事件环境的安全语义

`runtime/event_simulator.py` 将任务发布、提案返回、外部状态变化、动作启动和动作完成放到同一虚拟时钟上。它能重放记录的模型耗时，让晚发任务的短延迟提案先到达；当前调用接口仍同步取出提案，因此这是逻辑异步回放，不代表真实 API 并行。

环境在每次状态变化后检查硬约束，并统计从安全状态进入违规状态的次数和持续时间。协调策略会在动作启动前检查启动状态及预计完成状态；如果外部事件在运行期间使约束失效，当前环境会记录违规区间，但不会自动取消或中断设备动作。正式任务若要评测中断、补偿或局部修复，必须显式标注设备是否可中断、最小停止时延及停止后的状态，不能从通用动作模型中推断这些能力。

在没有真实设备时，episode 可以把 `calibration.status` 标记为 `synthetic_range`，并声明动作持续时间和功耗的相对范围。该范围只用于敏感性分析，不能写成设备测量值；只有接入模拟器轨迹、设备日志或公开规格并完成核对后，才能改为 `physical_trace_calibrated`。

过期状态任务可以在任务中声明 `recovery.wake_condition`。协调器拒绝过期动作后，执行器会等待后续外部事件使该条件成立，再重新请求同一任务；这只表示协议支持局部修复，不代表每个任务都必须重试。若外部事件已经满足全局目标，任务可以被安全取消，此时应同时报告较低的 `task_service_rate`。

## 4. 冲突定义 v0.1

第一版定义四类核心冲突。一个 episode 可以同时触发多类冲突。

### C1：直接设备冲突

两个 Agent 在重叠时间窗口内，对同一设备提交语义不兼容的写操作。例如一个要求空调制冷，另一个要求关闭空调。

判定依赖设备能力中的不兼容操作表，而不是比较自然语言表面是否相似。

### C2：间接环境冲突

两个动作针对不同设备，但通过共享环境变量产生相反效果，并导致目标变差、资源浪费或约束违反。例如开窗通风与高功率制热长时间同时进行。

判定需要设备效果模型：

- 动作影响哪些环境变量；
- 影响方向和估计强度；
- 多长的重叠时间构成有效冲突。

### C3：资源容量冲突

多个动作分别可行，但同时执行会超过共享资源容量，例如家庭总功率、网络带宽或设备并发上限。

第一版只将家庭总功率作为必选资源，其他资源留作扩展。

### C4：过期状态动作

Agent 根据旧状态产生动作，而在动作提交或生效前，相关状态已经变化，导致动作前置条件不再成立。

并非所有旧版本动作都算冲突。只有动作依赖的状态字段发生了超过允许范围的变化，并使前置条件失效时，才标记为 `stale_action`。

Episode 若显式标记 C4，应在 `conflict_rules` 中用 `task_id` 指定受影响任务，并在 `invalidating_conditions` 中列出会使该动作失效的条件；这些条件必须与该任务 `action_template.requires` 中的条件一致。机器校验不允许把一条无关状态变化随意标成 C4。

评测时把 C4 生命周期分开统计，避免把安全拒绝误记成冲突已执行，也避免漏掉动作开始后的状态失效：

- `stale_at_action_start_count`：动作因共享状态变化而在启动前被拒绝（原因是 `stale_state`）；变化可来自外部事件或其他动作；
- `in_flight_precondition_invalidated_action_count`：动作已开始后，外部事件或另一动作的开始／完成效果把其原本成立的显式前置条件变为不成立；同一动作只按第一次失效计一次；
- `in_flight_precondition_invalidation_source_counts`：按首次触发来源区分 `exogenous_update`、`action_started` 与 `action_completed`；逐条记录保留触发任务、触发 Agent 和失效条件；
- `cross_agent_in_flight_precondition_invalidated_action_count`：上述首次失效中，由不同 Agent 的动作引起的动作数；同一 Agent 的另一动作引发失效仍计入总数，但不计入此项；
- `unsafe_state_onset_during_action_count`：从安全状态进入违反约束的状态时，至少有一个动作正在执行。它是过程风险指标，不单独证明在途动作造成了违规；
- `conflict_counts.C4`：仍只表示评测轨迹中实际执行的过期动作，不包含安全拒绝。

报告上述计数时还需同时给出必要任务服务率、过程安全违规和持续时间，以及事件本身单独满足目标的比例。单有 `final_goal_success` 不能代表 Agent 服务了任务。
在途前提失效是独立的过程指标：它把显式 `requires` 作为运行期间的有效性观察条件，不自动增加 `conflict_counts.C4`，也不表示模拟器已经执行取消或修复，更不能单独推断物理危险。

## 5. 成功与时延定义

### 5.1 任务成功

第一版同时报告两种成功：

- `final_goal_success`：episode 结束时所有必要目标均满足；
- `process_valid_success`：目标满足，并且执行过程中没有违反硬约束。

不要求 Agent 复现唯一标准轨迹。只要目标和约束满足，不同动作顺序都可以成功。

同时单独报告 `task_service_rate`。每个可执行任务可以声明 `required_action`，例如 EnergyAgent 的节能任务要求实际产生 `living_hvac/off` 动作。这个指标用于识别“通过不执行低优先级任务来避免冲突”的策略，防止安全的 `noop` 被误解为完整任务完成。任务服务率不替代全局目标成功率：在互相冲突的任务中，安全协调器可能正确拒绝低优先级动作，因此需要共同观察安全、时延和任务服务率。

另报 `environment_only_goal_success`：初态或一段外部事件在没有 Agent 动作的情况下已使全部全局目标满足。此类 episode 仍可评估是否应安全取消冗余任务，但不能把事件造成的目标变化计为 Agent 服务成功。

### 5.2 首个有效动作

首个有效动作必须同时满足：

1. 已经生效，而不只是生成了文本或提交了 API 请求；
2. 对至少一个当前有效目标产生可测量的正向进展；
3. 没有立即违反 episode 的硬约束；
4. 不是与目标无关的查询、重复写入或无效动作。

首个有效动作延迟定义为：

`L_first = first_effective_at - episode_release_at`

该指标表示**目标开始产生有效进展**，对长时物理任务可能发生在设备启动之后。为单独衡量“设备是否迅速开始响应”，另报告 `first_action_start_latency_ms`：任务发布到第一个通过安全检查并进入 `action_started` 的时间。它不应与目标进展时间或全部任务完成时间混用。旧版 `first_effective_action_latency_ms` 在离散事件模拟器中保留作 `first_goal_progress_latency_ms` 的兼容字段。

P50、P95 和 P99 只在同一实验配置的多次 episode 结果上计算，不在单条 episode 内计算。

### 5.3 其他核心指标

- 最终任务成功率；
- 过程有效成功率；
- 任务服务率，以及因冲突被拒绝、延后或未完成的任务比例；
- 每类冲突的 episode 比例和事件次数；
- 过期动作率；
- 启动前过期拒绝数、执行中前置条件失效数、在途动作期间安全状态转坏数；
- 首次协调决策时延；
- 完整任务完成时间；
- 推理、通信、排队、验证和设备反馈的分段时延；
- Agent 消息数、LLM 调用数、Token 和 API 成本。

## 6. 四条种子 Episode

以下 episode 用于验证数据结构和评测器，不代表最终 benchmark 难度或分布。

### HC-SEED-001：安全并行控制

**任务家族：** `parallel_safe`

**初始状态：**

- 书房灯关闭，照度 80 lux；
- 卧室温度 28°C，空调关闭；
- 家庭总功率低于限制；
- `state_version = 100`。

**Agent 与任务：**

- `LightingAgent` 在 `t=0` 收到“把书房照度调整到适合阅读”；
- `ClimateAgent` 在 `t=0.2s` 收到“把卧室温度调整到 25°C”。

**目标：**

- 书房照度进入 400–600 lux；
- 卧室温度进入 24–26°C。

**冲突规则：**

- 两项任务没有共享设备、共享环境变量或容量冲突；
- 协调器若无必要地串行化两项任务，记录为协调开销，但不记为动作冲突。

**本条用途：**

检验多 Agent 是否能够获得并行收益，以及集中协调是否引入不必要的等待。

### HC-SEED-002：同一空调的直接冲突

**任务家族：** `direct_device_conflict`

**初始状态：**

- 客厅温度 29°C，检测到用户在客厅；
- 客厅空调关闭；
- 家庭策略规定：用户正在占用房间时，明确的临时舒适请求优先于普通节能策略；
- `state_version = 200`。

**Agent 与任务：**

- `ComfortAgent` 在 `t=0` 收到“未来 30 分钟把客厅保持在 24°C”；
- `EnergyAgent` 在 `t=0.3s` 收到峰值电价事件，根据普通节能策略准备关闭非必要空调。

**目标：**

- 在 episode 的响应预算内使客厅进入 23–25°C；响应预算将在模拟器校准后确定；
- EnergyAgent 不得覆盖仍有效且优先级更高的临时舒适请求。

**冲突规则：**

- 在舒适请求有效期间，`set_hvac(cool, 24)` 与 `turn_hvac(off)` 对同一空调构成直接冲突；
- EnergyAgent 可以提出建议、延后动作或选择其他节能设备，这些不算冲突。

**首个有效动作：**

客厅空调实际进入能够降低室温的工作模式。协调器完成冲突裁决只计入“首次协调决策时延”，不能代替首个有效物理动作。

**本条用途：**

检验独立 Agent、集中协调器和规则优先级在直接写冲突下的正确性与等待时间。

### HC-SEED-003：通风与制热的间接冲突

**任务家族：** `indirect_environment_conflict`

**初始状态：**

- 客厅温度 17°C；
- CO2 为 1600 ppm；
- 窗户关闭，暖气关闭；
- 室外温度 5°C；
- `state_version = 300`。

**Agent 与任务：**

- `AirQualityAgent` 在 `t=0` 获得降低 CO2 的任务；
- `ClimateAgent` 在 `t=0.1s` 获得将客厅温度提高到 21°C 的任务。

**目标：**

- CO2 降到 1000 ppm 以下；
- 客厅温度最终进入 20–22°C。

**冲突规则：**

- 窗户保持开启且暖气以高功率运行的重叠时间超过试验阈值时，记为间接环境冲突；
- 先通风、再关窗制热，或者采用满足两个目标的其他顺序，不记为冲突；
- 试验阈值需要在模拟器校准后确定，v0.1 不将某个秒数写成已验证标准。

**本条用途：**

检验只做同设备互斥的协调器是否会遗漏跨设备、共享环境变量冲突。

### HC-SEED-004：占用状态变化导致动作过期

**任务家族：** `stale_state_action`

**初始状态：**

- 客厅无人，扫地机器人空闲；
- `CleaningAgent` 观察到 `occupancy=false`，状态版本为 400；
- 家庭策略规定：行动不便的家庭成员在客厅时，扫地机器人不得启动。

**时间线：**

- `t=0`：CleaningAgent 根据版本 400 开始规划清扫；
- `t=1.5s`：CareAgent 检测到行动不便的家庭成员进入客厅，状态更新为版本 401；
- `t=3s`：CleaningAgent 提交基于版本 400 的启动动作。

**目标：**

- 当前有人时清扫任务被延后；
- 房间再次空闲后，清扫任务仍可以继续完成。

**冲突规则：**

- 如果启动动作提交或生效时 `occupancy=true`，且动作仍依赖旧的无人状态，则标记为过期状态动作；
- Agent 重新读取状态后选择延后，不记为冲突。

**本条用途：**

检验 Agent 的推理时间和状态版本变化如何导致原本局部合理的动作失效。

## 7. 参数化冲突家族 v0.3

固定种子只能证明评测器能识别预设事件，不能观察机制在临界条件附近如何变化。v0.3 因此围绕四类冲突定义连续或离散控制轴：

| 家族 | 控制变量 | 当前取值 | 预期边界 |
|---|---|---|---|
| C1 直接设备冲突 | EnergyAgent 信息可见性、第二任务间隔 | `policy_visible`／`local_only`；0／300／1000 ms | 信息不足或返回顺序变化时冲突率上升 |
| C2 间接环境冲突 | 制热任务相对通风任务的释放间隔 | 0／500／1000／1500／2500 ms | 动作重叠低于 1000 ms 后不再标记 C2 |
| C3 资源容量冲突 | 家庭并发功率上限 | 1.20／1.21／1.23／8.0 kW | 两动作合计 1.22 kW；容量高于该值后不再冲突 |
| C4 过期状态动作 | 住户进入时间 | 800／1200／1500／1800／2200 ms | 外部事件晚于动作生效后不再产生 C4 |

参数化变体的作用是估计冲突率、任务效用和时延随控制变量变化的曲线。边界数值是当前小型模拟器的校准参数，不应写成智慧家庭领域的通用阈值。

## 8. 第一轮基线

四条种子 episode 和参数化变体使用四种基线：

1. `CentralSingleAgent`：一个 Agent 可见全部状态并顺序决策；
2. `IndependentMultiAgent`：专业 Agent 独立决策，无显式协调；
3. `RuleCoordinator`：专业 Agent 加确定性设备锁、状态版本检查和显式优先规则。
4. `ConstraintCoordinator`：在 RuleCoordinator 基础上加入间接环境冲突和资源容量检查，只对冲突动作进行延后。

`ConstraintCoordinator` 是强规则基线，不作为论文新算法。当前阶段不加入新的计划修复算法。首轮目标是验证数据能否区分无协调、局部规则、完整约束规则与中央串行架构。

## 9. Episode 准入标准

一条候选 episode 只有同时满足以下条件，才能进入金标准集合：

- 至少涉及两个具有真实职责、工具或信息差异的 Agent；
- 初始状态、事件时间线和延迟配置可以复现；
- 成功条件主要由执行后状态验证，而不是由 LLM 主观评分；
- 冲突类型和触发条件可以程序化计算；
- 至少一个合理基线可能失败，且失败不是由故意隐藏必要信息造成；
- 不依赖真实家庭的个人隐私数据；
- 人工审核者能够解释为什么它属于对应任务家族。

## 10. v0.3 待确认问题

1. 专业 Agent 的最终角色和工具边界需要根据项目真实架构确认；
2. 间接环境冲突的时间和效果阈值需要由模拟器或真实设备轨迹校准；
3. 协调器主动等待是否算作有效协调决策，以及如何记录等待成本，需要在正式协议中统一；等待不计为首个有效物理动作；
4. 用户显式指令、家庭长期策略和系统默认策略之间的优先级需要形成公开规则；
5. 需要检查 SimuHome 和 HomeBench 的许可，确认哪些任务可以改写或重新发布；
6. 正式计算 P99 前，需要通过功效分析或重采样确定每个配置的重复次数。
