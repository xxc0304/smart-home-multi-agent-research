# HC-M06 物理轨迹与评测规格 v0.1

日期：2026-09-27。用途：为“多 Agent 换气／制热的协调—时延—用电取舍”确定可执行的数据入口和下一轮实验条件。本规格不把现有合成探针提升为真实物理证据，也不预设需要新协调算法。

## 研究问题与两类数据

先回答可证伪的问题：**在两个 Agent 分别处理空气质量与制热请求时，简单设备锁、动作区间规则、状态门控和带预测的选择，面对环境状态持续变化及参数误差，能否同时维持任务按时完成和合理用电？** 这里的“冲突”是可测的服务／能耗相互影响，不自动等于安全事故。

必须分开两类轨迹：

1. **环境识别轨迹**：无动作、仅开窗、仅制热、开窗与制热同时进行，以及开窗结束后制热。用来检查温度／CO₂的自然漂移、换气作用、加热作用与交互效应。若没有联合动作轨迹，不能验证单动作参数是否可组合；若没有无动作对照，不能把自然漂移归因于 Agent。
2. **协调评测轨迹**：固定同一初态、外界条件、任务目标、截止时间和 Agent 提案内容，只改变执行策略；每种策略还配一个初始 CO₂ 已达标、无需开窗的无冲突对照。环境识别与正式评测按房间、日期或工况拆分，不能用评测轨迹反推参数后再声称在线预测准确。

当前 SimuHome A–E 记录只覆盖空调制冷与室温，缺少本任务需要的窗户、CO₂和制热联动。它可以证明适配器的状态回读和时钟流程可行，但**不能**用于本任务的换气／制热参数拟合。下轮优先找支持这些变量的外部家庭／建筑模拟环境，或在可控房间采集；找到数据源后再核对接口、物理假设、许可和传感器精度。对公开数据的初步仓库检索尚未确认一份同时具有开窗状态、CO₂、制热功率、室内外温度与动作时间戳的可用轨迹，不能据此声称此类数据不存在。

作为备选环境映射，我还核对了固定版本 `SimuHome@83d28837` 的[湿度聚合器](https://github.com/holi-lab/SimuHome/blob/83d28837b69f0cbf1bc02ed5334cb8b561a9d54d/src/simulator/domain/aggregators/humidity.py)、[加湿器](https://github.com/holi-lab/SimuHome/blob/83d28837b69f0cbf1bc02ed5334cb8b561a9d54d/src/simulator/domain/devices/humidifier.py)和[除湿器](https://github.com/holi-lab/SimuHome/blob/83d28837b69f0cbf1bc02ed5334cb8b561a9d54d/src/simulator/domain/devices/dehumidifier.py)：两种设备可共同作用于房间湿度，理论上能构造原生双 Agent 环境试点。但现有 HC-M08 从 30% 湿度出发却要求防霉 Agent 除湿，任务语义不合理；直接移植只会制造人为冲突。必须先重新审核两个真实需求及匹配对照，再做设备状态／湿度响应试跑；源码可表达不等于物理已校准或论文证据已成立。本轮未启动新的 SimuHome 服务。

## 最小观测与动作记录

每条原始运行保存不可改写的源文件、来源版本、场景配置、房间／设备标识、时间基准、传感器单位与精度、采样频率、动作命令和回执。所需时间序列：室内温度、室外温度、室内 CO₂、窗户实际开闭、加热器实际功率；若有占用和通风量也应记录。命令发出、设备接受、物理状态改变、传感器上报分别记时，避免把 API 应答误当物理执行。住户占用数据若用于研究，应按机构要求去标识化。

可导入的 v0.1 轨迹对象有 `schema_version`、`sampling_semantics`、`trace_id`、`source`、`trial`、`events` 和 `samples`。`source.kind` 明确区分 `synthetic_fixture`、`external_simulator`、`physical_device`；`revision`、指向原始记录或生成程序的 `raw_data_reference`、`calibration_status` 与 `license_note` 不得缺失。`trial` 标明配对 ID、世界配置 ID、冲突／对照、策略、初态、目标和截止。`samples[0]` 是任务释放时刻 `t_ms=0` 的初态；后续温度和 CO₂是时刻 `t_ms` 的读数，`window_open` 与 `heater_power_kw` 表示**截至该时刻的上一采样区间**内状态／平均功率。采样边界必须对齐窗户与加热器开关事件；若区间内切换，应先在切换时刻拆分，不能用单个布尔值代表一段混合状态。

评测器检查严格递增时间、有限数值、单位范围、初态一致、来源、完整截止观测和冲突／对照的声明配置。它输出首次观测达标时间及相邻采样区间、首个物理响应的观测时刻、记录全程加热 Wh、**截至共同截止时间的加热 Wh**、开窗期间加热 Wh、采样间隔和配对差。若轨迹早于截止时间结束，则截止前累计用电记为未知，不外推为零；合成契约样例会在提前达标后继续观测至截止时间。超过 5 秒的采样缺口会报时间分辨率警告；正式论文若报告接近 1 秒的响应差，必须进一步提高采样频率或给出时间区间，不能以 5 秒采样宣称毫秒级差异。当前指标是**首次被采样发现达标**，尚未验证达标维持时长；正式目标需由领域审核者补充持续达标判据，且仍应保留原始序列以供重算。

## 任务与评测冻结规则

- 初始 CO₂高／低配对只改变这一项关键条件，温度、室外条件、设备能力、提案和截止保持相同；真实操作可随机化试验顺序，记录环境漂移，而不是假设每次 reset 完全相同。
- 截止时间根据先导数据中**物理可行性**预先分层：两种安全策略都能完成；只有部分策略能完成；任何策略都不可完成。不可行任务单列，不用作某方法“失败”的证据。确定阈值后冻结，不按目标方法结果反调。
- 环境参数只从识别集估计；按房间／日期／外界条件留出测试集。先在保存的固定提案和调用时延上比较协调策略，隔离协调效果；再让中央与多 Agent 架构各自生成提案，检验完整系统。模型调用费用和实际推理时延在第二阶段才计入。
- 至少比较 Independent、DeviceLock、ActionOverlapLock、StateGate、简单预测选择、带保守裕量的预测选择和已知真实参数的参考上界。参考上界只能标为 oracle，不当作公平在线基线。还应保留无冲突对照和“参数估错”的反事实。
- 同时报告按时完成、首次动作／首次目标进展、最终完成、能耗、无效或未服务任务、过程约束，以及每个策略可见的信息和传感器／预测调用开销。先给出服务—时延—用电的并列表格或 Pareto 比较，不事后调整加权总分。不能把总用电或开窗时加热用电直接等同于“浪费”；也不能把开窗加热直接标为安全违规。

## 已实现与尚缺证据

已有独立输入评测器 `homecoord_bench/runtime/physical_trace.py`、命令行入口 `homecoord_bench/score_physical_traces.py`、8 条**合成契约样例**和 4 组匹配审计。该样例来自同一人工物理配置、四种策略与两种初始 CO₂，作用是验证导入与指标复算，**不是八户家庭**。样例放在正式 episode `data/` 之外的 `homecoord_bench/fixtures/physical_trace_v0.1/hc_m06_synthetic.json`；导入审计见 `homecoord_bench/results/physical_trace_import_audit_20260927.json`。

这次导入还暴露一个容易误读的指标现象：合成冲突臂在 360 秒截止下，Independent 345 秒完成、耗电 187.22 Wh；StateGate 到截止时仅耗电 38.89 Wh，**却还未完成任务**，最终 575 秒完成时累计 158.33 Wh。因此论文不能只按截止前用电量排名，把未服务任务误称为节能优势；必须把任务服务、截止达成与用电并列报告，并在同等服务条件下比较成本。

尚缺的是可核验的联合物理轨迹、来源许可与校准记录、不同房间／工况、独立领域双审，以及真实或外部模拟器对照。只有这些到位，才能判断此 C2 任务是否值得进入 benchmark 主证据；即便进入，是否需要新方法仍取决于强在线基线在留出环境中的表现。
