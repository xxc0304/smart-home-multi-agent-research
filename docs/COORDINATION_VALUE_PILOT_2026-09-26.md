# HomeCoord-Bench 协调收益与无冲突开销配对试验

> 复核提示：本文件记录的是旧执行语义下的历史结果。动作前提与在线信息边界修正后的重放见 `docs/CAUSAL_EVIDENCE_AUDIT_2026-09-26.md`；尤其“6/6 无冲突对照有效”已修正为 5/6，请以后者为准。

2026 年 9 月 26 日。此报告是未审核候选任务上的小规模原型试验，不是正式 benchmark 结果。

## 要检验的问题

现有强约束规则在无冲突任务上是否仍会造成可观察的时延或任务服务损失？在相同 Agent 提案与相同模型调用耗时下，它消除冲突又需要付出什么代价？这直接检验把论文主命题改成“什么时候值得协调”是否已有经验依据。

## 设计

- 从 20 条未双审候选任务中选 3 条跨设备环境冲突任务（HC-M06–M08）和 3 条共享容量冲突任务（HC-M11–M13）。每条另生成一个只改变第二任务释放时间或家庭容量的匹配无冲突对照，共 12 个条件。
- 每个条件调用 `deepseek-flash` 生成一次独立专业 Agent 提案，记录每次逻辑 API 调用的实际耗时；将**完全相同的提案和调用耗时**回放给 `ConstraintCoordinator`。仅此一步不用再次调用模型。
- 同时比较过程有效成功、C1–C4 冲突、任务服务率、首个有效动作、目标首次满足时间，以及最后一个已执行动作的结束时间。后两项不是同一个指标。
- 重跑原有的 20 条候选任务和 10 条匹配安全对照的确定性强基线筛查，检查试验背景是否一致。

## 结果

| 条件 | 可评估数量 | 同提案强规则相对无协调的结果 |
| --- | ---: | --- |
| 匹配无冲突对照 | 6/6 | 首动作、目标首次满足、最后动作结束的增量均为 0 ms；任务服务率不变 |
| 原始任务中，无协调实际发生 C2/C3 冲突 | 4/6 | 4 条的强规则回放均消除冲突；首动作增量均为 0 ms；目标首次满足分别增加 1831、762、3703、5932 ms；任务服务率不变 |
| 原始任务 HC-M08 | 1/6 | 模型只给出一个动作，双方均无冲突，指标不变；不能作为冲突收益证据 |
| 原始任务 HC-M06 | 0/6 | 模型动作无法由能力表落地，执行器报错；此条件不计入成功或失败率 |

除 HC-M06 原始任务外，11 个完成条件各有两个真实模型逻辑调用；这些已记录调用耗时中位数为 1466 ms（22 次）。这只是单次 API 请求耗时，不是部署端到端物理动作时延。HC-M13 中目标首次满足增量为 5932 ms，而最后动作结束增量为 3000 ms，再次说明两者不能混称“完成时间”。

确定性复查仍得到：强约束规则在 20/20 原始候选任务上过程有效；10/10 无冲突对照没有多余时延或服务损失；现有候选任务未产生强安全基线之间的非平凡服务—时延前沿。

## 对命题的判断

这次试验**没有发现**现有强规则在无冲突条件下“协调过度”的证据，也没有形成需要新自适应协调算法的缺口。它支持继续把冲突收益与条件性时延／服务代价作为 benchmark 主线，却不足以把“什么时候协调值得其成本”升级成已经成立的核心发现。尤其不能通过与故意全局串行的弱基线比较，制造这个结论。

零增量有明确的实现前提：当前协调器使用本地规则，模拟时钟没有计入规则判断、状态同步、网络传输或设备反馈耗时，也没有新增模型调用。真实 API 提案虽已使用，模拟器仍把顺序完成的 API 调用按各自释放时间与耗时放回异步时间线；这不等于真实并发部署。候选任务与设备时长、功率未经双审和物理校准，且每个条件只有一次模型采样。因此“真实协调成本为零”并未得到证明。

下一轮若要真正检验“什么时候值得协调”，应先完成任务与评分审核，并给协调检查／状态获取提供可测或有依据的成本；随后在相同信息边界下比较强规则与其他安全方法。只有观察到稳定且非平凡的安全、时延、任务服务取舍，才考虑把“适用边界”升为论文主张。
