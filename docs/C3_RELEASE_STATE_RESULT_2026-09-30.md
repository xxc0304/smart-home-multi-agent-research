# C3 晚到任务按发布状态调用模型：结果

完成36次预定晚到请求：35次合规且操作正确，1次返回错误协议字段。所有失败均保留，未自动修复或重采样。另完成36次旧提案对照及70次无API轨迹复现／配对审计；14项相关测试通过。

本轮补强了晚到调度结果的稳定性，但也确认当前功能Agent看不到其他设备的共享资源状态：**不能把本轮说成已经验证了复杂动态状态推理。**

## 实验实际怎么运行

早期任务复用上一轮三个结构各三次真实提案及返回延迟。晚到任务在模拟器虚拟60秒发布时，读取当时允许功能Agent看到的状态和版本，重新调用DeepSeek。对比门控重试与已发布精确可行性退化服务规则，保留高／低压力两种条件。

API调用是同步执行后将测得耗时放入虚拟队列；没有按现实时间等待60秒，也不是整个系统真实联网并发执行。每分支的早期动作与对应旧提案对照一致；新旧晚到提案及网络时延可同时变化，不能单独归因于状态推理。

|---|---:|---:|---:|---:|
| N2-1 | 1.6 | 0/3 | 0/3 | 0 |
| N4-1 | 1.6 | 0/3 | 0/2 | 1（精确规则分支） |
| N5-1 | 1.6 | 2/3 | 3/3 | 0 |

35个有效分支全部最终服务所有必要任务，按时／超期结果与对应旧晚到提案对照35/35一致。高压力下两个结构仍超期，低压力18/18按时；第三结构精确规则在高压力3/3按时，保留负对照。不能由这些分母推出总体成功率或方法必然失败。

1个协议失败发生在N4-1、第二轮、高压力精确规则分支，模型用了type而不是response_type。其请求确实得到提供方响应，但不能生成合规动作；因此它不是一个有效调度结果，也不能归因于规则调度逻辑。动作正确率只能写35/35有效提案，完整协议成功率35/36。这一个失败不足以概括模型的协议可靠性。

## 状态审计发现

35/35新请求都通过了按事件前缀重建的状态、版本、发布时间、公开工具和任务信息核对，隐藏评分答案没有进入任务字段。35/35新分支都能通过保存提案和实测延迟无API复现；35/35对照的发布前动作前缀一致。

但功能Agent可见的本地设备状态35/35与初始相同。全局状态版本为2–5，说明早期动作确实改变了环境；功能Agent仅观察自己的设备，它自己的设备在发布时仍idle。不能把全局版本号变化当作看到了其他设备运行、容量余量或冲突信息。

所以本轮的新证据是“按晚发布时间和当前版本重新采样后，结果保持稳定”，不是“Agent处理动态共享状态的能力存在缺口”。这也解释为何正确提案没有改变早期非抢占启动导致的资源排队。

## 对选题的含义

积极之处：补充了此前反事实回放的一个环节，两个结构的高压力问题在晚到新提案下仍出现，同时保留成功结构与低压力对照。benchmark已有比较稳定的调度机制证据。

不足之处：当前案例的语言需求和本地状态仍简单。已有强规则可以解决不少条件，不能假定复杂协调算法必要。若要进一步揭示LLM多Agent的普遍局限，应扩展模型确实可观察、必须理解的信息变化，而非仅增加不可见物理复杂度或重复这三个结构。

下一步先设计一个小型共享信息／任务约束更新对照：明确谁能看到更新、何时看到，保留确实可行和无需协调的条件，再检验语言需求到动作／约束的理解与执行。仍围绕冲突—时延，不把全部新机制塞进一个新命题。协调计算时间的异步接入尚未实现。
