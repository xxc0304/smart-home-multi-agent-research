# HomeCoord-Bench：协调何时值得——下一轮实验协议 v0.2

日期：2026-09-27。用途：在“多 Agent 冲突—时延 benchmark”主线内，定义可反驳的条件比较；不是新算法或已确认的真实家庭规律。

## 研究问题与零假设

在相同任务、相同可见信息、相同动作提案和共同最低安全门控下，**提前协调**何时能比直接执行并接受安全门控更完整、更及时地服务任务？进一步，在强确定性规则已可协调时，是否还存在值得支付额外推理时延的剩余空间？

零假设是：覆盖设备互斥、共享容量和已声明状态前提的强确定性规则，在这些任务上与更复杂的协调方案服务质量相同或更好，且处理更快。实验必须允许零假设成立；不能通过故意漏写已知规则来制造所谓算法缺口。

## 固定的比较原则

1. 所有策略共享启动前的最低安全门控，包括动作权限与参数、当前前提、声明的设备冲突、共享容量及可计算的状态约束。门控只拒绝，不重试；策略可在门控前规划安全启动时间。独立执行在此设置下是“无提前协调＋相同安全门控”诊断基线，而非允许已知违规的部署选项。
2. 首批策略：无提前协调、仅设备锁、强确定性约束调度、单主 Agent＋执行器。已有 `ConstraintCoordinator` 在 C1/C3 上就是强确定性规则；`RuleCoordinator` 只作设备锁消融。未来新增 LLM 或选择性协调方法，必须与强规则共用安全门控、状态元数据和任务预算。
3. 固定提案回放用于隔离协调决策；真实模型提案用于检验自然语言理解、错误参数、调用失败和真实延迟。两组结果分开报告。中央与专业 Agent 的输入差异应明确列出，不能称为“同一信息”而忽略中央全局可见状态。
4. 规则处理、模型调用、设备命令、状态回读分别实测；人为 0/100/300/800 ms 延迟仅为敏感性探针。家庭冲突频率未知时，不把任意混合比例当作经验分布。

已有一项本机计时试测：完整的两任务 Python 事件模拟器中位数约 0.94–1.05 ms，P95 约 1.45–2.00 ms，P99 约 1.98–3.90 ms。它包括模拟器、dry-run、门控和评分，不包括 API、网络或真实设备。该结果不能替代部署测量；详见 `docs/LOCAL_EVENT_RUNTIME_TIMING_2026-09-27.md`。

## 任务与评估对象

先使用通过独立双审的 C1/C3 配对，增加多个**独立任务实例**，而非对同一合成样例重复运行充样本量。每组保留冲突、临界与安全条件，且只改变一个机制因素。C1 核对真实设备命令与时序语义；C3 有来源的家庭/回路容量才可称物理家庭任务，否则标为抽象容量子集。C4 只在定义停止/恢复语义后研究修复，C2 在校准前单列连续合成子集。

当前具体分层见[参数来源核查](C1_C3_PARAMETER_PROVENANCE_2026-09-27.md)：C1 仅是设备命令冲突诊断，其 6 秒降温终态不计现实热效果；书房灯 C3 是抽象容量任务；电动车／热水器 C3 是另一个未校准合成压力子集，不与前者或现实住宅样本合并统计。三者均待独立审核，不能因为有公开设备功率数量级就升级为现场校准。

每个 episode 至少记录：任务与世界配置来源、冲突机制、配对 ID、初态、Agent 可见状态、协调器可见状态、动作提案及其返回时间、设备动作起止、门控拒绝与理由、状态变化、任务必要服务、最终目标、过程安全和各段成本。审核者先只看任务文本与配置，再看策略结果，减少结果诱导。

## 主指标与条件曲线

主结果分开报告：①过程安全违规次数/持续时间；②每项必要动作是否执行及其完成时间、全部必要服务完成率；③首次安全物理动作启动时间；④最终家庭目标是否达成及达成时间；⑤模型/规则/设备各段耗时与调用成本。`process_valid_success` 和最终目标达成不能代替必要服务率：C1 当前就存在温度目标达成但能源任务被门控拒绝的实例。

在预先声明的一组响应预算下，报告“安全且在预算内完成的必要服务率”，并画出预算连续变化时的阶梯曲线/条件前沿。预算是**分析阈值**，不是事后写入任务的硬截止时间。若以后研究硬 deadline，需要另做可行性下界与任务依据。对真实延迟报告中位数及 P95；样本足够时再估 P99，不能用少数确定性重复估尾部。

## 当前试验给出的边界

共同门控的 30 个 C1/C3 合成固定提案单元见 `homecoord_bench/results/coordination_shared_safety_pilot_20260927.json`。C1 的设备锁已经足够；C3 的设备锁不检查容量，强确定性约束调度可提前排队并完成任务。无冲突对照下，额外 300 ms 的合成等待只增加首动作延迟。这是**实验流程验算**，还不是“协调何时值得”的经验规律，因为任务太少、参数未审核、耗时人为设置，也没有一个在强规则之上提供不同决策的额外方法。

随后用电动车充电／热水器的历史提案耗时做了统一事件回放：低容量、热水提案先返回时，等待后按期限排序保住充电按时完成；高容量时同样等待让首动作白等 180 ms。透明的容量感知期限规则已接入统一运行时，在这个样例中低容量按时完成、高容量避免白等。见 `docs/C3_EV_WATER_COMMON_GATE_REPLAY_2026-09-27.md`。这提供了更清楚的“何时等待”机制样例，但设备和截止时间仍未经校准，不能当成论文级适用边界，更不能据此主张新算法。

进一步的[公开功率上界敏感性试验](C3_EV_WATER_INFORMATION_BOUNDARY_2026-09-27.md)表明，这个强规则的兼顾能力依赖额定上界准确：低报会让充电在一条不利提案顺序轨迹中迟到，高报或缺失会让高容量场景的首动作多等 180 ms。该试验仍只是一种任务模板、五组历史耗时和人工协调延迟；规则处理的墙钟耗时尚未测量，也不能据此推断真实家居的错误分布。

再将容量、期限紧迫度和期限优先顺序做了 315 单元的控制参数扫描，结果见[协调价值边界试验](C3_EV_WATER_DEADLINE_BOUNDARY_2026-09-27.md)：6.0 kW 下，紧迫任务的提案若后返回，按期限等待改善按时率；期限宽松时，容量先到先排已经给出同等结果；容量达到 7.0 kW 后可安全并行，始终等待增加约 209 ms 首动作时延却没有按时率收益。这更具体地展示了协调价值依赖任务紧迫度与容量余量，但仍是单一合成模板上的参数格点，不能当作独立样本或新算法证据。

若审核后的广泛任务中强规则持续占优，应如实把结果写为：当前可声明的家庭资源约束主要由透明规则处理，额外 LLM 协调没有证明收益。若出现跨任务/世界配置稳定的剩余缺口，再先归因是规则表达能力、状态观测误差、异步反馈还是自然语言任务解释，然后只围绕该缺口设计方法。
