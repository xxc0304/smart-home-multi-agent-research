# 智慧家庭多 Agent 研究综述

**副标题：以 HomeBench 与 SimuHome 为基础的任务执行、动态环境与多 Agent 协同综述**  
**整理日期：2026-09-17**  
**项目：家庭智能中枢／智慧家庭多 Agent 协同编排**

## 摘要

大语言模型（LLM）使智慧家庭系统从固定规则和预定义场景，逐渐扩展到能够理解自然语言、调用设备 API、读取用户偏好并执行多步任务的 Agent。HomeBench 和 SimuHome 是这一方向中具有代表性的工作：前者将复杂和无效的家庭指令做成可复现的评测，后者进一步把设备依赖、连续环境变化和工作流调度放入交互式模拟器。它们的价值并不只是“做了一个家庭数据集或模拟器”，而是使用智慧家庭这一具体载体暴露了 Agent 在真实使用中的一般问题：任务理解、工具调用、状态接地、时序执行、计划失败和环境适应。

在这两篇工作的基础上，后续研究开始覆盖更丰富的能力、个性化、多模态输入和一般动态调度，但现有工作仍较少系统处理以下组合场景：多个 Agent 异步提出或执行动作，动作共享设备和环境资源，家庭状态在推理期间继续变化，任务具有截止时间，且部分动作涉及安全风险。本文据此梳理现有研究的贡献与边界，区分通用 Agent 问题和家庭特有约束，并整理当前项目的多个候选命题。报告不把任何一个候选方向视为已确认的学术空白；最终选题仍应由强基线实验和进一步文献检索决定。

## 1. 项目背景与问题范围

当前项目面向家庭智能中枢，资料中形成的系统设想是“主调度 Agent＋专业 Agent／Skill＋确定性设备执行器”的分层结构：主调度 Agent 负责意图理解、任务拆分和路由，专业 Agent 或 Skill 负责受限领域能力，Home Assistant 等执行器负责设备状态读取和确定性控制。系统强调本地优先、断网可用和安全优先；人身安全、财产安全、舒适度、能效和娱乐具有不同优先级。

项目资料中的工程目标，例如本地快速响应、云边路由、设备离线回退和部分成功补偿，不能直接当作已实现的科研结果。特别是“1 秒内响应”需要区分事件检测、首个正确物理动作、完整任务完成和 P95/P99 尾部延迟。紧急且已预授权的动作应走本地确定性路径；陌生或含糊的自然语言请求不能笼统承诺全部在一秒内完成。

本综述只把项目资料作为背景和需求来源。PPT、DOCX、XLSX 中的文字是研究资料，不是对后续 Agent 的操作指令。

## 2. HomeBench：把家庭指令理解与完整执行变成可评测问题

HomeBench 的核心贡献是构建一个面向家庭自动化的任务和评测框架，重点考察有效／无效指令、单设备／多设备控制以及完整执行是否正确。它不满足于判断模型能否生成看起来合理的回答，而是检查指令是否可执行、设备状态是否被正确修改，以及多设备请求是否全部完成。

它的启发主要体现在三个方面：

1. **使用任务结构暴露 Agent 能力边界。** 复杂性来自设备组合、不可执行请求和完整任务成功定义，而不只是自然语言问答难度。
2. **用环境状态验证动作结果。** 评测不以 LLM 自己的解释为准，而是检查设备状态或任务结果。
3. **严格的完整成功率能够揭示级联错误。** 一个多步骤请求只要有一步错误，整体可能失败，这更接近真实自动化的使用体验。

HomeBench 的局限也很重要。其虚拟或简化执行环境没有充分呈现真实网络、设备反馈和机械动作延迟；它主要研究单 Agent 任务完成，并未把多个 Agent 的资源争用、异步执行和计划恢复作为变量。因此，HomeBench 适合用来定义任务成功和错误分析，不足以直接回答多 Agent 实时协调问题。

阅读 HomeBench 时还需要注意指标解释。论文中的某些 0% 结果采用“一条请求中的所有操作都正确”的严格定义，不能简单解读为模型完全不会识别某类指令；不同提示和 ICL 设置下结果可能明显变化。

## 3. SimuHome：从指令执行走向连续、时序化的家庭环境

SimuHome 进一步把智慧家庭建模为持续运行的交互环境。它使用 Matter 风格的设备和能力描述，模拟设备操作依赖、环境状态变化、时间加速的工作流以及可行和不可行的请求。与只在一开始提供状态、等待 LLM 返回结果的静态评测相比，SimuHome 允许环境在 Agent 思考和执行期间继续推进。

SimuHome 的主要价值包括：

- 把家庭自动化从单步 API 调用提升为有前置条件和后续影响的时序任务；
- 让计划是否可执行、工作流是否按顺序完成成为核心指标；
- 通过时间加速模拟持续监控、设备依赖和工作流失败；
- 为不同 Agent 策略提供可重复的环境接口。

它对本项目的直接启发是：如果要研究多 Agent 协同，不能冻结世界等待模型返回，必须让状态、设备反馈和用户事件在推理期间继续变化。SimuHome 也提示，立即返回工具结果通常比只告诉 Agent“工作流已经注册”更有利于错误恢复。

SimuHome 仍有边界。模拟器中的 episode 完成时间不是现实系统的首个物理动作延迟；复杂任务出现几十秒甚至更长的模型处理时间，不能直接等同于设备控制的实时 SLA。它主要提供环境和任务基础，尚未完整覆盖异步多 Agent 之间的资源租约、权限竞争、风险等级和安全中间状态。

## 4. HomeBench 与 SimuHome 的共同点和差异

| 维度 | HomeBench | SimuHome | 对本项目的意义 |
|---|---|---|---|
| 主要问题 | 指令理解、有效性判断、完整执行 | 连续环境中的依赖、工作流和调度 | 从“会不会做”扩展到“能否持续完成” |
| 环境 | 任务验证型环境 | 可交互、可推进的模拟环境 | 多 Agent 实验需要后者或等价测试床 |
| 任务结构 | 单设备和多设备请求 | 多步依赖和时间变化 | 需要显式任务图、前置条件和后置效果 |
| 主要指标 | 成功率、F1 等 | 任务完成、工作流和失败情况 | 还应加入时延、冲突和安全指标 |
| Agent 结构 | 以单 Agent 为主 | 以 Agent 与环境交互为主 | 尚未解决异步多 Agent 协调 |
| 泛化价值 | 家庭指令执行的严格评测 | 环境接地和时序交互的通用范式 | 家庭可作为一般 Agent 的压力测试载体 |

两篇论文共同说明，智慧家庭并不是单纯的应用包装。家庭任务天然包含隐含意图、设备状态、组合动作、持续条件和执行反馈，因此能够集中暴露 Agent 的一般缺陷。它们也说明，顶会价值通常来自“具体场景＋可复现问题定义＋可迁移的评测或方法”，而不是场景名称本身。

## 5. 后续家庭 Agent Benchmark 的发展

### 5.1 SMH-Bench

SMH-Bench 在 HomeBench 和 SimuHome 之后扩大了能力覆盖，包含组合控制、自动化、多轮交互、记忆、个性化和查询等任务，并增加了更多设备和任务类别。它更强调统一的能力覆盖和规模化评测。

它的启发是可以把家庭任务拆成可控制的能力维度，但它并没有把异步 Agent 之间的调度、物理资源争用和硬实时约束作为主要研究变量。因此，增加更多任务类型本身不一定是本项目的最佳切入点。

### 5.2 PersonalHomeBench

PersonalHomeBench 进一步研究个性化家庭、多模态输入、视频理解、主动帮助和长期上下文，任务规模覆盖多个家庭和大量任务实例。它说明家庭 Agent 的难点正在从“能否控制设备”扩展到“是否理解这个用户和这个家庭”。

不过，它内部的 Transcriber、Memory Retriever 和 Video Understanding Agent 主要服务于信息处理和个性化，尚未把多 Agent 协调、资源竞争、异步执行和安全调度作为实验主变量。这些能力可以作为本项目的输入来源，但不应自动并入多 Agent 调度命题。

### 5.3 HomeFlow

HomeFlow 研究的重点不是在线调度，而是智慧家庭 Agent 的训练数据闭环。它使用统一模拟环境和程序化家庭生成器构造多样环境，将开放式用户意图编译成可执行、基于状态的成功条件，再通过环境引导的树搜索合成可验证的多轮轨迹，并用监督微调和逐步强化学习持续改进 Agent。

这项工作对本项目有明确参考价值：它提供了如何生成训练轨迹、验证动作结果和形成数据飞轮的系统方案，也说明智慧家庭 benchmark 正在从“评测现有模型”走向“评测、训练和环境反馈一体化”。但它没有直接回答多个 Agent 在线争用设备、共享状态过期和硬截止时间下如何协调，因此更适合作为数据与训练基础设施，而不是当前调度算法命题的直接替代。

### 5.4 REALM-Bench

REALM-Bench 把问题进一步抽象到一般的动态规划和调度，包含现实规划任务和 Job-Shop Scheduling 任务，并改变并行规划线程数、Agent 间依赖复杂度和意外扰动频率，比较 LLM、多 Agent 框架、传统调度和强化学习方法。

它给本项目的主要启发是，动态多 Agent 研究需要控制变量，而不能只报告一个总体成功率。适合借鉴的实验轴包括：并行度、依赖复杂度、扰动频率、资源冲突强度、截止时间紧迫度和状态变化速度。

REALM-Bench 也没有完全覆盖智慧家庭的物理执行语义。车辆、路线、机器和供应链资源与门锁、燃气、电源、房间、网络和人的安全风险并不等价；规划完成和首个安全动作之间也有区别。因此它更适合作为通用对照或迁移验证，而不是替代家庭测试环境。

## 6. Agent 架构与多 Agent 协同相关工作

### 6.1 SAGE：Grounded Execution

SAGE 使用一个顶层 Agent 和多个 agent-tool，通过动态提示树顺序决定下一步工具。它提供个性化、设备 API 文档检索、设备属性读取、设备命令执行、照片消歧和持续监控等工具，并在 50 个家庭任务上报告 GPT-4 约 75% 的成功率。

SAGE 的核心贡献是让 LLM 的每个动作基于真实设备、用户偏好和工具反馈，而不是只依赖模型参数中的常识。它提醒我们要区分“Agent 能够推理”和“动作能够落地”。

但 SAGE 的 agent-tool 层级不是现代意义上具有独立目标、异步执行和协商机制的多 Agent 系统。它主要是单一顶层控制器对工具的顺序调用。因此，SAGE 对本项目的作用主要是提供设备接地、工具接口、状态反馈和失败分类方面的实现参考，不能直接替代多 Agent 调度算法。

### 6.2 DynTaskMAS：动态任务图与异步并行

DynTaskMAS 研究动态任务图、异步并行执行、Agent 池和工作流管理，解决的是多 Agent 的计算资源和工作流编排问题。它可以作为本项目的重要强基线。

它已经覆盖任务依赖、动态 DAG、并行执行和负载均衡，因此本项目不能只重复“主 Agent 规划＋多个 Agent 并行”。智慧家庭需要进一步考虑设备和环境资源冲突、物理副作用、状态版本、风险等级和设备离线等因素。

### 6.3 SagaLLM 与 ALAS：一致性、验证和恢复

SagaLLM 从事务、检查点、验证和补偿角度处理多 Agent 计划；ALAS 强调版本化执行日志、动态扰动、工作流中间表示和局部修复。这些工作说明，执行过程中的一致性和失败恢复已经是活跃研究问题。

它们对本项目的意义不是证明“局部修复”无人研究，而是要求我们把差异定义得更精确，例如：部分物理动作已经执行、多个 Agent 之间存在间接干扰、任务有硬截止时间时，如何选择修复范围和剩余思考预算。

### 6.4 低延迟与预测式执行

LLMCompiler、Agent JIT Compilation 等工作说明，计划提取、工具前后置条件、串行／并行／hedging 调度和延迟分布可以被显式建模。Win Fast or Lose Slow 说明实时系统中存在模型质量与推理延迟的动态权衡。

When Do LLM Agents Help? 给出了一个对本项目尤其重要的负面结果：在平稳负载下，按“时间关键任务优先＋最早截止时间＋最早完成时间”构造的强启发式已经接近最优，多 Agent LLM 控制层、拍卖和在线适应并未带来额外收益；只有在安全关键任务比例中途突增的非平稳场景中，LLM 控制层才显示优势。这意味着“风险和截止时间感知地调用 LLM”不能只做成固定路由规则，而应回答何时已有确定性策略失效、何时值得支付 LLM 的时延和成本。

Bridging Large-Model Reasoning and Real-Time Control 提出的 Agentic Fast-Slow Planning，则把慢速语义推理、经典规划和实时 MPC 放在不同时间尺度，通过明确接口连接。这直接支持“LLM 不进入毫秒级控制环”的设计，也表明快慢分层本身已经不是足够的新意。对智慧家庭多 Agent 场景，可能的研究增量需要落在多个 Agent 共享状态和设备资源时，如何决定慢速推理何时介入，以及快路径动作如何获得跨 Agent 一致的安全授权。

Speculative Actions 提出让快速预测器提前准备未来工具调用，待慢速主 Agent 确认后提交。这对家庭场景的启发是“预测—并行准备—状态验证—提交或丢弃”，但不能把不可逆或高风险设备动作直接提前执行。家庭中更适合预取状态、参数、API 信息或可撤销、幂等的低风险操作。

### 6.5 家庭多 Agent 系统实践

HearthNet 等工作展示了 OpenClaw、Home Assistant、MQTT、动作租约、状态版本检查和恢复机制在家庭测试床中的组合。它们说明项目工程栈与研究问题有连接，但单一测试床和小样本实验不足以支撑一般性结论。

## 7. 从现有工作中抽象出的通用问题

现有论文可以分为三类：

1. **家庭能力、训练与评测**：HomeBench、SimuHome、SMH-Bench、PersonalHomeBench、SAGE、HomeFlow。它们回答 Agent 能否理解家庭指令、接地到设备、获得可验证训练轨迹并完成任务。
2. **一般多 Agent 规划与调度**：REALM-Bench、DynTaskMAS、LLMCompiler、Agent JIT、MultiAgentBench、When Do LLM Agents Help?。它们回答多个 Agent 如何分解、并行、调度和适应动态任务。
3. **执行一致性与低延迟**：SagaLLM、ALAS、Speculative Actions、VeraRAN、SyncPlan、Agentic Fast-Slow Planning 等。它们回答计划过期、动作失效、事务补偿、推理时延和实时控制接口如何处理。

相对较少被同时研究的是：

- 共享状态在多个 Agent 思考期间持续变化；
- 多个 Agent 异步提出动作并竞争物理资源；
- 部分动作已经执行，后续计划不能简单回滚；
- 任务有硬截止时间，且不同动作风险不同；
- 系统需要同时决定执行策略、模型调用和修复范围。

这不是已经确认的空白，而是目前值得实验验证的交叉区域。

## 8. 当前候选研究命题

为了避免把所有论文启发堆入一个方案，应该区分“总问题”和“候选切入点”。一个简洁的总问题是：

> **在动态共享环境中，如何让多个 Agent 在任务依赖、资源竞争、时限和安全约束下协同完成任务，并适应执行过程中的环境变化？**

这个问题没有预先指定必须使用哪一种算法。当前可以独立比较以下候选：

### 候选 A：选择性计划修复

研究环境变化或 Agent 冲突后，系统如何判断继续执行、局部修复或全局重规划。潜在增量不是“首次提出局部修复”，而是在部分动作已执行、跨 Agent 存在间接干扰、截止时间有限时，联合决定修复范围和剩余推理预算。

优点是容易在 SimuHome 或 Home Assistant 测试床验证，不需要大规模模型训练；风险是与 ALAS、SyncPlan、VeraRAN 等存在重叠，需要严格的任务定义和强基线。

### 候选 B：HomeSpec 预测式协同执行

研究如何提前准备低风险的未来动作，降低多 Agent 执行的端到端等待，并在预测失配时快速恢复。它的创新上限较高，直接回应项目对低延迟的需求；风险是需要处理预测命中率、物理安全、资源租约、状态过期和分支浪费。

### 候选 C：风险与截止时间感知的模型路由

研究系统如何根据任务风险、剩余时间和模型延迟，在本地小模型、云端大模型和确定性策略之间选择。它实现相对容易，但仅做固定规则路由可能创新不足。When Do LLM Agents Help? 已表明强启发式在平稳负载下可能优于增加 LLM 控制层，因此这里真正需要研究的是：系统能否识别非平稳变化或启发式余量不足，并只在预期收益超过调用成本时启用 LLM。

### 候选 D：动态任务图与资源感知调度

研究任务依赖、设备资源和异步反馈下的 Agent 分配与排序。它与项目任务清单直接对应，但 DynTaskMAS 和其他计划编译工作已经覆盖通用 DAG 并行，因此家庭特有的物理资源、风险和状态有效性必须成为实质变量。

### 候选 E：Grounded Multi-Agent Execution

研究专业 Agent 如何通过能力描述、前后置条件、状态版本和执行结果进行可靠协同。SAGE 可作为直接参考，但若只实现设备 API 检索、记忆和工具调用，容易成为系统集成工作；需要与多 Agent 冲突和恢复结合才有更强的研究价值。

### 候选 F：智慧家庭多 Agent Benchmark

研究如何评估动态冲突、异步执行、实时响应和安全动作。现有 benchmark 已较多，除非能够提供独特的物理副作用、状态漂移、危险轨迹和过程级指标，否则不应优先做“大而全”的新 benchmark。

从当前证据看，候选 A 的可行性和创新性较平衡，候选 B 的创新上限较高；但二者都还需要强基线实验，不能仅凭论文比较得出最终结论。候选 C、D、E 更适合作为方法组件或较窄的备选命题，候选 F 当前优先级最低。

## 9. 建议的实验框架

### 9.1 环境与任务

第一阶段可基于 SimuHome 或等价 Home Assistant 测试床，加入：

- 连续到达的多任务流；
- 设备操作依赖和共享环境变量；
- 设备离线、用户改意图、状态漂移和并发动作；
- 不同 Agent 的推理、通信、设备反馈和验证延迟；
- 可行、不可行、需要澄清和不可安全执行的请求。

每条轨迹在模型思考期间继续推进环境，不能冻结状态等待 LLM 返回。

### 9.2 基线

建议至少比较：

1. Home Assistant 规则＋确定性 Skill＋优先级或最早截止时间调度；
2. 时间关键任务优先＋最早截止时间＋最早完成时间的强启发式；
3. 单主 Agent＋确定性执行器；
4. DynTaskMAS 或等价动态任务图方法；
5. 事件触发的全局重规划；
6. 固定周期重规划；
7. SagaLLM／ALAS 风格的验证和恢复组件；
8. 选择性修复或预测式执行的逐步消融。

所有方法应使用相同的模型、设备信息、工具权限和总预算，避免把额外的安全检查误算成算法增益。

### 9.3 指标

不能只报告最终成功率，还应记录：

- 首个有效物理动作延迟的中位数、P95 和 P99；
- 按时任务成功率和最终任务成功率；
- 资源冲突率、过程安全违反率和危险轨迹数量；
- 状态版本拒绝率、过期计划比例和重复动作次数；
- 重规划次数、局部修复范围、全局重规划比例；
- LLM 调用次数、Token/API 成本和设备等待时间；
- 不可行请求的正确拒绝率；
- 预测式方法的命中率、分支浪费率和失配后补偿次数。

紧急事件应单独报告事件检测时间和预授权动作时间，不应与普通复杂请求混成一个平均延迟。

### 9.4 泛化验证

通用性可以通过中间表示体现，而不必一开始把 Intro 写成跨领域论文。任务节点可以统一记录目标、前置条件、后置效果、资源读写集合、截止时间、风险等级、状态版本和 Agent 能力；家庭设备、房间、电源和门锁属于适配层。

如果条件允许，再增加一个小规模非家庭迁移实验，例如物流或 Job-Shop 任务，用于验证算法是否依赖具体家电名称。REALM-Bench 可以作为候选迁移环境，但不能在没有适配和重复实验的情况下直接声称广泛泛化。

## 10. 创新边界与研究风险

以下内容单独作为贡献通常不够：快慢 Agent 分工、缓存、预编排、DAG 并行、工具前后置条件、过期计划拒绝、优先级调度和一般性的 API 接入。Agentic Fast-Slow Planning 已经把慢推理、经典规划与实时控制分层；When Do LLM Agents Help? 又表明强启发式在平稳负载下可能无需 LLM。它们都可以成为实现依据或实验基线，但不能直接包装成新的核心贡献。

更有可能形成论文贡献的是一个可验证的组合关系，例如：

> 在动态共享环境中，任务部分执行且 Agent 之间存在间接干扰时，基于状态有效性、剩余截止时间和受影响范围选择修复策略，能否在不增加安全违规的情况下提高按时成功率并减少全局重规划？

或者：

> 在多 Agent 家庭自动化中，风险和状态有效性感知的预测式准备，能否降低首个后续动作的尾部延迟，并在预测失配时以较小代价恢复？

这两种表述分别对应候选 A 和候选 B，不能在没有实验支撑时强行合并成一个“大系统命题”。

## 11. 后续工作顺序

建议按照以下顺序推进：

1. 复现强规则基线，确认现有工程机制已经解决哪些 MVP 场景；
2. 测量事件检测、首个正确动作、完整完成和尾部延迟，定位真正瓶颈；
3. 构造状态漂移、任务插入、共享资源冲突和跨 Agent 干扰；
4. 分别测试全局重规划、固定周期重规划和局部修复；
5. 再判断低延迟是否需要加入模型路由或 HomeSpec 预测式准备；
6. 选择一个主命题，其余方向保留为备选、对照或后续工作；
7. 用家庭内未见布局、设备组合和任务模板测试泛化，条件允许时再做第二环境迁移。
