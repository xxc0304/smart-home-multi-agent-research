# HomeCoord-Bench 代表性任务修订规格（草案）

日期：2026-09-27  
状态：已生成 9 条隔离的配对／时序草稿并通过离线结构试跑；**没有改写候选 JSON，也没有任何草稿或候选通过领域双审**。

## 目标

保留现有研究问题：

> 多个专业 Agent 异步作用于动态共享家庭环境时，协调机制减少动作冲突需要付出多少响应时延和任务效用？

这一轮把四类冲突都纳入短期评测范围：直接设备冲突 C1、共享环境变量的间接影响 C2、共享资源容量冲突 C3、状态变化导致的过期／在途失效 C4。C1/C3/C4 当前各有隔离的任务草稿；C2 沿 HC-M06 的连续换气／制热独立仿真探针整理为独立的场景审核稿，不能冒充已接入统一事件运行时或已物理校准。此项仍是 benchmark 数据质量工作，不提出新协调算法。

候选优先顺序：

| 类型 | 现有候选 | 选择理由 | 当前阻塞项 |
|---|---|---|---|
| C1 直接设备冲突 | HC-M01（空调制冷与关机） | 动作对象清楚；已有 SimuHome HVAC 接口试验可核对开关命令 | episode 另带无关 C3 标签；制冷效果与真实热状态未校准；需要一条不冲突控制 |
| C2 间接环境影响 | HC-M06（开窗换气与制热） | 独立连续房间模型已表达开窗期间 CO₂ 下降、热量散失及制热耗电；有 CO₂ 已达标的匹配对照 | 动力学和参数未校准；场景尚未接入统一事件运行时；需审核这应称为环境干扰／效用取舍，而非安全违规 |
| C3 容量冲突 | HC-M11（书房灯与卧室空调） | 能用同一任务和动作扫描容量边界，容易构成成对对照 | 设备功率和“家庭总功率／回路功率”口径不明；持续时间是合成值 |
| C4 状态失效 | HC-M16（清洁时居民进入） | 外部事件不会单独满足“清洁完成”目标，避免 M17–M20 的目标泄漏 | 需要区分动作启动前／执行中事件；没有暂停、取消、恢复动作契约与无事件控制 |

## HC-M06：C2 间接环境影响

场景审核稿位于 `homecoord_bench/revision_drafts/20260927/HC-PAIR-C2-VENT-HEAT-REVIEW.json`。它把两个设备的不同动作通过共同房间热状态连接：开窗让 CO₂ 下降，同时让室温向室外温度变化；制热恢复舒适温度，但在窗开时会增加耗电并可能影响按时完成。冲突臂从 CO₂=1600 ppm 开始，需要换气；对照只把初始 CO₂ 改为 850 ppm，使换气动作不再需要。任务目标、温度和参数假设、截止时间网格、指标及审核问题都记录在该场景稿中。

现有 18 个冲突格点与 18 个对照格点先经乐观物理下界筛查：3 个低换气／240 秒冲突配置即使忽略热损失也不可能完成，应排除。剩余 15 个未被下界排除的冲突格点中，Independent 按时 12/15，StateGate 按时 4/15，StateGate 平均耗电 141.59 Wh、Independent 162.67 Wh；8 个 Independent 按时而 StateGate 超时的格点全都通过该下界。18 个安全对照中所有策略均 18/18 按时、平均 88.89 Wh。准确物理模型下，OracleSwitch 参考策略保留了 Independent 的按时率，因此当前结果支持“C2 需要评测持续环境状态与时间／能耗后果”，并不证明新算法缺口。该独立模型没有真实设备或 SimuHome 的窗户／CO₂轨迹，也没有模型 API 提案；开窗期间制热是成本，不自动记作安全违规。审核者应优先评判它是否构成有意义的 C2 冲突，以及模拟参数与任务设置能否接受。代表性轨迹包 `homecoord_bench/results/c2_representative_trace_packet_20260927.json` 的 10 条样例通过了内部时序、状态趋势和能耗重算检查；这只证明仿真实现内部一致，不验证环境方程。

## 每条任务进入试验前的共同要求

1. `tool_catalog` 必须给出 Agent 真正能调用的工具名、参数类型、权限、错误／回执，测试输入不得泄露 `required_action` 或模板答案。只有在研究“Agent 如何选动作”时才强制提供多个合理动作；若只用同一批固定提案比较协调策略，可以保留单一提案，但论文必须称为协调回放而非完整规划评测。
2. 任务完成目标、过程安全约束、必要服务动作、取消／拒绝状态分别记分。外部事件单独满足最终目标时，标记 `external_event_only_goal_success`，不得记成 Agent 完成服务。
3. 每个主冲突至少有一个安全配对条件，只改一个构成因素（冲突／非冲突、事件／无事件、容量低／高）。初态、任务文本、Agent 可见信息、模型提案和调用时延尽可能固定。
4. 动作须区分请求、提交、设备生效、持续作用、反馈和完成；能否中断、停止时延、停止效果及恢复方式要有字段或明确声明不支持。没有这些定义，不报告“局部修复效果”。
5. 持续时间、功率、事件概率和截止时间要标明来源。来源未核实的数值只能标为 `synthetic_range` 并做敏感性分析，不写成现实测量。
6. 每条任务要做可行性下界检查：在给定模型／设备延迟下，物理上是否可能按时完成；不可行条件要作为独立类别，不能混入协调失败率。
7. 审核人 A/B 分别检查同一固定版本，先独立填写，再记录分歧与仲裁结果。研究作者的首轮复核可作为准备材料，不能冒充独立双审。

## HC-M01：C1 直接设备冲突

保留“舒适 Agent 要求制冷，能源 Agent 要求关闭同一空调”的核心。删除不参与该命题的 C3 容量规则；把舒适请求有效区间、能源请求释放时刻、房间温度目标及最终可同时满足的状态写清楚。

配对控制至少覆盖：

- **冲突条件：** 两个有效请求重叠，操作落在设备能力表声明的互斥集合内；
- **安全条件：** 任务内容与初态不变，能源动作延后到舒适承诺结束后，或将能源动作改成可与制冷共存的设备操作；两种控制方式择其一，并确保只引入一个关键差异。

主要指标：实际互斥动作重叠率、舒适任务服务率、能源任务服务率、首次安全动作启动时延、目标进展时延、完整任务完成时间。SimuHome 目前只可验证命令映射和离散 HVAC 终态；未对真实室温响应校准前，不使用温度达标率作现实结论。

验收：动作冲突规则来自机器可读的设备能力表；冲突条件触发且控制条件不触发；两种架构收到同一模型提案和时延；安全控制中不因协调而增加不必要串行等待。

## HC-M11：C3 共享容量冲突

保持同一对并行任务和 Agent 输入，围绕 `P_A + P_B` 扫描共享容量 `C`，构造低于、等于和高于需求总和的配置。主比较至少包括 `IndependentMultiAgent`、设备／资源锁、`ConstraintCoordinator` 和透明 EDF／优先级规则。

优先用实际可查的铭牌或回路规格核对负载。若当前没有可靠来源，明确称为抽象功率资源冲突，使用标记过的范围（例如容量上下浮动），避免把书房灯的假设功率描述为真实值。任务目标需使“拒绝低优先级任务”与“同时服务”有可观察的任务服务率差别；容量安全条件不得只依赖互相矛盾的文本规则。

配对控制只改变容量 `C`，其余保持一致；控制侧需能安全并行完成两项任务，以检测协调器是否过度串行。分别报告容量违规事件次数与持续时间、按时任务成功率、服务率和首个动作／全部完成时延。

验收：相同动作在低容量条件下确实同时超限，在高容量条件下可并行；每个单动作都可单独执行；若其中任一条件不成立，不能用该任务证明协调价值。

## HC-M16：C4 外部状态变化与在途动作

保留清洁动作和“有人进入时扫地机器人不得运行”这一清楚的约束。不要把状态事件本身当作清洁完成。第一轮先构造三个时间臂：

| 时间臂 | 事件时刻 | 该臂检查的情况 |
|---|---|---|
| 前置变化 | 动作尚未启动 | 根据新状态安全拒绝／延期，区分目标未完成与违规执行 |
| 在途变化 | 动作已启动、尚未完成 | 事件改变运行前提；记录是否能停机、停机期间违规持续多久、是否恢复任务 |
| 无事件配对 | 无居民进入事件 | 验证在普通条件下不会无故取消或过度重规划 |

若后续要声称“可取消／局部修复”，episode 还必须定义：机器人是否可中断、停止命令延迟、取消后的状态、部分清洁进度、居民离开后的重试释放条件和完成期限。先不要在候选文件里凭空设置这些参数；应先找到设备规格／模拟器语义，或把它们作为显式合成变量并标注敏感性范围。

主要报告当前已实现的三个分项：`stale_at_action_start_count`、`in_flight_precondition_invalidated_action_count`、`unsafe_state_onset_during_action_count`；并列任务服务率、过程违规持续时间和最终目标成功。`conflict_counts.C4` 只算实际执行的 stale action，安全拒绝不等于任务完成。

验收：事件发生在动作开始前时，安全拒绝要被记录但不能误报为冲突动作已执行；事件发生在动作期间时，环境应保持运行并暴露失效，而不是暂停时间等待 Agent；无事件控制中清洁任务可服务；若无任务恢复契约，只能研究状态失效诊断，不能声称展示了局部修复。

## 草稿离线试跑结果

已由生成脚本将 M01、M11、M16 的副本保存在 `homecoord_bench/revision_drafts/20260927/`。目录在 `data/` 之外，不进入 benchmark 正式数据审计或评分；所有草稿标记为 `proposed_revision_not_scored`。一组确定性 DryRun 结构试跑验证了配对是否能表达预定机制：

| 草稿对 | 主要结果 | 解释边界 |
|---|---|---|
| C1 HVAC 冲突／安全对照 | 冲突臂 Independent 的 C1=1、Constraint 的 C1=0；协调将 `peak_off` 完成推迟 5,800 ms。安全对照中两者均 C1=0，协调未再增加等待。 | 合成动作时长；没有真实室温校准；只证明这组回放可表达“冲突任务延迟、非冲突控制不被拖慢”。 |
| C3 低／等于／高容量 | 低容量臂 Independent 的 C3=1、Constraint 的 C3=0，全部任务仍服务，协调令全局完成晚 900 ms；等于 1.5 kW 的临界容量和 1.7 kW 控制中两个策略均 C3=0，完成时间相同。 | 1.2／1.5／1.7 kW 和各设备功率是占位值，仍需核实家庭／回路口径及来源。 |
| C4 无事件／提交前／在途／动作后事件 | 提交前臂记录 1 次 stale 安全拒绝、无违规；在途臂记录 1 个前置条件失效、1 次安全状态转坏、违规持续 2,900 ms；无事件与动作后事件控制无过程违规。 | 这是不可取消动作的诊断原型，**没有**展示取消、补偿或局部修复；时延是人为边界值。 |

HC-M06 的 C2 连续环境探针不是上述 9 条事件 episode 草稿之一，其结果和边界单列在 `docs/VENTILATION_HEATING_TRADEOFF_PROBE_2026-09-27.md`。不能把它的连续动力学结果与事件运行时的固定提案矩阵合并为一组实验。

草稿在内存中逐条通过事件运行时输入校验，行为回归测试验证冲突／安全配对确实被区分。C4 提交前与在途臂现统一使用 300 ms 提案延迟，分别在 350／500 ms 注入进入事件，消除了旧版 400／300 ms 提案延迟的混杂因素。字段级机器审计及独立审核任务包见 `docs/REPRESENTATIVE_DRAFT_REVIEW_PACKET_2026-09-27.md`。当前证据只说明草稿结构和评测指标工作，不说明模拟参数可信、策略泛化或算法创新；九条草稿均无完成截止时间，不能声称检验了硬截止时间调度。

## 本草案不支持的结论

- 不证明 C1–C4 已穷尽多 Agent 冲突。
- 不证明普通协调器存在无法解决的冲突，也不提出新算法。
- 不把合成时延、功率、模拟器默认方程写成实际部署性能。
- 不因 20 条任务结构校验通过，就称数据集已经通过领域双审。
- 不预设 HomeBench 或 SimuHome 的录用原因；本项目需要用自身实验说明问题为何重要。
