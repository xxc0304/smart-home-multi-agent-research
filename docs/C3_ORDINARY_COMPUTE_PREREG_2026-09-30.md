# 普通协调与重试计时：运行前协议

使用E2双模式结构复验5个完整真实提案批次，保留网络失败不补API。策略为GateRetryRule、ConstraintCoordinator、DeadlineAwareCoordinator，均不得改变提案模式。每批每策略3次零延迟回放测本机dispatch回调耗时，共45次；另固定容量3、双fast、三提案800ms同时到达的脚本结构3次，确保校准重试路径。合计48次校准回放。

dispatch计时范围：工具授权、动作落地、候选起点/资源安排、预约记录和入队。retry_batch范围：已等待重试的批次排序、资源安排、预约记录和入队。两阶段按策略汇总所有校准观测的中位数，ceil至整数ms，再锁定profile与校准结果哈希。没有观测的重试阶段记0且显式注明not_observed；不能当作测得0ms。时钟分辨率会使亚毫秒函数收1ms，必须并列报告原始墙钟和注入值。

独立配对回放5批×3策略×零/校准延迟=30运行；脚本重试结构零/延迟=2运行；另同一脚本结构测试无关版本变化、必要条件在计算中失效=2运行。总计82运行，不新增API。输入/模式/返回延迟保持，不调期限制造失败。

计时采用一个FIFO协调计算worker：dispatch按提案/批次可调度时刻入队，retry_batch仅在资源释放且确有重试任务时入队，一批收费一次。期间状态/任务/动作完成照常推进；完成后按最新预约与状态安排，再经过命令延迟和启动前安全复核。这是校准成本回放，不是逐次实测耗时在线精确注入；profile只给阶段/策略的常数成本，不读取未来事件/答案。

EDF收齐/排序前端、启动安全门控、序列化、通信及API本身不在dispatch计时内。上一轮public_plan耗时和本轮公共执行路径开销范围不同，不能将两个表作为全部算法端到端耗时排名。普通策略控制之间同范围比较；完整架构时延仍待新实验。

审核原模型延迟、零延迟与原成果一致；job开始/完成一一对应且无worker重叠；任何预约不早于对应完成事件；命令100ms保留；重试次数/任务和本机测量分列，未发生重试不收费；必要条件失败不启动且缺失指标null，无关版本变化不拒绝。报告等待增量与按时结果，允许校准计时改变资源事件顺序，不强求每项任务仅增加一常数。
