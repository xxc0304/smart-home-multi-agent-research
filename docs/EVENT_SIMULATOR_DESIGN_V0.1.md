# HomeCoord-Bench 事件仿真环境设计 v0.1

## 目的

在真实家庭设备尚未接入时，先用可复现的虚拟时钟检验多 Agent 家庭任务的提案延迟、异步返回、共享状态变化、动作冲突、资源占用和任务截止时间。当前环境是研究原型，目标是把实验假设写清楚并暴露问题，不替代 HomeBench、SimuHome 的环境实现，也不声称已经复现真实家庭物理。

HomeBench 的虚拟家庭重点是设备、属性、可调用方法以及自然语言指令能否映射为有效操作；其论文说明虚拟执行避免了真实设备机械延迟。HomeCoord-Bench 在这个基础上另建一条**协调时间线**：多个任务与 Agent 的提案何时返回、如何排序、设备何时开始及何时完成、期间状态是否变化。两者服务于不同的研究问题，不应把动作 API 覆盖数量当成 HomeCoord 环境的充分性。

### 与相关家庭评测环境的边界

| 环境 | 主要评测对象 | 时间／状态推进 | 主要观测指标 | 当前多 Agent 协调覆盖与差距 |
|---|---|---|---|---|
| [HomeBench](https://aclanthology.org/2025.acl-long.597/) | 家庭指令有效性、单／多设备 API 操作和完整任务执行 | 以虚拟家庭状态和操作序列核验结果；论文指出没有模拟真实设备机械延迟 | 整条请求成功率、操作级 F1 | 多设备任务不等于多个自治 Agent；借鉴有效／无效任务和部分正确度量，本项目需额外记录并发提案和协调成本 |
| [SimuHome](https://proceedings.iclr.cc/paper_files/paper/2026/hash/43456e781fac3a034842f0807860474a-Abstract-Conference.html) | 时间与环境感知的家庭 Agent 任务 | Matter 风格设备、时间推进、环境变化和工作流执行 | 任务类别表现、工作流完成与状态／时序一致性 | 提供动态家庭任务测试床；异步多 Agent 冲突不是其主要评测轴，环境动力学比当前原型丰富 |
| **HomeCoord-Bench 当前原型** | 动态共享状态下多 Agent 的异步提案、冲突、设备启动／完成时序及截止时间 | 离散事件钟；回放记录的逻辑调用延迟、外部事件和动作完成 | 过程安全、冲突、任务服务、按时完成、设备启动／目标进展／任务完成时延 | 多 Agent 协调是当前核心变量；有限状态转移和合成物理参数尚不足以宣称达到 SimuHome 的家庭环境覆盖或真实度 |

这张表用于说明互补关系，不是环境质量排名。HomeCoord 当前确实已有一个可运行的虚拟环境，但它更准确地说是**协调器的离散事件实验台**，还不是完整家庭模拟器。正式 benchmark 若要声称环境接地与可迁移性，需要进一步证明任务和状态动力学可靠；最省风险的路径是先做一小批与 SimuHome 或等价家庭仿真器的任务映射可行性检查，核对接口、许可和状态语义，再决定复用外部环境还是扩充自己的动力学。无需一开始从头实现完整热力学或真实设备网络栈。

当前数据规模也提示了原型的边界：34 条 episode、68 个任务里，原始 episode 明确带外部事件的有 7 条（共 9 个事件），明确设置完成截止时间的任务有 4 个；敏感性探针会在副本中额外扫描合成截止时间。89 条 grounding 是动作能力记录，不等于 89 个已审核物理动作。可中断动作、持续温湿度变化、传感器反馈与设备停止时延尚未建模。因此当前适合验证事件顺序和协调逻辑，不足以单独代表广泛的动态家庭 benchmark。

还要把“运行次数”和“任务覆盖”分开看：本轮 674 是同一批有限 episode 上的策略比较、敏感性扫描和反事实回放次数，不是 674 个独立任务。[HomeBench](https://aclanthology.org/2025.acl-long.597/) 报告 100 个家庭场景与超过 17 万条指令，[SimuHome](https://proceedings.iclr.cc/paper_files/paper/2026/hash/43456e781fac3a034842f0807860474a-Abstract-Conference.html) 报告 600 条 episode；这类规模和场景覆盖也是 benchmark 可信度的一部分。HomeCoord 下一版应优先扩充经过审核的任务／配对和环境扰动维度，而不是把同一小批任务多跑几遍就说覆盖充分。

因此，论文贡献不能只写“我们也做了一个智慧家庭模拟器”。需要说明现有环境缺少什么评测变量、为什么家庭任务能稳定实例化这个 Agent 问题、任务标签和指标如何被独立验证、相较强基线实验揭示了什么可复现的规律。当前期限小样例已被普通 EDF 规则解决，反而说明后续必须用更广的审核情境检验 benchmark 能否区分策略，而不能只展示自建环境可以跑通。

## 一条 episode 的执行过程

```mermaid
flowchart LR
    A[任务发布] --> B[Agent 读取当时可见状态]
    B --> C[提出一个结构化动作]
    C --> D[按记录的模型调用时延排入虚拟事件队列]
    D --> E[提案返回]
    E --> F[协调策略决定接收、拒绝或延后]
    F --> G[设备动作启动]
    G --> H[应用启动效果并更新共享状态版本]
    H --> I[外部事件和其他任务继续推进]
    I --> J[动作完成]
    J --> K[应用完成效果并更新共享状态]
    K --> L[确定性评测器检查安全、冲突、服务、时延和截止时间]
```

同一时刻的事件按稳定优先级处理，保证外部状态更新和设备完成先于后续任务读取状态。提案返回以记录或指定的逻辑调用时延安排；当前 Python 决策接口仍然顺序调用 provider，不能据此报告真实并行 API 的墙钟速度。

对固定 episode、策略、提案内容和提案时延，事件时间线可确定性重放；请求 ID 在事件模拟器中也由 episode／策略／任务稳定生成。真实模型若重新采样出不同提案或不同调用时延，轨迹仍可能不同，因此随机模型输出实验应保存原始提案与时延供后续离线重放。

仓库保留的旧 `run_closed_loop.py` 原型会在 `action_effective` 时一次性应用完整效果补丁；它适用于较早的闭环协议测试，不表达动作启动／完成分离。需要物理生命周期或持续时间结果时，应运行这里的一键事件环境，它才会遵循 episode 中 `start_effects` 和 `completion_effects` 的标注。

## 当前环境包含什么

| 部分 | 当前实现 | 证据边界 |
|---|---|---|
| 家庭与任务 | Episode 描述设备状态、Agent 能看到的状态、任务发布时刻、目标和截止时间 | 种子与候选数据仍要领域人员复核；候选不可当金标准 |
| Agent 提案 | 支持 DryRun，以及对保存的 DeepSeek 提案和调用时延重放 | 固定提案重放只比较协调，不代表每种架构独立调用模型 |
| 虚拟事件钟 | 任务发布、提案返回、动作启动、动作完成和外部事件进入事件队列 | 逻辑并发回放，不是真实多 API 并发 |
| 动作周期 | 区分 `start_effects` 与 `completion_effects`；动作持续时间和功率由环境数据决定 | 物理参数是假设或公开规格估算，尚未设备校准；连续温度、电量变化未模拟 |
| 在线策略 | 独立执行、设备锁规则、约束／容量协调、已发布任务的截止时间优先基线 | DeadlineAware 是普通强基线，不是论文的新算法 |
| 评估指标 | 过程安全、C1–C4、任务服务、截止成功、首次设备启动、首次目标进展、动作完成 | 外部事件导致运行中违规时会记录区间，但尚不会自动取消动作 |

## 当前可复现批次

```powershell
python homecoord_bench/run_event_pilot_suite.py
```

该命令截至 2026-09-26 汇总通过 95 项单元测试，并执行 34 条 episode × 5 策略事件矩阵（170）、28 组保存提案 × 2 个配对条件 × 4 策略离线回放（224）、截止时间敏感性扫描（200）和提案延迟次序反事实（80）；合计 674 次仿真或重放，不发起模型 API 请求。9 项适配轨迹测试只校验日志契约；新增 2 项期限可行性测试和 2 项基线覆盖测试分别审计当前数据与策略覆盖，不表示运行了第三方环境。汇总在 `homecoord_bench/results/event_pilot_suite_20260926.json`，34 条 episode 的运行时输入审计在 `homecoord_bench/results/event_episode_validation_20260926.json`。

事件模拟器现在在排队前校验时间戳、Agent／任务引用、唯一任务 ID、约束条件、grounding 数值和容量配置。固定时刻的外部更新先于同刻任务读取状态；回归测试会直接检查 Agent 请求快照。若单个动作功率已经超过 C3 容量，协调器会留下 `resource_capacity_exceeded` 拒绝记录，而不是抛异常中止整条 episode。这个改动只让边界行为可审计，不增加新的物理或算法主张。

本批数据有一项重要负结果：低容量、紧截止时间的 EV／热水器小样例中，先到先处理的 ConstraintCoordinator 会有 1/5 次 EV 超时；简单 DeadlineAware 基线将这 5 次全部按时、安全完成，但首个动作启动中位数增加约 228 ms。当前样例说明评测环境能揭示安全、时效与等待之间的影响，也说明此结果可被常规规则解决；它没有证明需要新算法。

## 必须分开的三种时间

- `first_action_start_latency_ms`：首个通过检查并开始执行的设备动作相对任务发布的延迟，主要回答“设备何时开始响应”。
- `first_goal_progress_latency_ms`：首次安全地改变任务目标状态的时间，可能包含物理工作时长。
- `task_action_finish_time_ms`／`task_completion_time_ms`：具体任务动作完成时间／全局目标首次满足时间。

例如，热水器动作开始后要运行一段时间才达到目标水温。只报告“首个有效动作”会把设备响应时间和热水加热时间混成一个数，因而实验表格应分别报告启动、目标进展和完成。

## 不能省略的后续验证

1. **先确认环境选型。** 用 3–5 个代表任务做一次小型环境适配试验：检查 SimuHome 或等价环境能否表示 Agent／工具、共享状态、并发动作、动作进度、截止时间和轨迹导出；同时核对许可。若关键协调变量无法表达，再在当前离散事件台上逐项补齐，避免盲目重建成熟的家庭环境。
2. **审核任务和可行性。** 为冲突 episode 建立匹配的无冲突对照；双人复核动作效果时点、可中断性、硬约束和每个截止时间是否物理可行。保留原始标签与修订记录。
3. **加入强而透明的比较基线。** 至少比较独立执行、设备锁、约束／资源检查、EDF／截止时间优先，以及共享状态重验证。基线只用当时可见信息，并把等待和查询开销计入延迟。
4. **让模型架构公平交互。** 中央单 Agent、专业多 Agent 和协调器各自生成提案；固定同一模型、提示、工具、可见状态和调用预算。先小样本估算费用，再由用户决定是否扩大 API 批次。
5. **校准物理和执行反馈。** 优先用公开设备规格或可复现的家居仿真校准功率、持续时间和状态转换；之后才接真设备。命令确认、动作启动、实际完成、传感器上报和停止响应须分别记时。
6. **扩展动态执行模型。** 明确定义外部事件触发后的停止延迟、设备是否可中断、不可逆动作和局部恢复成本。先实现可重放模型，再决定是否值得做硬件在环。

阶段 1–2 验收后，才判断 benchmark 是否具有稳定、可复现且区别于简单规则的发现；若强基线覆盖全部现象，应调整研究主张，而不是人为制造规则例外。
