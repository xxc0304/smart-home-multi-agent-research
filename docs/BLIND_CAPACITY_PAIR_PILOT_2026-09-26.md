# HomeCoord-Bench 盲测容量配对小试验

2026-09-26。**结论：在一个干净输入的合成任务中，完整观察到了“模型提案并发→低容量冲突→在线协调等待→高容量对照无额外等待”的因果链；仍不足以作为论文总体证据。**

## 设计

以书房照明与卧室制冷为两个异步任务，给每个专业 Agent 两种可调用动作及其参数签名。模型看得到任务目标、可观察设备状态与动作目录，**看不到 `required_action`、`action_template` 或未来提案**。每组 DeepSeek `deepseek-flash` 只生成一次两 Agent 提案，并记录调用耗时；同一提案和耗时分别回放到 1.2 kW 低容量与 1.6 kW 高容量家庭，再分别运行独立执行和因果在线强规则。容量是唯一环境差异。设备动作耗时和功率继承未经校准的 HC-M11 合成候选任务。

8 组配对、16 次成功逻辑调用；另有 2 次失败尝试后重试。真实模型输入 19,627 tokens、输出 2,882 tokens（含失败尝试）。单次成功 API 请求耗时中位数 1462 ms、最近秩 P95 2606 ms。API 调用在墙钟上顺序进行，回放时按各自调用耗时放入逻辑异步时间线，不能视作真实并发部署响应。

## 结果

| 条件 | 无协调 | 在线强规则 | 目标首次满足时间增量 |
| --- | --- | --- | --- |
| 低容量 1.2 kW | 7/8 组出现 C3 超容量冲突；1/8 因提案到达间隔足够大而天然安全 | 8/8 无冲突、两任务均获服务 | 7 组增加 510–2859 ms；1 组 0 ms。8 组中位增量 796 ms |
| 高容量 1.6 kW | 8/8 无冲突、两任务均获服务 | 8/8 无冲突、两任务均获服务 | 8/8 为 0 ms |

16 个模型动作均能按公开动作目录落地；8 组均选择照明与制冷目标动作，没出现格式正确但无法执行的提案。两种容量下，协调前后**首个有效动作时间均未改变**。低容量的等待是为避免两个已提议动作功率相加超过容量，属于此合成调度模型内的必要排序时间；没有测得规则计算、状态同步、网络与设备反馈开销。

## 解释与边界

这组配对比旧试验干净：没有动作答案泄漏、同提案控制了模型采样差异，高容量条件提供了明确负对照；1 组天然安全也证明我们没有强行让每次运行都发生冲突。它可以作为论文实验设计的**最小有效样例**。

但任务只有一个基础模板，且模型的两个动作选择很容易；目标状态在仿真中随动作开始立即更新，目标首次满足时间不等于真实制冷完成时间。功率与时长没有设备校准，容量规则已知且足以解决问题。因此它证明评测框架可以量化一个条件性安全—等待取舍，**没有证明新算法的必要性，也不能据此报告多 Agent 系统的一般冲突率或真实部署时延**。下一步应在不同容量任务、负对照和经审核的设备语义上重复，加入执行时长／反馈与真实协调成本。
