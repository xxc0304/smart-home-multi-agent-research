# C3 电动车／热水器：强规则的信息边界敏感性

日期：2026-09-27。性质：**未校准的合成压力试验**，用于检查现有强确定性规则依赖什么公开信息；不是新算法、现实家庭统计或模型端到端测试。参数来源缺口见[核查表](C1_C3_PARAMETER_PROVENANCE_2026-09-27.md)。

## 问题与设计

在[共同安全门控回放](C3_EV_WATER_COMMON_GATE_REPLAY_2026-09-27.md)中，容量感知期限规则看起来同时兼顾低容量的按时率与高容量的响应速度。但它读取两个任务的公开额定功率上界。若这些上界不准确或缺失，其优势是否仍成立？

使用同一电动车／热水器任务模板、两种合成容量（6.0/7.2 kW）、5 组历史 DeepSeek 调用耗时、三种已有强规则（容量先到先安排、始终等待按期限排序、容量感知等待）、4 种公开功率上界状态，以及 0/300/800 ms 人工协调延迟，共 180 个事件回放单元。只有容量感知规则使用公开上界；其他规则不重复跑无关的上界格点。物理动作、真实功率、任务目标及共同安全门控均固定。没有新 API 调用或真实设备。

上界状态为：准确（充电 4.0、加热 3.0 kW）、充电低报（2.0、3.0 kW）、充电高报（5.0、3.0 kW）、缺失。历史提案耗时是顺序调用后做的逻辑异步回放；仅一组出现“热水提案先返回”。因此 5 组是**同一任务的五条时延轨迹**，不是五个独立家庭样本。

## 0 ms 人工协调延迟下的关键结果

| 合成容量与热水先返回的轨迹 | 容量感知规则：准确上界 | 充电上界低报 | 充电上界高报或缺失 |
|---|---|---|---|
| 低容量 6.0 kW | 等待充电提案，两项均按时；首动作 1524 ms | 误判可并行，热水先占用容量；两项都得到服务，但充电错过合成期限；首动作 1344 ms | 等待，两项均按时；首动作 1524 ms |
| 高容量 7.2 kW | 直接启动，两项均按时；首动作 1344 ms | 直接启动，两项均按时；首动作 1344 ms | 白等另一提案，两项仍按时；首动作 1524 ms |

在五条历史时延轨迹中，低容量、准确上界和保守高报／缺失均为 5/5 两项按时；低报与先到先安排均为 4/5。高容量所有策略均为 5/5 两项按时，但高报／缺失与始终等待在唯一热水先返回的轨迹上使首动作多等 180 ms。所有 180 单元均完成两项必要服务、无过程容量冲突；共同门控没有拒绝。**安全、服务完成、是否按时和首动作时延是四个不同结论。**

人工协调延迟 300/800 ms 在这组小时级合成期限下没有改变按时计数，只把相应动作时间后移。它不是实测规则处理耗时，结果 JSON 明确标为 `synthetic_coordination_delay_ms`，并记录 `actual_rule_wall_clock_measured=false`。因此本试验不能回答真实部署的规则、模型、网络和设备各段耗时，尤其不能证明 1 秒响应目标已满足。

## 研究判断和下一步

此试验把此前“强规则几乎完美”的判断限定为**公开上界准确且可见**的条件：低报会损失紧迫任务的按时性，高报或缺失会增加安全场景中的等待。共同门控只保证不超容量，并不能替规则恢复期限收益。可是当前调度器在提案返回后仍使用合成环境中的真实动作功率与时长做预约，故这里测到的误差敏感性还是**乐观下界**，不能称为现实不确定性鲁棒评估。

这说明 benchmark 可以有一个清楚的条件维度：**协调决策依据的信息是否可靠**。它还没有证明需要学习型协调器。下一轮应先由领域审核者决定这些设备、容量实施点和期限能否形成可信任务；若只能作为合成子集，就明确标注。随后在多个独立任务模板中预先定义信息可见性和误差分布，比较同等信息下的强规则、保守等待与可能的新方法，并实测各段延迟；若强规则仍占优，应如实报告。
