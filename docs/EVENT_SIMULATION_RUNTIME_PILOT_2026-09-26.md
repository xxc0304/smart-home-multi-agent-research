# HomeCoord-Bench 离散事件环境原型记录

日期：2026-09-26  
阶段：研究环境原型与确定性冒烟验证；不是正式 benchmark 结果。

## 本轮完成

新增 `homecoord_bench/runtime/event_simulator.py`，把任务发布、提案返回、设备启动、物理完成和外部状态变化统一放到虚拟时钟上。动作的最终效果可以等到 `action_completed` 才写入状态；虚拟时钟按提案逻辑返回时刻处理，因此一个后发、低延迟的提案可以先于先发、高延迟提案返回。为旧版数据保留 `effects` 兼容路径；持续动作的新数据可以用 `start_effects` 与 `completion_effects` 分别写出设备运行态和完成态。

协调策略在动作启动前检查当前启动状态和预计完成状态。运行期间的外部状态变化也会触发约束检查；结果记录安全状态到违规状态的转换次数和违规持续时间。若外部事件在动作进行中造成违规，原型会准确暴露该违规，但目前不会假设设备支持中断，也不会自动取消动作。

新增 `run_event_simulation_matrix.py`，对当前 34 条数据分别运行 `CentralSingleAgent`、`IndependentMultiAgent`、`RuleCoordinator` 和 `ConstraintCoordinator`，共 136 次确定性 DryRun。逐情境时间线、状态和指标保存在 `homecoord_bench/results/event_simulation_matrix_20260926.json`。此入口排除配对数据目录下的 `manifest.json`。

## 回归与冒烟验证

新增事件语义测试覆盖：

- 提案返回顺序由逻辑调用时延决定，而非任务发布顺序；
- 状态目标在动作完成时生效，而非动作启动时生效；
- 协调器能在启动前拒绝预计会违反约束的完成效果；
- 外部变化可在长动作执行期间造成可观测的安全违规区间；
- EV 充电、热水加热分别表达“正在工作”和“工作完成”状态。
- 设备首次启动时延与目标首次进展时延分别报告，避免把长动作的能量消耗时间当成命令响应。

该批原始事件仿真运行时，整个 HomeCoord-Bench 测试套件为 82 项；随后新增的模拟器适配轨迹契约测试先将当时总数扩展到 86 项。截至 2026-09-26 最新事件套件已通过 95 项测试，其中新增 2 项核验截止时间可行性、2 项核验基线覆盖；新增测试均不代表第三方模拟器已运行。批量事件矩阵完成 **34 条 episode × 5 种策略 = 170 次运行，0 个运行错误**。五种策略为四种既有架构策略及新增的透明截止时间基线。事件仿真结果中的 `first_action_start_latency_ms` 是首个设备动作通过检查并启动的时间；`first_goal_progress_latency_ms` 是第一次有效改变任务目标状态的时间。历史字段 `first_effective_action_latency_ms` 保留为后者的兼容别名。新增 episode 运行时输入审计发现 34 条全部符合当前事件队列契约；自身功率超过容量的动作现在在协调阶段被拒绝并留下轨迹，不再中断整条运行。

## 冒烟结果如何读

这些数值只核对引擎是否产生预期可区分轨迹，不能作为模型能力或方法效果的估计：

| 子集 | CentralSingleAgent | IndependentMultiAgent | RuleCoordinator | ConstraintCoordinator | DeadlineAwareCoordinator | 解释 |
|---|---:|---:|---:|---:|---:|---|
| 4 条种子 | 4/4 | 3/4 | 3/4 | 4/4 | 4/4 | C1–C4 基本冲突路径能在新时间语义下执行 |
| 8 条配对试验 | 8/8 | 3/8 | 6/8 | 8/8 | 8/8 | C1 配对中，不协调动作会造成更多无效轨迹；设备锁规则已解决部分冲突 |
| 2 条物理容量假设 | 2/2 | 1/2 | 1/2 | 2/2 | 2/2 | 6 kW 容量冲突会使独立执行超载；容量协调可将加热延后；7.2 kW 对照允许并行 |
| 20 条候选 | 10/20 | 0/20 | 1/20 | 10/20 | 10/20 | 候选未双审，部分动作仍缺少显式生命周期标注；结果主要用来暴露数据语义和事件建模问题 |

上表报告 5 种策略的过程有效数。DeadlineAware 只在尚未返回的**已发布任务**提案都返回后，按截止时间、优先级排序，再运行相同的约束／容量检查；额外收集等待体现在首个设备启动时延中。它是解释结果的基线，不是新算法。

在两条带有中途状态变化的候选中，机器人清洁情境 HC-M16 在住户进入后至清洁动作结束期间保持 2,601 ms 的违规状态；灌溉情境 HC-M17 在降雨开始后至动作结束期间保持 2,101 ms 的违规状态。即使结束状态恢复安全，过程仍应判为无效。这个结果支持把“过程中安全状态”纳入评测，但**不证明现有协调器无法解决**：环境目前没有中断动作的能力模型，协调器也没有设备停止接口。

物理容量情境中的作用时长由公开的能量方程及明确假设生成，不是设备数据。时延矩阵使用 DryRun 的 1 ms 默认逻辑时延；单独回归测试通过设定 100/900 ms 的逻辑时延验证了异步返回排序，不产生真实 API 并发、推理时延或设备反馈时延结论。

随后又把已有的 28 组 DeepSeek 决策和实测调用时延离线重放到新环境，在四种在线策略间比较，共 224 次策略运行，未新增 API 调用。配对冲突、容量对照和任务时延的详细结果见 `docs/RECORDED_EVENT_REPLAY_PILOT_2026-09-26.md`。该回放使引擎与真实模型输出接通，但仍是固定提案下的协调策略比较。

另有 5 组 EV／热水器提案被重放到五档 EV 截止时间、两种容量和四种策略中，共 200 次运行。低容量下在 310／320 分钟档，先到先处理的 ConstraintCoordinator 有 1/5 次 EV 超时；普通截止时间基线把这 5 次都按时完成，同时将首个设备动作启动中位数增加约 228 ms。高容量对照无需安全排序，但 DeadlineAware 仍承担这段提案收集等待。详细数字、物理假设及指标边界见 `docs/EVENT_DEADLINE_SENSITIVITY_PILOT_2026-09-26.md`。这说明当前小样例上的取舍能被普通规则消除，因而不是新算法证据；它说明 benchmark 还要评估强基线和其他任务目标。

为了隔离“提案返回顺序”本身的影响，又固定五组 EV／热水器模型决策，只交换两名 Agent 已记录的调用延迟；在低／高容量、两种延迟次序和四种策略下共重放 **80 次**。这个反事实检查与截止时间扫描分开保存于 `homecoord_bench/results/proposal_order_sensitivity_20260926.json`，只用于确认异步排序是否会改变轨迹，不代表重新测量模型时延。

## 解释边界与仍需完成

1. **本轮是软件环境搭建，不是新的模型实验。** 批量结果由确定性 DryRun 生成，无 API 调用，无模型间比较。
2. **候选数据不能据此定量论证论文主张。** 20 条候选仍需人工双审；设备能力、运行态和完成态应逐条核对。旧 `effects` 对未拆分任务仍按完成效果处理。种子集的动作能力现已迁到 episode 数据中，但其设备设定仍是任务原型而非校准规格。
3. **运行中的安全机制尚未闭环。** 需要为可中断设备明确停止命令、停止延迟、停止后的物理状态和不可逆任务的处理，才能比较“预防违规”和“发生变化后局部修复”。
4. **在线时延仍是分段模拟。** API 调用没有真实并行发出，协调计算耗时、网络传输、设备确认和状态反馈也未纳入墙钟测量。
5. **未上传 GitHub。** 原有工作区存在大量其他未提交内容，本轮只新增/修改当前研究任务相关文件。

下一步建议先对 HC-M16、HC-M17 和 C1/C3 配对样例完成运行态／完成态双审与动作可中断性定义，再决定是否把这种执行中状态变化纳入正式 benchmark 批次。暂不扩充算法主张。
