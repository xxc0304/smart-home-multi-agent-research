# HomeCoord-Bench：信息边界—提案—执行结果配对试验

2026-09-26。**结论：得到一条可信但范围很窄的机制证据链；尚未证明完整的“冲突—时延”论文主张。**

## 问题与设计

同一个节能 Agent 要判断是否关闭客厅空调。舒适请求生效时，关闭空调不合适；请求未生效时，关闭非必要空调是合理的。我们用一个 2×2 信息干预区分：是否看到 `comfort_active` 状态事实、是否看到“请求生效时不得强制关机”的条件约束，并设置请求未生效的负对照。舒适 Agent 每组独立生成一次制冷提案，随后在组内复用于六种节能 Agent 条件。DeepSeek `deepseek-flash` 每条件独立调用 10 次，共 70 次成功逻辑调用（10 次舒适任务，60 次节能任务）。条件次序在每组内打乱。

所有模型请求都去掉了评测用的 `required_action`、全局标准答案 `goals` 和未来提案；条件名称也没有送入模型。节能 Agent 看到的任务目标、设备状态、工具和协议一致，只改变上述事实与约束。两种负对照把事实设为 `comfort_active=false`。

每个真实模型提案用相同的合成时间线回放：舒适动作在 1500 ms、节能动作在 1800 ms 到达；环境动作效果由现有种子任务定义。**所有基线都先检查动作自带的 `requires` 前提**；只有前提成立才会执行。在线安全门再用当时可见的舒适请求状态拦截不安全关机，不查看未来提案。此回放只隔离提案质量与安全门的作用；1500/1800 ms 不是实测 API 或真实设备时间，门控耗时也未计入。

## 分层结果

| 舒适请求 | 节能 Agent 可见信息 | 关机提案 | 前提检查后仍可执行的冲突关机 | 无协调过程有效 | 在线安全门过程有效 |
| --- | --- | ---: | ---: | ---: | ---: |
| 生效 | 事实、约束均不可见 | 10/10 | 5/10 | 5/10 | 10/10 |
| 生效 | 仅事实 | 8/10 | 3/10 | 7/10 | 10/10 |
| 生效 | 仅条件约束 | 6/10 | 2/10 | 8/10 | 10/10 |
| 生效 | 事实＋条件约束 | 0/10 | 0/10 | 10/10 | 10/10 |
| 未生效 | 仅事实 | 10/10 | 10/10（合理关机） | 不适用 | 不适用 |
| 未生效 | 事实＋条件约束 | 10/10 | 10/10（合理关机） | 不适用 | 不适用 |

同一组配对中，从“只见事实”改成“事实＋约束”时，有 8 组由关机提案变成不提议关机，反向 0 组；但这是**同一任务模板**的重复采样，不能当作跨家庭或跨模型的普遍概率。负对照 20/20 均提议并能够执行关机，说明“事实＋约束”条件下的 0/10 关机不是模型无条件拒绝节能任务。

最重要的核查是执行前提：在“只见事实”的 8 个关机提案里，5 个写了当前不满足的守卫条件，因此不能直接算成 8 次冲突；真正会执行并产生冲突的是 3 次。“只见约束”的 6 个关机提案中，4 个也被自身前提挡住。在线安全门消除的是剩余 5、3、2 次可执行冲突，同时相应放弃这些节能动作；**没有测得安全门增加了时延**。部分提案的 `reason_code` 与动作／前提并不完全一致，评分应依据可执行轨迹而非模型自述理由。

本轮 70 次成功调用的单次 API 耗时中位数为 1193 ms、最近秩 P95 为 1711 ms，最大 2551 ms；另有 3 次失败尝试后重试。累计输入 66,330 tokens、输出 9,327 tokens（含失败尝试）。这些是顺序发起请求的服务端往返测量，不能直接当作并行多 Agent 端到端响应时间。

## 对论文命题的判断

这轮实验支持一个具体的 benchmark 价值：同一 Agent 目标与设备状态下，**信息可见范围改变其提案；动作前提又改变提案是否真的造成冲突；在线协调只需处理前两层剩余的冲突。** 如果把三层混成一个“冲突率”，会夸大问题，也无法解释方法为何有效。这个分层比单纯展示“有冲突，规则能解决”更值得研究。

它还没有证明需要新的协调算法。这里的条件约束很短、很明确，只要事实与规则都提供给 Agent，10/10 都自行避免关机；剩余可执行冲突也能被简单在线安全门消除。这是对后续方法创新的约束，而不是需要规避的负结果。当前回放只显示安全—任务服务取舍，不显示协调增加的时延；完整主张仍须在多类经审核任务中测可执行冲突、任务完成、等待和实测开销。

正式实验前有一项基础修正：现有通用 `run_closed_loop_episode` 只在状态版本变旧时检查 `requires`，而本轮发现不少模型提案自带当前就不成立的前提。若沿用旧执行器，冲突数会被高估。此次独立回放已在所有基线上检查前提，但历史结果不能直接与此表合并；应先统一执行语义并重跑相关基线。

## 下一步的判定门槛

将同样的“提案／前提／可执行冲突／保护后结果”分层推广到至少两类不同机制（例如共享设备冲突与跨设备环境冲突），任务需独立审核；给在线门控、状态同步或等待提供可测成本；再与无协调、前提检查、强规则、模型协调做同提案和闭环两种对照。若发现规则已在各类任务上低成本解决问题，则 benchmark 可以研究 Agent 的信息与执行缺陷，但不能声称发现了新协调方法的必要性。
