## 再测公平比较：共同最低安全门控

事件模拟器新增可选 `shared_safety_gate=True`，默认关闭以保持既有实验行为。打开时，每一种策略在物理动作启动前使用同一只读门控：检查当前在途动作是否与新动作有声明冲突、容量是否超限，以及动作开始/完成效果是否违反已声明状态约束。门控**只拒绝，不排队、重试或重新规划**。协调器可以提前安排安全启动时间，因此可比较它相对纯安全拒绝是否保留更多任务服务。门控使用 episode 内的真实容量和接地动作功率，属于理想化信息条件，不可据此声称现实可直接部署。C4 的在途事件风险也不由启动前门控解决。

`homecoord_bench/probe_shared_safety_gate.py` 使用 C1 两臂、C3 三臂，同一固定提案和 300 ms 提案延迟，对独立执行、设备锁规则、完整约束规则及单主 Agent 各做一轮；规则/约束另加 300 ms **合成**协调延迟，共 30 个试验单元。没有模型 API、真实设备或独立样本重复。

| 条件 | 共同安全门控下的结果 | 可得解释 |
|---|---|---|
| C1 冲突 | 独立执行安全拒绝能源动作，未服务全部任务；设备锁、约束规则、单主 Agent 都完成两项任务，且无门控拒绝。设备锁/约束规则在 0/300 ms 合成协调延迟下，全部必要动作完成于 6900/7200 ms。 | 同设备冲突用普通设备锁即可处理；不能据此主张复杂协调的新增收益。 |
| C1 安全对照 | 四策略都完成两项任务、无门控拒绝；额外 300 ms 协调延迟使首动作由 400 到 700 ms。 | 无冲突时，不必要的额外协调只增加等待。 |
| C3 低容量 | 独立执行和设备锁都被共同门控拒绝一项任务；约束规则与单主 Agent 完成两项任务，约束规则 0/300 ms 人工延迟下全部必要动作完成时间分别为 4400/4700 ms。 | 设备锁不是强容量基线；已知容量的确定性规则足以提前串行安排，无需 LLM。 |
| C3 高容量对照 | 四策略都完成两项任务且无门控拒绝；独立、设备锁和约束规则 0 ms 下完成于 3500 ms，单主 Agent 因串行化完成于 4400 ms。 | 过度串行也会损失时间；强规则应允许安全并行。 |

完整逐单元结果：`homecoord_bench/results/coordination_shared_safety_pilot_20260927.json`。结果单列 `final_goal_completion_time_ms` 与 `all_required_actions_completed_at_ms`：前者是最终家庭目标达成时间，**不是全部 Agent 服务完成时间**。C1 冲突中，独立执行虽在 6400 ms 达到温度目标，能源动作被拒绝，故后者为 `null`；甚至 `process_valid_success=true`，也不能代替“全部必要任务服务成功”。安全违规、门控拒绝和必要服务必须分别报告。合成 300 ms 是敏感性因素，不是测得的规则计算时间。

## 对下一轮的决定

1. C1/C3 仍作为审核草稿。先把 `review_packets/20260928/` 中的 Reviewer A/B 包分别交给两位领域审核者，使用[第一阶段盲审表](C1_C3_PHASE_A_BLIND_REVIEW_2026-09-28.md)判断 C1 的任务目标／设备语义、C3 的共享容量口径与参数自然性，再决定修改、降级为抽象资源任务或剔除；意见锁定后才提供策略结果并做第二阶段复核，修订后重新做配对审计。
2. 若经审核保留 C1/C3，强确定性规则应覆盖设备互斥、容量和状态前提，且所有策略有同一安全门控。现有 `ConstraintCoordinator` 在这两类任务上已是确定性强规则行为，不应包装为新算法。`RuleCoordinator` 仅是设备锁消融。
3. 当前没有一个比强确定性规则多做有效推理的独立“额外协调”方法；给同一规则人为增加 300 ms 只是在检验成本敏感性，**不能**由此推断何时该调用 LLM 协调器。若下一轮仍只有 C1/C3 这类已知规则即可处理的任务，应把它们当作强基线必须通过的诊断，而不是方法创新舞台。
4. 数据冻结后才扩充独立配对任务、实测规则/模型/设备各段耗时，并用固定提案和真实模型提案分别画任务服务—时延条件曲线。当前 30 个单元只验证设计和暴露基线公平性，不估计家庭冲突频率或论文级协调边界。服务—时延曲线应使用各必要动作的完成时间，不能用最终环境目标完成时间代替；时间预算是分析阈值，不能追写成原任务的硬截止时间。
