# C3 按发布状态生成晚到提案：运行前方案

补充此前晚到条件仅反事实复用同时发布提案的证据缺口。采用混合实验：早期任务复用上一轮真实提案及测得返回延迟；晚到任务在虚拟60秒发布时，从模拟器当前状态构造请求，重新调用DeepSeek。

固定N2-1／N4-1／N5-1、此前三轮早期提案、紧期限晚到、资源压力1.6／0.8，以及门控重试／已发布精确可行性退化服务两种策略，共36个分支、36次新晚到调用。每分支另运行旧晚到提案对照。输入／提案源哈希先锁定，每请求最多一次提供方尝试，保留失败分支，不自动重采样提供方错误。

在同一分支，早期提案与返回时延相同；新旧晚到提案的动作和API时延都可能不同，因此结局变化不能单独归因于状态推理。所有新请求必须在本任务发布时构造，隐藏required_action／action_template。以发布事件之前的状态变化日志重建可见状态和版本，逐字段核对。输出逐任务等待／完成迟延、全服务／按时、授权及动作语义。

当前观察权限保持功能Agent仅看自身设备。其他设备运行改变的全局状态版本不等同于功能Agent读到了共享容量或其他动作；明确记录可见状态是否真的不同于初始。若全部相同，结论仅是“晚发布时间／版本下的新提案复验”，不能宣称验证了复杂环境状态变化推理。

这不是全新端到端在线实验：初始提案仍复用，API调用在虚拟发布时同步执行后将测得耗时放入事件队列；并未按现实时间等待60秒，也不具有运行中真实网络并发。资源周期／功率／期限仍是合成条件，不注入协调计算时间。低压力为负对照，预告特权策略本轮不参与。
