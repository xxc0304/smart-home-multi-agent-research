# 本地协调运行时的墙钟耗时试测

日期：2026-09-27。该试测量的是当前 Python **离散事件模拟器**在本机上的处理时间，不是部署系统的真实端到端延迟。

## 测量口径

选取 3 种规则（容量约束先到先排、始终等待期限排序、容量感知期限排序），分别在 6.0 kW 冲突和 7.2 kW 可并行条件下，重放 EV 提案先返回与热水提案先返回两种历史时延顺序。每个组合预热 300 次、计时 2,000 次。计时范围包括 episode 拷贝、配置验证、DryRun 提案、事件调度、共同安全门控和结果评分。模型提案时延只作为虚拟时间写入仿真，程序没有等待这些时延；无 API 请求、网络通信或设备调用。

## 观测到的时间

12 个“容量 × 提案顺序 × 规则”组合中：

| 指标 | 12 组观测范围 |
|---|---:|
| 中位数 | 0.94–1.05 ms |
| P95 | 1.45–2.00 ms |
| P99 | 1.98–3.90 ms |

同一代码的波动已与规则差异相当或更大，因此不能根据这 12 组的微秒级差异给三种规则排出速度名次。P99 也会受到本机操作系统调度、解释器和后台进程影响。原始逐组结果在 `homecoord_bench/results/local_rule_runtime_benchmark_20260927.json`。

作为量级参照，此前保存的 10 条 DeepSeek 提案调用耗时中位数为 **1495 ms**。这只是历史 API 记录与本机模拟器运行时间的粗略对比，不能当作当前在线端到端测量；它提示模型等待可能比这套小型确定性模拟调度路径长约三个数量级。生产系统还要测网络、排队、设备命令与设备回执，不能把本试测的 1 ms 写成真实协调延迟或证明“1 秒内响应”。

## 可得结论

当前证据只支持：在这台机器上，这个两任务、小状态 Python 事件模拟器的一次完整模拟通常约 1 ms；几个确定性规则都落在同一量级。人工加的 300 ms 虚拟协调延迟与墙钟 CPU 运行时间是不同概念。若要判断现实系统是否能快速响应，后续应在实际部署路径上对 API 首 token／完整响应、协调计算、网络往返、设备启动回执分别打点；如暂时没有设备，应明确报告可测的软件段与未测物理段。

复现：`homecoord_bench/benchmark_local_rule_runtime.py`。本机样本为 2,000 次／格，结果对硬件、解释器和进程负载敏感。
