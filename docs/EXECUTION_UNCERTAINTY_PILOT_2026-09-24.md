# HomeCoord-Bench：命令回执与物理执行分离的小试验

状态：未审核的合成设计实验；不是设备实测，也没有调用 LLM API。目的仅是判断“执行结果不确定”能否构成可测问题，以及简单确认规则能否解决。

## 场景和对照

通风 Agent 在 0 ms 发出关窗命令，并立即得到“命令已接收”回执；空调 Agent 在 100 ms 收到制冷任务。制冷只能在窗户**物理上已关好**后启动，且希望在 1200 ms 内启动。命令接收、物理关窗和状态上报是三个不同事件。物理关窗时间取 0、200、600、1000、1400 ms，或执行失败；成功场景的被动状态上报再滞后 0、100、500 ms，组成 18 个参数格点。这些数值是占位参数，18 个格点也不是独立的真实设备样本，不能计算经验成功率。

比较四条规则：收到命令回执即启动；固定等到 500 ms；等待被动状态上报确认；从 100 ms 起主动查询设备当前物理状态（每次查询 150 ms，每 200 ms 可再查）。主动查询假设设备能返回准确的当前物理状态，是一条较强但简单的基线。

| 规则 | 物理前置条件违规格点 / 18 | 安全且按时启动格点 / 18 | 未启动格点 / 18 |
|---|---:|---:|---:|
| 只信命令回执 | 15 | 3 | 0 |
| 固定等待到 500 ms | 12 | 6 | 0 |
| 等被动状态确认 | 0 | 11 | 3 |
| 主动查询真实设备状态 | 0 | 12 | 6 |

其中 3 个执行失败格点和 3 个直到 1400 ms 才关窗的格点，任何遵守前置条件的策略都不可能在 1200 ms 前启动制冷。其余 12 个物理上可行的格点，主动查询全部安全且按时；它一共进行了 60 次查询。被动确认少达成的一个参数格点是关窗 1000 ms、状态上报再滞后 500 ms；主动查询在状态上报前观察到物理关窗。

脚本：`homecoord_bench/probe_execution_uncertainty.py`。逐事件结果：`homecoord_bench/results/execution_uncertainty_pilot_20260924.json`。运行：`python homecoord_bench/probe_execution_uncertainty.py`。

## 判断

“命令被接收不等于动作完成”是明确的评测缺口：当前 HomeCoord-Bench 闭环在动作生效事件时立即更新环境状态，尚未建模设备回执、执行延迟、失败和状态报告延迟。该缺口具有现实合理性，但本轮**没有发现强方法缺口**：如果能准确查询当前设备状态，简单的确认与重复查询就解决了所有可行格点。因此不能用本表声称已找到新协调算法的创新点。

若继续研究，应先用设备接口说明或实际日志校准延迟、失败和查询能力，并明确“查询结果本身是否可靠”。随后让协调规则、状态确认、超时重试等强基线在相同事件轨迹上比较安全、按时服务、额外查询和设备动作数。只有强基线存在稳定且现实的取舍，才值得扩展为 benchmark 核心任务或方法问题。
