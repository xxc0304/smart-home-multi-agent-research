# HomeCoord-Bench：HC-M07 持续状态干扰设计试验

状态：未审核的合成设计实验。没有修改原 HC-M07 候选任务，没有真实设备或模型 API 调用；通风速率、制冷速率、关窗时间及截止时间都是占位参数。本试验检查旧 C2“动作时间重叠”与“动作留下的持续物理状态”是否会给出不同结论。

## 从现有候选任务发现的评测边界

原 HC-M07 的确定性强协调轨迹在 700 ms 打开窗户，在开窗动作的 2000 ms 持续时间结束后于 2700 ms 开始制冷。现有评测返回 `process_valid_success=true`、C2 冲突数 0；但轨迹中没有关窗动作，制冷开始时 `devices.window=open`。这不是现有 C2 评测器在其规范内计算错误，而是它只禁止两个**动作区间**重叠，没有表达“开窗后状态持续为开”的家庭能耗策略。原任务还在开窗动作生效时立刻把 CO₂ 设为 900 ppm，因此没有通风过程。

## 独立的新任务模型

为使“先通风、后制冷”成为可执行任务，试验单独加入关窗动作和渐进式环境变化。窗户在 700 ms 打开，CO₂ 从 1600 ppm 随开窗时间下降；达到 900 ppm 后发出关窗命令，300 ms 后物理关闭。空调 Agent 的提案在 800 ms 可用。房间从 30°C 降至 24°C；窗关时制冷速率为 2°C/s，窗开时为 0.5°C/s。任务希望在 10000 ms 前同时达到 CO₂、温度与关窗目标，并遵守**本试验明确声明的策略**：空调运行时窗户不得打开。该策略代表能耗/舒适约束，不应误称为设备安全定律。

比较独立执行、只避免开窗动作与制冷动作区间重叠、基于当前窗户状态放行制冷，以及事先知道合成 CO₂ 下降速率的完整顺序计划。最后一种是拥有准确动力学信息的参考上界，并非公平的在线学习基线。CO₂ 下降速率取 100/150/300 ppm/s；另加初始 CO₂ 已达标（850 ppm）的无冲突对照。四个格点是参数敏感性检查，不是四户真实家庭。

| 条件 | 动作不重叠规则 | 状态检查／完整顺序 |
|---|---|---|
| 初始 CO₂ 已达标 | 800 ms 开始制冷，无策略违规 | 同样 800 ms 开始制冷，无额外等待 |
| CO₂ 下降 150 ppm/s | 2700 ms 开始制冷；其中 3000 ms 窗开且空调运行；8000 ms 完成目标 | 5700 ms 窗关后开始制冷；无策略违规；8700 ms 完成目标 |
| CO₂ 下降 300 ppm/s | 仍有 700 ms 窗开制冷 | 无策略违规，6400 ms 完成目标 |
| CO₂ 下降 100 ppm/s | 5300 ms 窗开制冷，虽 9700 ms 完成目标但违反策略 | 8000 ms 才能关窗并制冷，11000 ms 完成，错过截止时间 |

在四个格点中，独立执行和动作不重叠规则各只有 1/4 遵守持续状态约束；状态检查和完整顺序均为 4/4。后两者各有 3/4 在本试验的截止时间内完成。慢通风格点在给定动作集合和严格“窗开时不得制冷”策略下本来就无法按时完成，不能当作状态检查方法的失败。逐事件数据见 `homecoord_bench/results/persistent_state_pilot_20260924.json`，脚本是 `homecoord_bench/probe_persistent_state.py`。

## 对研究方向的含义

旧任务确实遗漏了持续状态导致的跨 Agent 干扰：仅把两个动作错开，不能保证它们的物理后果不冲突。但**简单状态检查规则就解决了本试验中所有可行的格点**，与完整顺序执行结果相同。因此它更像一个需要先修正的数据与评测定义问题，而不是已发现的新算法突破口。旧 HC-M07 没有关窗动作，直接给它追加“窗开不得制冷”约束会把任务变成不可解；必须先补齐可执行动作和环境变化模型。

若继续发展，应先审核“哪些动作效果是瞬时、哪些状态会持续、哪些是过程约束”，为不同设备组合构造可解与不可解的匹配对照；再把状态检查、时序规划、闭环重规划等强基线放在同一可复现环境中。只有它们仍表现出稳定的质量—时延取舍，才有方法研究空间。当前数据量、合成物理参数和单一任务模板都不足以支持这一判断。
