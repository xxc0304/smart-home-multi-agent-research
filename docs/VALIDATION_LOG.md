# HomeCoord-Bench 验证记录

## 2026-09-19：v0.2 最小闭环

本轮目标是验证数据结构与自动评测器，而不是评估 LLM 能力。所有时延均为人工轨迹中的测试值，不是模型 API 或真实设备实测结果。

### 已完成

- 将 4 条种子任务写成机器可读 episode；
- 固定事件轨迹格式，包括状态更新、协调决策和物理动作生效；
- 实现目标完成、过程约束、C1 直接冲突、C2 间接冲突、C3 资源容量冲突和 C4 过期动作判定；
- 构造 8 条人工金标准轨迹；
- 建立 7 项自动测试；
- 用 3 种脚本化架构做区分度冒烟试验。

### 自动测试结果

7 项测试全部通过。评测器能够：

1. 区分最终目标完成与过程有效完成；
2. 识别直接设备冲突、跨设备间接冲突和过期状态动作；
3. 避免把协调器的文本裁决计作首个有效物理动作；
4. 在无冲突任务中测出不必要串行化造成的时延。

### 脚本化冒烟结果

| 架构 | 最终目标成功率 | 过程有效成功率 | 冲突总数 | 首个有效动作时延中位数 | 完成时间中位数 |
|---|---:|---:|---:|---:|---:|
| CentralSingleAgent | 100% | 100% | 0 | 950 ms | 3650 ms |
| IndependentMultiAgent | 75% | 25% | 3 | 500 ms | 800 ms |
| RuleCoordinator | 100% | 75% | 1 | 600 ms | 850 ms |

这些结果来自手工轨迹选择，只证明种子任务具有预期区分度。它们不能用于论文中的模型优劣或系统性能结论。

### 当前判断

最小数据闭环成立：无协调多 Agent 响应快但容易产生过程冲突；中央串行策略安全但可能增加响应和完成时间；设备锁、优先级与版本检查组成的规则协调器能处理直接冲突与过期动作，但会遗漏跨设备的间接冲突。这恰好为下一阶段的真实执行器试跑提供可检验假设。

### 下一阶段

1. 实现统一的 Agent 输入与结构化动作输出协议；
2. 用同一低成本模型运行三种架构，避免把模型差异误当架构差异；
3. 每个配置先重复 20 次，只报告成功率、冲突数、P50 和 P95；
4. 根据失败轨迹修正数据歧义和评测器；
5. 通过后扩展到 20 条人工审核任务，再做强弱模型和异构模型消融。

## 2026-09-19：统一 Agent 协议与 API 适配器

已完成真实模型试跑前的工程链路：

- 每项任务显式绑定 `agent_id`，不再依赖数组顺序隐式分配；
- 统一 Agent 输入包含 episode、架构、当前时间、状态版本、完整状态、角色、任务、目标、约束、工具和待协调提案；
- 统一输出支持动作提案、协调决策、延后和无动作四类响应；
- 动作包含目标设备、操作、参数、依据的状态版本、前置条件、预计执行时间和预计功率；
- 输出使用严格 JSON Schema，所有对象禁止额外字段并要求完整字段；
- OpenAI Responses API 适配器默认使用 `gpt-5.6-luna` 和低推理强度，设置 `store=false`；
- JSONL 日志记录完整合成请求、结构化决策、API 端到端时延、模型、服务层级、输入／输出／推理 Token 和错误；
- API Key 只从 `OPENAI_API_KEY` 环境变量读取，事件日志不记录密钥。

离线协议试跑覆盖了 4 条 Episode、8 个专业 Agent。累计 12 项自动测试全部通过。本机目前未配置 `OPENAI_API_KEY`，因此尚未产生任何真实模型结果或 API 费用。

## 2026-09-19：DeepSeek 真实 API 冒烟试验

### 校验器修正

第一次真实运行完成 8 次 API 调用。自动校验最初报告 8/8，但人工审计发现 CleaningAgent 的一个嵌套前置条件使用了 `value`，协议要求的是 `value_json`。原因是本地校验器当时只检查动作顶层，没有递归检查参数和前置条件。

校验器现已增加嵌套对象字段、JSON 编码值、操作符、数值范围和列表类型检查，并新增回归测试。第一次运行按严格口径应记为 7/8，不能记录为完全成功。

### 严格校验后的复测

使用 `deepseek-flash`、非思考模式重新执行 8 次调用，结果如下：

| 指标 | 结果 |
|---|---:|
| API 调用成功 | 8/8 |
| 严格结构验证成功 | 8/8 |
| 最小时延 | 1208.185 ms |
| P50 时延 | 1410.099 ms |
| P95 时延 | 1630.116 ms |
| 最大时延 | 1665.093 ms |

当前 8 个样本中，最短模型调用仍为 1.208 秒。因此，在当前网络、接口和完整结构化输出设置下，仅依赖一次远程 LLM 调用尚未达到 1 秒内完成物理响应的项目目标。这只是小样本工程信号，不能据此形成稳定的 P95/P99 或模型普遍性结论。

## 2026-09-20：三架构最小执行闭环

### 闭环范围

新增事件驱动执行器，将结构化动作提案转换为设备动作，注入外部状态变化，并把完整轨迹交给确定性评测器。第一版支持：

- `CentralSingleAgent`：一个中央 Agent 可见完整状态并拥有全部工具，集中排序动作；
- `IndependentMultiAgent`：专业 Agent 按各自可见状态独立提交动作；
- `RuleCoordinator`：专业 Agent 加设备冲突、优先级和状态版本规则；
- HC-SEED-004 在过期清扫动作被拒绝后，可在住户离开时进行一次局部重试；
- 模型预计时长和功率作为提案元数据保存，设备实际时长和功率由环境能力表确定。

实现过程中修正了两个评测问题：评测器原先只能接受第一条协调决策；执行器原先错误地把模型预计持续时间当成设备实际持续时间。两项均增加了回归测试。目前共 24 项自动测试全部通过。

### DeepSeek 单次闭环试跑

使用 `deepseek-flash`、非思考模式，对 4 条种子任务和 3 种架构各运行一次。24 次模型调用均成功并通过严格结构校验，本轮没有触发格式重试。

| 架构 | 过程有效成功 | 冲突总数 | 首个有效动作时延中位数 | 完成时延中位数 |
|---|---:|---:|---:|---:|
| CentralSingleAgent | 4/4 | 0 | 1307.5 ms | 1869.5 ms |
| IndependentMultiAgent | 3/4 | 1 | 1333 ms | 1476 ms |
| RuleCoordinator | 3/4 | 1 | 1242 ms | 1310 ms |

模型调用时延为：最小 876.003 ms、P50 1145.923 ms、P95 1382.792 ms、最大 2280.330 ms。24 次调用共使用 20,513 输入 Token 和 3,056 输出 Token，按输入均未命中缓存估算，费用为 0.00491–0.00982 美元。

12 个架构—任务组合的首个有效物理动作均超过 1 秒，最快为 1123 ms。该结果包含固定的 100 ms 设备生效延迟，但不包含真实局域网和真实设备反馈，因此只能说明当前远程模型闭环尚未达到 1 秒目标，不能代表部署系统最终时延。

### 数据校准发现

- HC-SEED-003 稳定区分了架构：独立多 Agent 和规则协调器都会遗漏开窗与制热的间接冲突，中央 Agent 能够顺序执行；
- HC-SEED-002 未产生预设直接冲突，因为 EnergyAgent 看到舒适请求后主动选择了兼容动作；
- HC-SEED-004 未产生过期动作，因为清扫动作在 1500 ms 状态变化前生效；
- 因此下一版不能只保留单个固定时间点，而应围绕任务间隔、外部事件时间和 Agent 信息边界生成参数化变体。

本轮每个配置只有一次运行，不能据此报告稳定的 P95/P99、显著性或模型普遍性。聚合结果见 `homecoord_bench/results/deepseek_closed_loop_pilot_20260920.json`。

## 2026-09-20：参数化变体与 DeepSeek 单次扫描

### 变体与离线边界验证

围绕上一轮没有触发的直接冲突和过期动作，新增 11 条参数化变体：

- HC-SEED-002：EnergyAgent 的策略可见性取 `policy_visible` 或 `local_only`，第二任务间隔取 0、300、1000 ms；
- HC-SEED-004：住户进入时间取 800、1200、1500、1800、2200 ms。

dry-run 形成了预期边界：EnergyAgent 看不到舒适策略时，独立多 Agent 产生 C1，规则协调器能够阻止；住户在清扫动作生效前进入时，独立多 Agent 产生 C4，规则协调器拒绝旧动作并在住户离开后重试。新增两项边界回归测试后，自动测试共 27 项并全部通过。

### DeepSeek 单次扫描

使用 `deepseek-flash`、非思考模式对 11 个变体和 3 种架构各运行一次，共 33 个架构—变体组合。产生 71 次逻辑模型调用和 73 次 API 尝试；2 次输出未通过协议校验，均在一次格式重试后成功。包含失败尝试在内共使用 65,251 输入 Token、9,703 输出 Token，估算费用为 0.01561–0.03122 美元。

| 指标 | CentralSingleAgent | IndependentMultiAgent | RuleCoordinator |
|---|---:|---:|---:|
| 过程有效成功 | 11/11 | 8/11 | 10/11 |
| C1 / C4 冲突数 | 0 / 0 | 2 / 1 | 0 / 0 |
| 首个有效动作中位数 | 1383 ms | 1299 ms | 1443 ms |
| 平均任务服务率 | 72.7% | 81.8% | 59.1% |

直接冲突家族中，IndependentMultiAgent 在 `policy_visible` 条件下 3/3 无冲突，在 `local_only` 条件下只有 1/3 过程有效并产生 2 次 C1。RuleCoordinator 在两种可见性下均未产生 C1。这个结果支持“信息边界会改变冲突概率，显式协调能降低直接冲突”的可检验假设，但每个配置只有一次运行，不能报告稳定概率。

过期动作家族中，住户 800 ms 进入时 IndependentMultiAgent 产生 C4；1200 ms 进入时，模型和设备动作在事件前完成，因此没有过期；CentralSingleAgent 和 RuleCoordinator 在早期事件中拒绝旧动作并延后到住户离开后执行。RuleCoordinator 在 1500 ms 条件下拒绝旧动作后，重试模型选择继续延后，而当前执行器没有调度第二次唤醒，最终没有完成清扫。该失败揭示了恢复协议和延后动作语义仍需明确。

### 新增任务服务率

单次扫描还暴露出只报告全局目标和冲突会奖励安全 `noop`：某些运行没有执行 EnergyAgent 的节能动作，却仍满足舒适目标并被判为过程有效。评测器因此新增 `required_action`、逐任务 `task_service` 和 `task_service_rate`。它把“安全但牺牲任务效用”和“完成更多任务但发生冲突”分开报告，而不把两者压成一个总分。

成功 API 尝试的模型时延为 P50 1258.007 ms、P95 1633.266 ms；把无效输出及其重试成本计入逻辑调用后，P50 为 1260.022 ms、P95 为 1969.596 ms，最大值为 6213.663 ms。33 个架构—变体组合的首个有效物理动作仍全部超过 1 秒。

本轮是数据校准证据，不是论文结果。下一步应只对能区分机制的临界配置做重复试验，并在扩展到 240 Episode 前实现可持续的 `defer` 唤醒和恢复语义。

聚合结果：`homecoord_bench/results/deepseek_variant_sweep_20260920.json`。

## 2026-09-20：6 个临界配置的 5 次重复校准

从 11 个变体中选择 6 个能够区分信息边界、规则协调和过期动作恢复的配置，每个配置重复 5 次，共运行 30 个架构—变体实例。64 次逻辑模型调用产生 69 次 API 尝试，5 次无效结构输出均在一次重试后成功。包含无效尝试的费用约为 0.01437–0.02874 美元。成功 API 尝试的 P50/P95 为 1187.324/1430.933 ms；计入格式重试后，逻辑调用 P95 上升到 2686.392 ms。

### 直接冲突

| 配置 | 过程有效成功 | C1 | 平均任务服务率 |
|---|---:|---:|---:|
| Independent，策略可见 | 3/5 | 2 | 70% |
| Independent，仅局部状态 | 0/5 | 4 | 100% |
| RuleCoordinator，仅局部状态（修正前） | 2/5 | 3 | 80% |

“把全局策略写进专业 Agent 上下文”没有稳定消除冲突；即使策略可见，独立 Agent 仍在 2/5 运行中产生 C1。局部信息条件下，独立 Agent 服务了更多局部任务，但 5/5 都未达到过程有效成功。这形成了明确的安全—任务效用张力。

修正前的 RuleCoordinator 还暴露出异步顺序缺陷：低优先级 EnergyAgent 先返回时会立即获准执行，稍后返回的高优先级 ComfortAgent 无法撤回已经接受的动作。规则基线随后增加“同一资源上仍有高优先级任务待返回时，保留低优先级动作”的待决检查。修正后单独复测 5 次，结果为 5/5 过程有效、0 次 C1、5/5 都拒绝了低优先级节能动作，平均任务服务率为 50%。首个有效动作中位数从不协调局部配置的 1372 ms 增加到 1501 ms，当前小样本差值为 129 ms。

这个修正不是提出了论文新算法，而是建立一个可信的强规则基线。它也显示 benchmark 应明确测量“为等待潜在冲突任务付出的时间”，不能只测最终是否冲突。

### 过期动作

| 配置 | 过程有效成功 | C4 | 平均任务服务率 |
|---|---:|---:|---:|
| Independent，住户 800 ms 进入 | 0/5 | 3 | 60% |
| RuleCoordinator，住户 800 ms 进入 | 2/5 | 0 | 40% |
| RuleCoordinator，住户 1500 ms 进入 | 4/5 | 0 | 80% |

规则协调器稳定消除了 C4，但没有稳定完成任务：部分运行中模型在安全状态下仍选择 `noop` 或继续延后。执行器已经支持在过期动作被拒绝后进行局部重试，并对一次显式 `defer_until_ms` 再唤醒；测试总数增加到 29 项并全部通过。剩余失败应作为 Agent 决策与恢复能力问题保留，不能由模拟器强制改写为成功。

### 当前判断

重复校准使选题比单次试跑更可信：冲突不是只靠提示词或共享策略就能稳定解决；异步返回顺序会破坏看似正确的优先级规则；安全协调会增加等待并牺牲部分任务服务率；格式重试还会显著拉长尾时延。这些现象都直接对应“协调减少冲突需要付出多少响应时间和任务效用”的 benchmark 问题。

样本仍只有每配置 5 次、一个模型和两个任务家族，不能用于显著性检验或顶会论文结论。下一阶段应先把每个关键配置扩到至少 20 次，再增加资源容量与间接环境冲突的参数化家族。
