# 2026-09-14 研究讨论记录：异步执行安全、选择性修复与低延迟 Agent 执行

> 本记录整理今天围绕 VeraRAN、Agent JIT Compilation、SyncPlan、MultiAgentBench 和 Win Fast or Lose Slow 的讨论。它是研究过程记录，不代表已经确认的学术空白或最终论文命题。

## 一、当前研究判断

智慧家庭是主要验证场景，但希望抽象出一般的 Agent / 多 Agent 协调问题。当前最值得继续观察的主线是：多个 Agent 在共享且持续变化的环境中执行任务时，如何同时保证执行过程安全、保留已执行进度，并降低不必要的等待和重新思考。

目前不能把任何候选命题直接表述为已经确认的新颖学术空白。后续仍需要系统检索、强基线复现和实验验证。

## 二、VeraRAN：Agent 执行轨迹安全

VeraRAN 在 O-RAN 中讨论了一个重要动机：单个动作分别看起来合法，并不意味着多个动作异步执行时，整个执行过程安全。动作可能经历请求、交付、接受、应用、完成和观测等不同阶段，接口延迟和事件交错会产生不安全的中间状态。

它对我们的启发不是简单把 O-RAN 方法搬到智慧家庭，而是把问题转化为 Agent 版本：

> 当多个 Agent 异步改变共享环境时，如何保证整个执行过程安全，而不只是保证单个动作或最终结果安全？

这是一个可以跨智慧家庭、机器人、浏览器 Agent 和其他工具型 Agent 的简洁研究问题。它目前应视为重要候选方向，而不是已经确认的新颖问题。直接把 VeraRAN 的方法移植到智慧家庭，创新性可能有限；更有价值的是研究 Agent 特有的计划生成、工具调用、委派和动态状态变化。

## 三、Agent JIT Compilation：低延迟 Agent 执行

这篇论文的核心不是单纯使用更快的模型，而是把自然语言任务编译为可执行计划，减少逐步 fetch-screenshot-execute 循环中的重复 LLM 调用；同时生成多个候选计划，验证工具前置/后置条件，估计执行成本，并选择更低延迟的计划。它还根据延迟分布选择串行、并行或 hedging 调度策略。

对智慧家庭最重要的启发是：低延迟应被视为计划和调度问题，而不只是模型速度问题。可借鉴的核心原则是：

> 如何让 Agent 只在必要的决策点重新思考，其余步骤通过经过验证的计划快速执行？

智慧家庭不能直接照搬网页 Agent 的并行或重复执行，因为设备动作具有真实物理副作用。并行执行必须受到安全条件、设备状态和动作可重复性的约束。

延迟指标还必须区分：

- 事件检测时间；
- 首次有效物理动作时间；
- 完整任务完成时间；
- P95/P99 尾部延迟。

项目方案中的 <1 秒、<100 ms、<1 ms 仍然只是目标指标，不能写成已经验证的结果。

## 四、SyncPlan：预测式局部修复

SyncPlan 的基本思想是：先生成较长的多 Agent 协同计划，执行阶段由轻量运行时维持同步，只在计划变得不可靠时触发重新规划。它使用显式等待、死锁检测和 Plan Staleness Detector，以减少重复 LLM 调用。

对我们的研究，最有价值的不是照搬其等待机制，而是进一步追问：SyncPlan 可以检测计划何时变得陈旧，但能否只修复受影响的部分？因此可以把原来的“Agent 执行中的任务恢复”候选命题简化为：

> 当执行计划即将失效时，Agent 能否提前发现问题，并只修复受影响的部分，而不是让所有 Agent 重新规划？

这个方向同时连接准确率和延迟：提前发现可以减少错误执行，局部修复可以减少 LLM 调用并保留已经正确完成的进度。

可以用一句话概括其思想：

> 计划稳定时复用，计划临界时预警，计划失效时局部修复。

目前不应再把预测失败、时间预算、云边端联合调度、风险函数等全部塞入命题；它们是后续方法或实验设计的可能组成部分。

## 五、MultiAgentBench：过程级评估

MultiAgentBench 的主要贡献是说明多 Agent 系统不能只看最终任务是否完成，还要评估协作过程、里程碑进展和协作质量。它比较了不同通信拓扑和协作策略，但本身主要是 benchmark 和评测框架，不是新的执行机制。

这对智慧家庭的启发是：最终设备状态正确，并不代表过程良好。系统可能经历了很长等待、重复动作、Agent 冲突、不安全中间状态或过度拒绝。

因此，项目评估应同时关注：

- 事件检测、首次有效物理动作和完整完成延迟；
- 里程碑进度、等待和阻塞时间；
- 冲突、重复动作、撤销和重规划次数；
- 执行轨迹安全性；
- 错误拒绝率和不必要的保守行为。

MultiAgentBench 暂时不形成独立核心命题，而是作为所有候选方法的评测思想。

## 六、Win Fast or Lose Slow：自适应思考调度

这篇论文研究的是模型推理配置层面的速度—准确率权衡，例如动态选择模型规模和量化精度。它说明不存在对所有任务都适用的固定最优速度—准确率点。

对项目的主要启发不是重复做模型量化，而是把这种权衡上移到 Agent 编排层：

> Agent 什么时候应该快速执行，什么时候值得继续思考？

它与低延迟执行的关系是：

- Agent JIT 主要回答“什么时候可以不再思考”；
- Win Fast or Lose Slow 主要回答“需要思考时，应该思考多久、使用多少决策资源”。

因此它不是新的独立命题，而是对低延迟方向的细化。更完整但仍然简洁的表述是：

> Agent 如何在安全前提下决定何时思考、思考多久以及何时执行，从而降低实际响应延迟？

安全不应简单作为速度和准确率之间的普通加权项。应先满足硬安全约束，再在安全方案中优化延迟和决策质量。

## 七、目前保留的核心候选命题

经过今天的讨论，建议暂时保留以下三个方向：

### 1. Agent 执行轨迹安全

> 当多个 Agent 异步改变共享环境时，如何保证整个执行过程安全，而不只是保证单个动作或最终结果安全？

### 2. 预测式局部修复

> 当执行计划即将失效时，Agent 能否提前发现问题，并只修复受影响的部分，而不是让所有 Agent 重新规划？

### 3. 低延迟 Agent 执行

> Agent 如何在安全前提下决定何时思考、思考多久以及何时执行，从而降低实际响应延迟？

这三个方向之间存在关联，但暂时不强行合并：

- 执行轨迹安全关注“过程是否安全”；
- 预测式局部修复关注“计划失效后如何处理”；
- 低延迟执行关注“如何减少不必要的等待和思考”。

多 Agent 状态冲突与协同、任务契约、风险感知、云边端调度和 benchmark 暂时作为方法机制或评测维度，不单独列为新的核心命题。

## 八、当前证据与研究假设

已有证据：

- 相关论文分别证明了异步执行安全、计划陈旧检测、JIT 计划/调度、过程级多 Agent 评估以及任务相关的速度—质量权衡具有研究价值。
- 这些论文也说明，单看最终成功率或平均延迟不足以评估真实 Agent 系统。

仍属研究假设：

- Agent 执行轨迹安全是否能形成比现有领域方法更一般的抽象；
- 预测式局部修复是否能在保留安全和成功率的同时，显著降低重规划延迟；
- Agent 层自适应思考调度是否能比固定快/慢模型路由更好地改善智慧家庭的首次有效动作时间和 P95/P99 延迟；
- 上述增量是否足以支持方法论文、benchmark 论文或部署系统论文。

当前仍处于文献讨论阶段，暂不把这些假设写成已经验证的结论。
