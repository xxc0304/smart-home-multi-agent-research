# C1/C3 语义与在线信息边界审计

日期：2026-09-30。状态：作者侧静态审计和候选输入修订；不是独立审核或正式 benchmark 冻结。**本轮未调用模型 API，也未连接真实设备。**

## 本轮做了什么

检查了 2026-09-30 新 C1 命令任务、C3 洗衣—烘干—供暖任务的字段语义、运行时策略能读取的信息，以及实际构造给 Agent 的请求。发现旧稿的模型可见 episode ID 含有 `OVERLAP`、`NONOVERLAP`、`RHO=...` 条件标签；旧 C1 Agent 还默认接收全局 goals 和 constraints。当前保存提案回放没有重新调用模型，因此这些问题**不改变已经报告的固定提案结果**，但会影响之后的真实模型采样。

原稿与哈希版本均保留。另建 `homecoord_bench/revision_drafts/20260930_core_review_v03/`：

- C1 两个 Agent 显式设置 `goal_visibility=local`、`constraint_visibility=local`；模型侧使用与实验条件无关的 opaque episode ID，并开启 `blind_future_task_arrivals`。
- C3 专业 Agent 显式保留本地目标、约束和状态可见范围；模型侧 episode ID 不再包含容量压力档，并开启 `blind_future_task_arrivals`。
- 任务目标、动作参数、周期、负载、截止时间和容量均未改动。新版五个 JSON 均通过现有 episode 结构校验。

逐个构造 13 份真实 Agent 请求后，没有发现请求含有其他 task ID、实验臂标签、全局目标或全局约束；C1 的 EnergyAgent 请求中也没有 `comfort_active`。逐字段请求结果与五份新候选的哈希见 `homecoord_bench/results/core_semantics_information_audit_20260930.json`，结构校验和 C1 固定提案复核见 `homecoord_bench/results/core_semantics_information_audit_validation_20260930.json`。

## 任务语义审查

### C1：同一空调的制冷与关机

两个条件只改变 EnergyAgent 任务的发布时间。共享安全门控和 C1 冲突识别仍读取完整环境状态；专业 Agent 只拿到自己的状态、目标和工具。EnergyAgent 看得到空调状态与峰值告警，但不知道 `comfort_active`，也没有全局舒适约束。这是一种明确的信息边界设定，不代表所有家庭系统都这样工作。

原稿“nonoverlap”一臂的时间需要准确解释：Comfort 提案在 300 ms 返回，命令在 400 ms 启动，6 秒后于 6400 ms 完成。Energy 任务在 6200 ms 发布，早于 Comfort 完成 200 ms；但 Energy 提案和命令延迟后，最早在 6600 ms 执行。因此它是**动作区间不重叠**的对照，不是“后一任务在前一任务完成后才发布”的对照。重叠臂 Energy 在 200 ms 发布，最早于 600 ms 启动，会与 Comfort 服务动作重叠。若论文关注任务发布时序，需要按“后一任务提前／延后于当前动作完成多少时间”明确报告。

屏蔽全局信息后的 DryRun 固定提案复核仍得到同一大体模式：重叠条件下独立执行的关机被共同门控拒绝、第二项服务未完成；设备锁、约束调度和等齐提案均能完成两项服务，等齐使首动作从 400 ms 推迟到 600 ms。非重叠条件下各策略都完成两项服务，首动作均为 400 ms。此结果支持 C1 作为“设备锁已足够”的负控制；它仍是作者脚本提案，不是新增 DeepSeek 样本。

### C3：洗新衣物、烘干另一批衣物、房间供暖

三个专业 Agent 只看到自己的任务、本地设备状态和自己的工具；不接收其他 Agent 任务、共享容量或全局目标。三个任务都在 `t=0` 发布，模型提案按不同延迟返回。因而此处测的是**任务同时可见、动作提案异步返回**时的排序与等待；并非任务本身陆续到达。

在线调度策略只按已发布任务排序。`CapacityAwareDeadlineCoordinator` 另外读取公开的总容量、任务功率上界和已发布任务期限；本结构所有任务在 `t=0` 已发布，所以这些信息对该基线可用。它不读取未来到达任务。安全门控另有更强的信息：能看见当前动作参数与环境状态并阻止不安全启动。所有可部署基线共用此门控，所以结果只能解释为**给定共享安全层下的调度比较**，不能证明去中心化系统仅凭本地传感器也能保证同等安全。

首次真实模型提案是在 `ρ=1.2` 模板上采样，episode ID 当时显式包含压力标签；同批提案后来被回放到 `ρ=0.8/1.6`。这意味着已有的 DeepSeek 数据可以比较调度器面对同一批提案的反事实结果，但不能证明模型在不同容量压力下会生成相同或不同的提案。之后如需比较模型对压力的理解，必须分别调用匿名化输入或设计压力不可见的配对请求，并作为新的样本报告。

## 当前判断与后续门槛

1. 当前固定提案的 C1/C3 结果保留为探索证据，不回写成新模型结果。C1 的新候选离线复核没有改变策略大体排序。
2. 新候选 v0.3 已解决模型输入里直接暴露实验臂标签和 C1 全局目标／约束的问题；13 份构造请求中未检出这些泄漏。最终数据仍应给各臂随机、臂间不相关的公开 ID，避免固定字符串成为可学习线索。
3. 当前 C3 可以支持受控的“同时发布、异步提案”机制比较。它不能支持任务到达预测、多种家庭拓扑或真实配电规律的结论。下一项结构复核应至少改变任务关系与释放机制，且在看结果前锁定任务、容量、期限、信息契约和分析指标。
4. 试图重新连本机 SimuHome API（`127.0.0.1:8765`）时连接被拒绝，因此本轮没有新增模拟器回放。已有 2026-09-28 C1 SimuHome 命令状态交叉检查仍可作为同类 `cool/off` 命令映射证据，但不能当成这五个 v0.3 JSON 的新运行结果。

### 证据边界

当前最有价值的结论仍是：简单 C1 冲突能被简单锁处理；C3 中资源压力会改变等待／排序的价值。但独立任务结构、匿名化输入下重新采样、独立任务语义审核和闭环模型实验仍未完成。因此，本审计提升了后续实验的可信度，**没有单独提升已经观察到的效果强度或证明跨任务泛化**。
