# C3 可见家庭需求更新：运行前方案

本轮仍研究正确服务与冲突—时延的关系，不提出新算法。上轮晚到功能Agent可见状态未变化，故设计真正进入状态请求的需求更新对照。

三个既有结构N2-1／N4-1／N5-1，各有四臂：需求A稳定、A到B更新、需求B稳定、B到A更新。A为原始服务模式，B为另一公开模式；工具命名／描述沿用既有候选。更新在虚拟30秒发生，任务在60秒发布。功能Agent只新增观察自己设备的household_requests字段，其中revision和自然语言requirement明确当前需求。

四臂任务goal一致，要求根据当前记录选择服务；评分所用required_action和action_template继续隐藏。更新前后模式具有相同公开时长和功率，容量和截止不变，避免把服务理解和成本变化混在一起。最终正确模式只用于评分，不加入goal。更新已发生在自身任务开始之前，**不是对正在执行任务的局部修复／撤销实验**。

24个派生候选：三结构×四臂×高／低压力。运行前检查结构合法、工具公开成本相等，以及知道未来的分析调度器能给出满足期限的计划。参考当前需求与冻结初始需求两个已知模式选择器，只作评分／干预诊断，不是有竞争力的方法；两策略×两选择器×24候选，共96次无API检查。

新API采样固定精确可行性退化规则、高压力，复用上一轮rep1／rep2早期真实提案及返回时延，只对晚到需求调用模型。三结构×四臂×两轮共24次新请求，最多一次提供方尝试，失败保留不修复／重采样。每条新晚到提案在两压力×两策略回放，共预期96次；只有采样配置按现场状态新生成，其余是反事实回放。

记录协议／授权／语义正确、可见状态相对初始是否变化、全任务服务及按时、逐任务启动等待／完成迟延。从事件前缀重建发布状态，并要求现场分支能由保存提案无API复现。错误提案和错误协议均保留，分别报告。

如果模型全部选对，应接受负结果：本轮仅建立可见动态需求与调度结果分开计分的工具，不能声称发现了LLM动态推理缺口。冻结需求诊断失败是设计预期，不能当作打败强基线的算法贡献。所有参数仍受控合成，未加入协调计算耗时或真实设备。
