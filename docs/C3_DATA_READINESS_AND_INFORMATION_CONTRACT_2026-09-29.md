# C3 数据准备度与在线信息契约

日期：2026-09-29。状态：作者侧机器审计；尚未冻结 benchmark 数据。

## 本轮完成的检查

以厨房回路和早晨出发两个基础模板为单位，组合三档名义容量压力、六个未来紧急任务到达时间及三种协调策略，形成 108 个有／无未来任务的配对策略条件。使用一批已保存的模型提案，仅回放和检查输入；没有新 API 调用。

每个配对条件在紧急任务发布前满足：

- 已发布任务的字段、初始状态、容量、约束和外部事件相同；变化仅是额外任务及其相关元数据。
- 相同策略收到的 Agent 请求完全相同，包括可见目标、状态、任务、episode 和 request 标识。
- 紧急任务发布前的执行事件序列完全相同。强先验规则在有／无插入两侧得到相同的潜在任务先验，不读取本次实际会否发生。

结果：**108/108 配对条件通过，0 个因素隔离错误**。这是避免“提前知道答案”的必要检查，但它不验证任务的现实性，也不提供 108 个独立统计样本。审计脚本为 `homecoord_bench/audit_c3_online_information_contract.py`，机器结果为 `homecoord_bench/results/c3_online_information_contract_20260929.json`。

`blind_future_task_arrivals` 模式另作了两项防漏处理：没有公开的 `base_episode_id` 时拒绝生成请求；若已发布与未发布任务映射到同一个全局目标路径、无法判定该目标能否隐藏，也拒绝生成请求。当前两个模板的目标路径互不重合。这个检查不等于所有字段对任意新模板都已证明无泄漏；新模板必须重新运行配对审计。

## 下一项应做的具体工作

优先建立**基础任务结构级**候选库，而不是继续在现有两个模板上加随机种子。每个新增候选先记录任务来源、设备能否执行命令、额定与执行时长证据、期限为何合理、Agent 可见信息、是否存在安全可行排程；再配一个只改变预先声明因素的无冲突或无插入对照。若某字段没有现实来源，可留作明确标记的合成压力子集，不应补造“真实”参数。

现有 EV／热水器双任务场景可用作**规则容易解决的负控制候选**，但其容量、效率和期限未校准，且与早晨模板共享 EV／热水设备，不宜冒充完全独立的留出家庭。只有新增未参与方法设计的基础结构后，才划分开发与留出测试，并在冻结条件上重新采样模型提案。此后再考虑是否存在同信息强规则无法覆盖的稳定协调缺口。
